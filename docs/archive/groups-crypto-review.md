# Groups: cryptography review

**Status (14 October):** every finding below is applied in the revised `docs/groups-design.md` and `docs/groups-threat-model.md`; N1 is applied in full rather than deferred, with group signatures made hybrid Ed25519 + ML-DSA-65 in version 1. People's identity signatures remain Ed25519 and are the spec's next open design.

Independent review of `docs/groups-design.md` against its threat model, `docs/integrity-design.md` and the crypto code (TS and Rust). 14 October 2026.

## Verdict

Do not build this as written. The statements are cleanly domain-separated and suite 3 is a sound base. Two flows fail at what they claim. Child conversion and release rest on the master-key rotation flow, which in the code keeps the identity private keys, the settings key and the personal workspace key, so a guardian who opened the root once keeps everything. Guardians and `members` holders are absent from the signed roster, so the server picks who receives a child's root. The roster and succession rules let a removed holder fork history, let the chain check be skipped, and let a holder fold in server-supplied identity keys unchecked. All are cheap spec fixes.

## Ambiguities to resolve

1. 2.2 "groupId (UTF-8)" → "the 36-character lowercase hyphenated UUID; the words are the digest's first 132 bits, as `fingerprintWords`".
2. 2.3 "(empty for version 1)" → "the JSON string `""` for version 1, otherwise base64url of 32 bytes".
3. 2.3 "Sorted by `userId`" → "strictly ascending bytewise, no duplicates; verifiers re-encode and refuse differing bytes".
4. 2.3 `kemPublicKeyDigest` → "SHA-256 of the 1184-byte key, base64url; the signer checks the KEM binding first".
5. 2.3 "at least the highest version" → "equal to it with the same digest, or previous + 1 with every intermediate roster verified".
6. 4 "Successions since `after`" → "successions whose `oldVersion` is at or above the key version of the roster at `after`".
7. All versions → "integers from 1 to 2^53−1".
8. 2.4 "a holder makes a new key" → "a holder active with `members` on the latest roster; `newVersion = oldVersion + 1`".
9. 2.5 "the context matches" → "`groupId` is the vouching roster's group, `workspaceId` belongs to it, the version is at or above the stored mark, and the grantee and key version are the reader's own".

## Checked and sound

- Every new domain string (`hushos/group/*`, `hushos/account/guardian-seal`) differs from every existing statement and AD (`hushos/drive/*`, `hushos/identity/*`, `hushos/id`, `hushos/workspace/grant`, `hushos/settings`), with the version second. The group key signs only group statements. No confusion is possible across kinds or versions.
- Suite 3 resists key-compromise impersonation: authenticity comes from the sealer's signature, checked before decapsulation, not from a static DH. The salt binds the KEM ciphertext, the ephemeral key and the recipient's key, and ML-KEM binds the encapsulation key.
- The group fingerprint prefix differs from `hushos/identity/fingerprint/v2`. With a canonical groupId every field has a fixed length. 132 bits defeats a second preimage.
- The `group` and `workspace` id kinds fit the scoped-id scheme, with no existence oracle.
- Admission is a two-way word check plus an atomic transaction; the server never seals a grant.
