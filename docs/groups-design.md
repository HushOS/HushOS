# Groups: the core families and companies share

This document fixes the group core: groups, members, invitations, the signed roster that lets members trust each other, shared areas, spaces, pooled storage, the payer and child accounts. Family plans ship on it alone; company plans add the custody key, admin browse, policies, audit, offboarding, storage control, domains and SSO on top (see the build plan, "HushOS for Companies — Build Plan", whose decisions this follows). Each statement below is the exact byte layout the web (`packages/crypto`) and the Rust core (`crates/hushos-core`) must produce and accept, pinned by shared fixtures.

Revised on 14 October after the independent review in `docs/groups-crypto-review.md`: every finding there is applied, and group signatures are post-quantum from the first version. Revised again on 15 October after `docs/pq-devices-crypto-review.md`: roster entries carry each member's ML-DSA key digest, and every conversion waits 7 days.

Nothing here changes what the server can read. It learns who is in which group, which it must know to authorise anything; every key it handles stays sealed.

## 2. Cryptography

### 2.1 Encoding

Statements are canonical JSON arrays as in `docs/integrity-design.md`, with these rules every implementation follows exactly:

- **Ids** are 36-character lowercase hyphenated UUIDs, validated on both sides; anything else is refused.
- **Byte strings** are base64url without padding, including key digests (never hex).
- **Integers** (versions) run from 1 to 2^53−1; Rust refuses larger values, so TS and Rust agree.
- **The empty digest** (`previousRosterDigest` of version 1) is the JSON string `""`; otherwise it is base64url of 32 bytes.
- **Lists** (roster members, roles) are sorted strictly ascending by the bytes of their sort key, with no duplicates.
- **Verifiers re-encode.** A verifier rebuilds the statement from the parsed fields and refuses any document whose bytes differ, so no two encodings of one statement exist.
- **One grammar beneath the fields** (`canonical.ts` / `canonical.rs`, enforced by both the encoder and the parser, whatever the platform's JSON library allows):
    - at most 4 MiB (`MAX_STATEMENT_BYTES`), no byte-order mark;
    - a JSON array nested at most four deep, of strings and integers only: no objects, booleans, null, floats, exponents or `-0`;
    - strings of printable ASCII other than `"` and `\`, so there is never an escape, a lone surrogate or a non-ASCII byte;
    - integers from 0 to 2^53−1;
    - the bytes are exactly the compact encoding of what they hold.
- **Empty byte strings** are never canonical: both twins' field helpers (`bytesOf`, `bytes_of`) refuse `""`. (The shipped general base64url decoders differ on `""` — the web refuses it, the core decodes it to nothing — and stay as they are; no group field reaches them without the field helper and a non-zero length.)
- **Identity key versions** (keys statements and succession links) run from 1 to 2^53−1 in both twins, like every statement integer.
- **`kemPublicKeyDigest`** is SHA-256 of the 1184-byte ML-KEM-768 public key, and **`mlDsaPublicKeyDigest`** SHA-256 of the 1952-byte ML-DSA-65 public key, both base64url. A signer checks the identity's keys statement (`docs/identity-pq-design.md` 1), which binds all four keys, before putting either digest in a statement. Version 2 identities carry no KEM binding.

### 2.2 Group signatures are post-quantum

The group key is a pair: an Ed25519 key and an ML-DSA-65 key (FIPS 204; `ml_dsa65` in `@noble/post-quantum`, the `ml-dsa` crate in Rust, beside the ML-KEM libraries already used). Its seed is 64 bytes: 32 for Ed25519, 32 for ML-DSA-65 key generation. Every group signature is both:

- an Ed25519 signature (64 bytes) over the statement bytes, and
- an ML-DSA-65 signature (3309 bytes) over the same bytes with FIPS 204 context string `hushos/group/v1`.

A group signature is valid only if both verify. A quantum adversary must break ML-DSA, a classical one Ed25519; neither alone forges a roster or a succession.

People's own identity signatures on seals (2.3, 2.6, 2.9), rosters' signer signatures and identity successions are hybrid too: `docs/identity-pq-design.md` adds an ML-DSA-65 identity key (context `hushos/identity/v1`) and ships before group milestone 1, so no roster, seal or succession is ever signed by Ed25519 alone. A reader checks a member's ML-DSA half only under a key whose digest is the member's roster entry's `mlDsaPublicKeyDigest` (2.4) or the reader's version 3 pin of them, never under a key the server serves on its own. Writer statements, the file and folder signatures inside areas, are not hybrid: they stay Ed25519, as everywhere, until their planned upgrade (`docs/identity-pq-design.md` 7). A signer identity signature below is that hybrid signature (3373 bytes).

### 2.3 The group key and its seals

The group key is made on the creator's device. Its fingerprint, shown as twelve words exactly as a person's are (`fingerprintWords`: the first 132 bits of the digest), is:

```
SHA-256("hushos/group/fingerprint/v1" || groupId (36 ASCII bytes) || ed25519PublicKey (32) || mlDsaPublicKey (1952))
```

**The words are always the version 1 key's**; pins keep the version 1 keys. Joining does not use them: a newcomer compares the join code instead (2.4, 3.2), which pins the version 1 keys through the chain it verifies, successions included (2.5). The core keeps `groupWords`; no 1c client shows them.

The 64-byte seed is sealed only to members whose roster entry has the `members` role, with the share suite 4 construction (ephemeral X25519 + ML-KEM-768 to the holder's identity, signed with the sealer's hybrid identity signature; `docs/identity-pq-design.md` 3), under HKDF `info` `hushos/group/key-seal/v1` and AEAD associated data equal to the statement without its final digest:

```
["hushos/group/key-seal",1,groupId,groupKeyVersion,holderUserId,holderKeyVersion,sealerUserId,rosterVersion,rosterDigest,sha256(sealed)]
```

`rosterVersion` and `rosterDigest` name the sealer's latest accepted roster when they sealed: a sealer refuses to name any other, and an opener refuses a seal whose roster is not on its own accepted chain (a later roster than it has, or one from another history). A seal made on a branch, such as by an honest holder whom a withheld removal kept on a removed holder's history, so never opens on the real chain. That alone does not stop a device kept at the branch point, whose latest roster is on everyone's chain: area grants are therefore also bound to the area keys the roster lists (2.6), so such a device cannot hand on a key the real chain never listed. A key seal needs no more: its opener derives the group key from the seed and compares it with the chain's. A holder opens a key seal only if the sealer is active with `members` on the latest verified roster (or is the creator, for version 1, while active), and refuses a seed whose derived public keys are not the group key at `groupKeyVersion`.

### 2.4 The roster

One signed document names every member, their keys and their roles:

```
["hushos/group/roster",1,groupId,kind,rosterVersion,previousRosterDigest,groupKeyVersion,signerUserId,members,areas]
members = [[userId,keyVersion,encryptionPublicKey,signingPublicKey,mlDsaPublicKeyDigest,kemPublicKeyDigest,status,roles,sinceVersion], ...]
areas   = [[workspaceId,workspaceKeyVersion,commitment], ...]
```

- `members` is sorted by `userId`; `roles` is a sorted subset of `billing`, `guardian`, `members` (companies add `data_admin`, `recovery`); `status` is `active` or `left`; `sinceVersion` is the roster version the entry last changed at. Entries for former members stay.
- `previousRosterDigest` is SHA-256 of the previous roster's statement bytes, so rosters form a chain; `rosterVersion` is always the previous one plus one.
- A roster has at most 10,000 entries (`MAX_ROSTER_MEMBERS`, both twins, built and parsed), well inside the 4 MiB statement cap (2.1); departed members' entries count toward it.
- `areas` carries a row only for each area the roster creates or rotates (round 10: delta rows), sorted by workspace id, each with the new key's version and commitment (2.6); at most 1,024 rows per roster (`MAX_ROSTER_AREA_ROWS`, both twins, built and parsed), as many as a family may have areas, so the roster that removes someone from a family, rotating every area, always fits (about 110 KB at the cap). A roster that touches no area carries `[]`. The accepted chain folds the rows into every commitment each area has had (`areaKeys`), so a roster's size no longer grows with the number of areas.
- It carries a group signature (2.2) by the group key at `groupKeyVersion`, and the signer's own identity signature over the same bytes, so every roster says who made it. The signer must be active with `members` on the previous roster (the creator, for version 1), and active on the roster they sign: a holder's own departure, with the rotations it carries, is another holder's to sign. Every roster keeps at least one active `members` holder, so the group can always sign its next roster (round 11; both rules hold in `rosterRules` / `roster_rules`, so `nextRoster` and `checkNextRoster` inherit them).

**Folding in changes.** Before signing, the signer's client checks every changed entry: a new member's keys, the ML-DSA and ML-KEM keys by digest, are the ones the word check confirmed; a member whose identity changed is followed by the group walk (2.8) from the entry's keys, ML-DSA digest included, to the served ones, on each link's version 2 signature (`foldInEntry`; consent buys nothing there, 2.8), and the entry moves straight to the served identity however many links that takes, once its keys statement holds; an entry whose chain fails stays as it was, and the member is shown as needing a check.

**Checking a member's signature through the roster.** The reader takes the Ed25519 key from the entry and the ML-DSA key from the server, and uses the served key only if its SHA-256 equals the entry's `mlDsaPublicKeyDigest`; otherwise the signature does not verify. This covers every member signature checked through a roster: key seals, area grants and rosters' signer signatures. A member seals and grants only with the Ed25519 and ML-DSA keys their current entry names: after replacing their identity they seal nothing until a roster folds the new one in (milestone 1 trades that liveness for one rule an opener can check). A seal or grant made before its signer's identity was folded in still opens: given the signer's served identity and succession links, the opener also accepts the keys on the signer's own verified succession path from the first set of keys their entries named on the chain (the one a words check admitted) up to and including the keys their entry names now, and never past them. So a seal made under the entry's keys still opens after the member moves on, and one made under keys no roster has folded in never opens. A key a holder wrote into an entry later never opens a seal, even with a link its planter signed from it. Only an active `members` holder seals the group key (the creator, for key version 1, while active), and only an active member grants an area; the openers ask the same. A member whose identity forked (2.8) lends no history: their seals open only under their entry's own keys, confirmed by the served ML-DSA key. A key seal opens only for the holder and key version it names. Each member's own client checks its own entry on every roster and raises a hard warning if it names none of their identities, or one older than the roster before named (a rollback to a replaced identity). An entry that changed at a roster to one of their own identities older than their newest is a soft note (`ownEntryBehindAt`, reported by the acceptance that adds the roster, not kept in the cache): a holder folded in an identity the member has since replaced, or the member rotated just after a fold-in. A succession list the server cuts short (served identity S1, links E→S1, while the member is at S2) cannot be told from an honest one without a per-member high-water mark of link-verified key versions, which milestone 1 does not keep.

**The area rules** (`checkAreas`, Rust `check_areas`). Each row is an area's next version: 1 for an area the chain has not seen (every row on roster 1 is one), or one above the latest version the chain lists for it. A row at a version already listed, a skipped version, or a new area above 1 is refused, and so is a row whose commitment the chain listed before, in any area at any version, or twice in one roster: the commitment is of the key alone (2.6), so a repeat is a key used before, and a no-op rotation, a rotation to another area's key or one key for two areas is refused from any client (a set lookup per row). So every version of every area is listed by exactly one commitment on exactly one roster, no key twice, and the accepted chain keeps them all (`AcceptedRosters.areaKeys`, cached with the rest). Two rules tie areas to membership:

- **A removal carries its rotations.** In a family, a roster that marks anyone `left` who was `active` on the roster before must rotate every area the chain has, in the same statement; one that leaves any area's key unchanged is refused (`A roster that removes a family member rotates every area.`). Every family member can open every family area, so this is exactly the set the departing member could open. `nextRoster` refuses to build it otherwise; `areasToRotate` (Rust `areas_to_rotate`) names the areas the client must rotate. A company roster is not held to it: it does not say who opens which area, so a company's rotations stay a client duty (3.3).
- **A family has at most 1,024 live areas** (`MAX_FAMILY_AREAS`): a row that would make the chain list a 1,025th area that is not retired is refused, so the removal rule can always be met in one roster. Format 2 (2.10) retires an area with a tombstone at its next version: it stops counting, is never rotated again, and its earlier grants still open.
- **Rows come from keys.** `nextRoster` takes the new area keys (`areaKeys`) and computes the rows itself (`areaRows`), refusing an area named twice and any key whose commitment repeats, as acceptance does: one HKDF per new key and a set lookup, so a removal at the cap costs 1,024 HKDFs however long the chain (round 12; round 11 compared each new key with every commitment, a cost a holder could grow with rotation-only rosters until their own removal took minutes). The commitment function is not in the package's exports (Rust: not exported to the apps), so a client cannot build a row by hand. A signer who hand-builds a hollow row (a "new" commitment over a fresh key while handing the removed member the old one, or over a key the removed member was given out of band) defeats the rotation no check can see: that is the signer's betrayal, like leaking the key. A rotation to any key the chain listed before, in any area, is refused by acceptance itself.
- **No admission on a holder's removal.** A roster that drops a `members` holder (the one that makes a succession due, 2.5) admits no one: no entry new to it or turned `active` (`No one is admitted on the roster that removes a key holder.`). The newcomer then comes in on a later roster, under the group key that succession made, which the removed holder never held (the join code, below, names it).

**The entry rules.** From one roster to the next, entries never disappear (a former member stays, marked `left`), and each entry's `sinceVersion` is the version it last changed at. That is all: the keys an entry names, and its `keyVersion`, are a holder's claim and nothing more. Acceptance does not constrain key versions: they may go up, down or back to an earlier set of keys. Succession chains are followed from an entry's keys without its `keyVersion` as a floor, so a member's real keys written at an inflated version leave their later identities followable. Key versions do matter elsewhere: a seal or grant names its recipient's key version, and the sealer and opener require it to equal the entry's exactly, so an entry at an inflated version locks the member out of every new seal and grant to them until it is put right (their own client flags the entry as not theirs). Planted keys are covered in 2.8. The server refuses an entry, new or changed in a roster, whose keys are not an identity the member has had with its keys statement holding (`checkNextRoster` with the members' identities, 4); clients do not rely on that.

**Accepting rosters.** Every device verifies the roster chain from version 1, or continues from its own local cache (2.7), and never from synced state:

1. The server serves every roster from version 1 (or every one after the cache), and every succession (4).
2. **The person's marks first**, which need nothing from the server: their pins (2.7, the settings' and each device's) and this device's cache. Within one session (a worker, an app's ledger) the chain it already committed for the group is a mark too (review of the 1d core step, 2026-10-18): a served chain short of it is a lost race or a rollback and keeps nothing (`OLDER_CHAIN`, which the data layer reads again quietly), and one through another roster at its version is the hard warning, never committed (`SPLIT_CHAIN` is the ledger's backstop). Each fixes a roster digest at its version, and so, through the hash chain, every digest below it; group key marks fix the group key at a key version; and each fixes the version 1 keys the person checked (through a join code, or at creation). Marks that disagree with each other are the hard warning (below), whatever the server serves, even junk. The served version 1 keys must then be the ones the marks agree on, or are refused as not the checked ones; with no mark at all, they are taken only as below.
3. **The chain** is the one ending at the latest roster served, linked back by `previousRosterDigest` to version 1 (or to the cache's last roster). Two rosters at the latest version are refused (the server's to resolve); a link that does not reach version 1 is refused; rosters after the cache that do not continue its last roster are refused, and the device fetches the chain again from version 1, where the cache is one more mark. Any other roster served is a **dead branch**: it is ignored for acceptance and listed as a soft note with its version and claimed signer, unverified and never named as a culprit.
4. **Verify.** One pass along the chain: each roster must hold under the group key current at its version (2.5), be signed by a member active with `members` on the roster before it (version 1: on itself, the creator), carry one copy with both a valid group signature and the signer's identity signature, keep the entry rules, and come after the succession a dropped `members` holder made due. Each succession is taken as soon as the roster it is tied to is held, so the rosters after it are judged under the new key. Anything that fails is refused before the marks are compared with the chain, so a server cannot raise the warning with statements nobody signed, nor with version 1 keys it made up.
5. **The marks against the verified chain:** a mark the chain does not pass through is the hard warning; a chain short of a mark (a lower head, or fewer group keys) is a rollback, refused.
6. Anything that fails leaves member records at their personal-check verdicts, never better.

**With no marks at all** (a device with no pin and no cache), nothing is accepted on faith: the caller must say explicitly (`firstKeysChecked`) that the version 1 keys are known good, and exactly two places may say it (milestone 1c):

- **The join flow** (3.2), only together with a join mark (below): the person compared the join code their device worked out over the served chain with the one the admitting admin's screen shows, and acceptance carries that code as a mark, so the verified chain must pass through the admin's roster. Made-up version 1 keys then give a fork or a refusal (fixtures `join-mark-made-up-first-keys`, `join-mark-made-up-first-keys-succession`). The worker refuses `joining` without a mark. The code itself comes from a preview (`groupJoinPreview`): the served chain verified as acceptance would (against the marks if there are any, else over the served version 1 keys), and the code of the roster at which this account's entry last became active returned; nothing is committed, kept, marked or set as a fork, so a code nobody compared vouches for nothing.
- **Creation** (3.1), inside the crypto worker, over keys it just made: the creating device generated the group seed itself, so it knows the version 1 keys without asking anyone. It sets `firstKeysChecked` only while it still holds the seed of this creation (in its staged secrets, or the sealed outbox entry of the creating call), and only for served first keys equal to that seed's public key: once to accept its own unsent roster version 1 as a staged chain (below), and once more to accept what the server serves after the call succeeds, the acceptance that writes the device's first cache and pin. After that the group needs the flag no more on that device, and the creator's other devices start from the synced pin. **The creating call's outbox entry, and the seed in it, are deleted only after that first committed acceptance has written the device's cache and pin** (and the settings pin is saved): "committed but not yet pinned" is a state the sealed outbox keeps across a reload, and the next open finishes it (re-sync from what the server serves, `firstKeysChecked` against the held seed, write the cache and pins, then delete the entry). The outbox tests of the web data layer (milestone 1c) must cover a reload in that state. Creation never sets the flag over keys it did not make: a device without the seed, and without a pin, is a newcomer and needs the join code check. A creator who loses the device between the server's answer and the first pin write has no mark anywhere; in a family with no other member nobody can compare a join code with them, which is a denial (the group cannot be verified), never a forgery.

Anything else is refused.

**Identical statements served twice.** The same statement bytes may come with different signatures (a client that retried, hedged signatures differing): either copy that verifies will do. Only when no copy verifies is the statement refused.

**Checking the next roster and succession.** `checkNextRoster` (Rust `roster_check_next`) and `checkNextSuccession` (Rust `group_succession_check_next`) are acceptance itself, continuing from a chain's cache with that one statement, so they refuse exactly what every device would. In TypeScript they take a reader's accepted chain or the server's stored one and return the chain extended by it as a **stored chain** (`StoredChain`, frozen and registered in its own registry, not the accepted one); the Rust ones return nothing, since no app is the server. A stored chain carries no cache: its record to continue from is a `StoredChainCache` (`origin: 'server'`) that only the server entry hands out (`storedRecord`), and a reader's acceptance refuses it as a cache, by type and at run time (`checkCache`), as the server's acceptance refuses a device's. The server's own acceptance of what it stores is `acceptStoredChain`, exported only from the server entry `@hushos/crypto/group-trust/server` (it refuses to load where `document` or a worker scope exists, and the web app's test `server-imports.test.ts` fails if any non-server module in `apps/web/src` imports it; workspace packages the web bundles are not scanned, so the load guard is the real control): its anchor is the version 1 keys it stored at creation, with no reader, no pins and no words check, so it is never a reader's acceptance. A stored chain is taken only by `checkNextRoster`, `checkNextSuccession` and `acceptStoredChain`; every seal, opening, write version, row, pin and trust function refuses it, as a type error and at run time (`This is not a member list this device accepted.`), so nothing the server accepted can vouch for a key on a reader's behalf. `nextRoster` applies the same rules before a holder signs, and clients run `checkNextSuccession` before signing a succession. The server must run both before storing (4): a stored roster that fails stops every device's sync, since every later roster chains to it, and a stored succession no device takes (one tied before the latest roster under its old key, for instance) stops the group at its next roster.

**The hard warning** ("Acme's member list was shown differently to you") appears only when the person's own marks conflict: two pins with different roster digests at one version, or different group key digests at one key version; a pin and the cache that disagree; two marks naming other version 1 keys (`of: 'group-key'` at version 1, each side's digest then being the SHA-256 of the Ed25519 key and the ML-DSA key's digest, as a pin keeps them); or the verified chain not passing through a mark (another roster at a marked version, another group key at a marked key version). Served version 1 keys other than the marks' are a refusal, not the warning: a server can make up a group key and sign anything under it. A group key mark that the valid successions served do not meet waits while the one it names may still be tied to a roster not reached yet. It is the warning only if a roster needing the next key holds under one of the others, signed by a `members` holder: a real other history the mark contradicts. A roster under the marked (withheld) key while only the others are served is refused as a missing succession, and a mark still unmet once the chain is verified is a rollback, refused: a server withholding the real succession gets a refusal, never the warning. A succession whose new key is the key it replaces, or any earlier group key, is refused. The warning lists both sides, each with its digest, where it came from (pin, cache or served) and, only when that side's statement was verified (in the pass, or by this device before, for the cache), its signer: a conflict among the marks alone names only the cache's; it never names one side as the culprit, since either may be the one the person was shown elsewhere. A fork is never resolved by taking the higher version. The marks are compared with each other before anything served is parsed, so junk the server adds (bytes that are not a roster, a roster of another group) can refuse acceptance but never hide the warning the person's own marks raise.

**The join mark** (milestone 1c: `AcceptInput.joinMark`, `accept_rosters_joining`). The join flow anchors a newcomer on a **join code** for the roster that admitted them (the roster at which their entry last became active): its version and twelve words, the first 160 bits of SHA-256("hushos/group/join-code/v1" ‖ rosterDigest ‖ groupKeyDigest ‖ u64be(groupKeyVersion)) read as the fingerprint words are (the top 132 bits, twelve 11-bit BIP-39 words; `joinCode`, Rust `join_code`). rosterDigest is the 32 bytes its base64url names; groupKeyDigest is exactly `groupKeyDigest` of the group key that roster is under (SHA-256 of its Ed25519 key followed by its whole ML-DSA key), never a pin's first-keys digest (an admin client using that form at key version 1 would raise false forks). Acceptance holds it as one of the person's marks: the verified chain must pass through a roster at that version whose code it is, or it is the hard warning (`of: 'roster'` at that version, a side `from: ['join']`); a chain short of it is a rollback, refused; a mark that is not twelve lowercase words is refused outright (`Invalid join mark.`), not ignored. Acceptance works the code out again from the chain it verified (the roster digest at that version, the group key that roster is under, and its key version), never from a pin, so the code alone pins the version 1 keys: under key 1 a made-up key is the code's key and gives the warning, and after a succession a made-up key reaches the code's key only through a succession a holder signed (the residual below). The family's version 1 words add nothing once the code is checked, and the flow no longer compares them.

What it covers, honestly: a newcomer admitted on the real chain whom the server would start on any other history (a removed holder's branch, or a concurrent upload's loser when the admitting roster is the one the server stored: if the server lies to the admin about a 409 and keeps the admitting roster as the loser, the code binds the newcomer to that branch, and admin and newcomer sit on it together, the fork-consistency residual). Matching the code with another roster is a second preimage on 132 bits, out of reach, so the digest alone holds; the group key is defence in depth, and it adds something only because of the flow rule above (no admission on a holder's removal): the admitting roster is then under a group key no holder removed before it ever held. It does not cover a newcomer whom a holder admitted before that holder's removal (that roster is real on both histories), or an admitting admin whose device is compromised. A divergence after the join is covered by the newcomer's own marks only once they hold one past the admitting roster: a removal right after the join (admit at r_k, remove the admitting holder at r_k+1) that the server withholds from the newcomer before then is the withheld-removal residual, for the newcomer as for everyone.

The flow (3.2): once the admin has checked the newcomer's words, the admin's client signs the admitting roster and uploads it in one step; a retry resends the same signed bytes (the concurrent-uploads rule below). If the upload meets 409 `stale` (another roster stored at that version), the client discards the unsent roster and signs a new one over the new head. Only once admit has succeeded is a code shown: the admin's from its committed chain after re-syncing (the stored roster, never the staged one), the newcomer's over the chain route 5 serves. The newcomer's client takes the code as its mark only when the person has checked ten words and typed the two its screen hid as the admin read them, and only while what is served still gives that code; otherwise it keeps nothing. Residual of comparing after the upload: a code that does not match leaves the newcomer admitted on the server (a seat taken, the areas' keys granted to the keys the admin checked) while their device trusts nothing of the family; sorting it out may mean removing them. Residual of dropping the words: a server working with a holder who signs a succession from a made-up key 1 can serve a made-up history below a join roster that comes after that succession and still meets the code (`join-mark-made-up-first-keys-succession` refuses it without the holder's signature); the roster statements are the real ones, only the version 1 keys and the successions before the join differ, and with the version 1 words no longer compared nothing in the flow shows the newcomer that their pin names made-up first keys. Such a holder can already sign any roster.

**Staged chains** (milestone 1c). A seal or grant names the sealer's latest accepted roster (2.3, 2.6), and a roster call carries the seals and grants that the roster makes due, naming that very roster (the server checks them against the roster in the same call). So a client building such a call first accepts its own signed, unsent roster on top of its **committed chain** (the one it accepted from what the server served): a **staged chain**, which it uses only to seal and grant for that call (and, for a removal's rotations, to judge writers as the roster marking someone `left` does). Roster version 1 at creation is staged the same way (`firstKeysChecked`, above). A staged chain **never becomes a mark**: it is never written as the device's cache or pin, never synced, and never passed to acceptance as a mark. Only once the server confirms the call (201 or 200, or a resend answered as a replay) does the client re-sync from what the server serves, and only that committed acceptance writes the cache and the pin; on 409 `stale` (or any other refusal) the staged chain is discarded with its roster and secrets. A **refusal** is a definite answer: a 4xx carrying a code. An unknown outcome (a 5xx, a timeout, a dropped connection) is not one: the client keeps the outbox entry, the staged chain's secrets and the signed bytes, and resends them unchanged; the server answers a resend of a call it already stored as a replay, which commits it. Were a staged roster kept as a mark, a device that lost a `stale` race would hold a mark on a history the server never stored, and its next sync would raise the hard warning against itself. The staged roster's signed bytes, and the keys its seals and grants carry, are what a retry resends unchanged (below). Residual: a lost admit race leaves what was already uploaded for that admission (seeds and grants sealed to the newcomer, whose keys are the group's and the areas' current ones) on the server until the next rotation replaces those keys. The 1b server stores a roster call in one transaction, so nothing of the refused call itself; seals and grants naming a roster no chain holds never open (`sealedOnChain`), so the newcomer reads nothing through them, but the keys they carry stay current until then.

**Concurrent uploads make second histories.** Two holders signing roster `n` at once (or a client retrying after the member list changed) each produce a valid next roster; the server stores one and has seen the other. It can later serve the loser as the latest roster to newcomers and to devices with no mark at `n` or above, who accept it (a removed holder may still be active there, with no succession due), and showing it to a device with a mark from the stored one raises the warning with nobody's help but the server's. The same holds for two successions from one key. The client rule for milestone 1c: a retry resends exactly the signed bytes it already uploaded, never a re-signed statement, and the join mark above covers newcomers.

What this does and does not stop:

- **A removed holder** keeps the group key versions they held and can still sign statements under them, on a branch of their own from the last roster they held `members` on. Served beside the chain, that branch is a dead branch: ignored, a soft note at most, never a warning. Served as the chain itself (the server colluding), it is accepted only by a device with no mark beyond the branch point, which takes it as the history; a device with any mark above it raises the warning (the branch does not pass through the mark) or refuses it (shorter than the mark). A device verifying the real chain never accepts a roster under a key a succession replaced.
- **The server** can withhold the latest rosters (a device then sees an older chain, refused once it has a mark above it), serve two latest rosters or two valid successions from one key (refused: a stall), or serve a different chain to a device with no marks at all (which is why a newcomer's join code check is required). Where holders signed two histories (a removed holder's branch, say), it can split different people across them for good: this is fork consistency, not more. Only a person's own devices, through their marks, detect that they were shown two histories; nothing tells two people apart. It cannot make a device with a mark accept a chain off that mark without the warning, cannot raise the warning without statements a holder signed (served version 1 keys it made up are refused against the person's marks before anything is verified), and cannot forge a roster or succession.
- **A sole `members` holder** who starts over without a succession link can never sign again: no entry names keys they hold. Another `members` holder can fold their new identity in from a words check; a group with no other `members` holder cannot recover its roster.

### 2.5 Group key succession

A succession replaces the group key and is tied to a place in the roster chain:

```
["hushos/group/key-succession",1,groupId,oldVersion,newVersion,oldEd25519PublicKey,oldMlDsaPublicKey,newEd25519PublicKey,newMlDsaPublicKey,lastRosterVersion,lastRosterDigest,signerUserId]
```

- `newVersion` is `oldVersion` + 1, and the statement carries a group signature by the old key and the signer's identity signature; the signer is active with `members` on the roster at `lastRosterVersion`.
- Rosters signed by key `v` must have versions after the `lastRosterVersion` of the succession into `v`, and up to the `lastRosterVersion` of the succession out of `v`. A roster under a key that a later succession has already left behind is refused.
- **A holder leaving or removed** is the last roster under that key: the roster that marks a `members` holder `left` makes a succession due, and no further roster is accepted until it exists. The new seed is sealed to every remaining holder; a succession that drops a holder who was not removed raises a warning.
- Successions are tied in order: each `lastRosterVersion` no lower than the one before.
- A succession **holds** when it names the chain's key at `oldVersion`, one copy carries the old key's group signature and the signer's identity signature, the signer is active with `members` on the roster it names by version and digest (a roster on the chain), and it is tied no earlier than the succession into it. One that does not hold is ignored. A succession is taken as soon as the roster it is tied to is reached, so one tied before the last roster already signed under the old key leaves that roster under a replaced key, and it is refused. A former holder who kept an old key cannot make one that holds: the signer must hold `members` on the roster the succession is tied to.
- **Two successions from one `oldVersion` that both hold at the same roster** are refused, unless one of the person's group key marks (2.7) names one of them, which is then taken; a mark that none of them meets waits, and is the warning only if a holder-signed roster holds under another (2.4). Two tied to different rosters are not "both valid" at once: the earlier-tied one is taken when its roster is reached, and if the other was the real one the chain then stalls (a roster refused as under a replaced key). That is a denial the server can cause with a holder's second signed succession, never a forgery.
- A succession's new key must be new: not the key it replaces, nor any key the group had before (k1 → k2 → k1 is refused).
- A succession tied too early (before the last roster already under the old key) is taken too early, so that roster is refused and the group stalls. Clients run `checkNextSuccession` before signing one, and the server must run it against the stored chain before storing one (4).
- The server stores one succession per `oldVersion` and refuses a second. It has still seen the refused one, signed, and can serve it later (see the second-history residual in 2.4).

### 2.6 Area grants

**Area keys are on the roster.** Every area's current key is listed on the roster with its commitment:

```
commitment = HKDF-SHA-256(ikm = workspaceKey, salt = 32 zero bytes, info = "hushos/group/area-key/v2", length = 32), base64url
```

It depends on the key alone (round 12; round 9's v1 folded in the workspace id and version) and reveals nothing of the key but whether two keys are equal. Its area and version are where the roster lists it: a grant opens only to the key whose commitment the chain lists at the grant's area and version, as the group key's own publication binds key seals (2.3), and acceptance refuses any commitment the chain listed before (2.4). So a new area, or a rotation, is a roster first, signed by an active `members` holder (`nextRoster` with the new key, which computes the row), and only then are its grants made. **This is a product rule change:** until now any member holding an area's key could rotate it; now only `members` holders create or rotate areas. The rotation itself (the new node key on the area root, the version bump) is still the rotating client's work.

Why: a holder whose device the server keeps behind (a withheld removal, no branch roster needed) would otherwise make a new area or a rotation on its own view, where the removed holder is still active, and grant the new key to everyone there, naming its latest roster, which is on every real-chain device's chain too. Real-chain members would open it and upload under a key the removed holder holds. With commitments on the roster that grant opens nothing on the real chain: the version is not listed there, or is listed with another key's commitment.

**Rows are deltas.** A roster carries a row only for an area it creates or rotates (at most 1,024, 2.4), so its size depends on what it changes, never on how many areas the group has. Every version is listed once, on the roster that introduced it: the area rules (2.4) make each area step 1, 2, … with one commitment per version, and every device verifies the chain from version 1 (or its cache, which keeps them), so the accepted chain holds every commitment (`AcceptedRosters.areaKeys`). A grant of an earlier version, a key a reader needs for older files, opens against the commitment the roster that introduced it listed; a grant of a version the chain does not list, or of a key no roster committed to, opens nothing. The server (milestone 1b) refuses a roster row creating an area whose workspace is not a group workspace it has for that group.

**Writing.** A member writes an area only under its latest version on the accepted chain (`areaWriteVersion`, Rust `area_write_version`: the number of commitments the chain has for it). A client holding no grant for that version writes nothing there until it has one: the server reporting the area at an older version is no protection against the server, which could otherwise keep a member writing under a key a removed member holds (a withheld rotation). The client rule is milestone 1c's; the core gives the version now.

An area's workspace key is granted with the suite 4 construction, under HKDF `info` `hushos/group/area-grant/v1` and AEAD associated data equal to the statement without its digest:

```
["hushos/group/area-grant",1,groupId,workspaceId,workspaceKeyVersion,granteeUserId,granteeKeyVersion,granterUserId,rosterVersion,rosterDigest,sha256(sealed)]
```

`rosterVersion` and `rosterDigest` are the granter's latest accepted roster, as for a key seal (2.3). A granter grants only a key its latest roster lists, for that area and version (an earlier version by the chain's commitment). A grantee opens a grant only if: the roster it names is on the grantee's own accepted chain (so a lagging holder's grant of a removed holder's branch key never reaches the real chain); the chain lists the area at that version, and the key opened has the commitment the chain listed for that version (so a granter kept behind cannot hand on a key the real chain never listed, and a key made under a retired identity of the granter's opens only to the key the roster committed); the granter is `active` (not `left`) on this group's verified roster; `groupId` is that roster's group and the area belongs to it, meaning its workspace id is derived under the group (the `workspace` id kind, scoped to the group id, checked from the area's id seed); only such areas enter the pin's `areas`; and the grantee and key version are the reader's own. There is no floor on `workspaceKeyVersion` (round 10 dropped the high-water check in both twins): an earlier version's grant opens after a later one has, since readers need earlier keys for older files, and a key a removed member holds is kept from new writes by `areaWriteVersion` and the removal's rotation, not by refusing old grants.

**Rotating an area** is a roster listing the next version's commitment, signed by a `members` holder, and then the rotation: it bumps `workspace_key_version`; the area root is the root of a `drive_rotations` run and gets a new node key in the same request that bumps the version, so a cached root key opens nothing new. In format 2 (2.10) the roster also commits to that new root key, and readers take the root as current only by that commitment. New grants go to active members only.

### 2.7 Pins and rollback

The settings document gains, per group:

```
groups: { [groupId]: { firstEd25519PublicKey, firstMlDsaPublicKeyDigest, checkedAt, keyVersion, groupKeyDigest, rosterVersion, rosterDigest, areas: { [workspaceId]: highestKeyVersion } } }
```

`checkedAt` is the 24 ASCII characters of an ISO 8601 UTC time to the millisecond (`YYYY-MM-DDTHH:MM:SS.sssZ`, as `toISOString` writes it); anything else is no pin, so every client orders check times alike, byte by byte. `firstMlDsaPublicKeyDigest` is SHA-256 of the version 1 ML-DSA key, which the client compares with `firstKeys` as served; the settings document has no room for the key itself (`docs/envelope-migrations.md` 2). `rosterVersion` and `rosterDigest` are the latest roster this person's devices accepted, and `keyVersion` and `groupKeyDigest` (SHA-256 of the group key there, Ed25519 then ML-DSA) the group key at that point. The pin is never a starting point. Its only jobs are rollback (a served chain shorter than the pinned roster, or without the pinned group key, is refused) and split-view detection across devices: it is one of the person's marks (2.4), so another roster at the pinned version, another group key at the pinned key version, or two pins that disagree raise the hard warning. Each device also keeps its own pin. Both are passed to acceptance; the pin written afterwards is the chain's latest roster and group key, with the areas the group's grants tied and the earliest check (`checkedAt`). The areas' keys scope roster trust (2.8); the version each carries is kept for the pin's form and is no longer a floor anywhere (2.6). A lower pin needs no keeping once the chain has been seen to pass through it, so nothing like an earlier-marks list is stored. The `groups` field makes the document version 2, which older clients refuse rather than save over (`docs/envelope-migrations.md` 2).

**The local cache.** A device may keep, locally and never synced, what it verified (`GroupChainCache`): every roster's digest, the last roster's statement and whether it dropped a holder, every group key and every succession's tie, digest and signer, the creator, every set of keys each member's entries named (X25519, Ed25519 and the ML-DSA digest), every commitment each area has had (`areaKeys`), and the versions where the reader's own entry was wrong. On input the last roster's rows must be their areas' latest commitments, and at roster 1 its rows must be every area there is; earlier commitments are this device's own record and are trusted as stored (a compromised device is out of scope), as the rest of the cache is. It is bound to its group and to the roster it is through (the last digest is the statement's, whose version is the digest count), and every part is checked for form on input; one that fails is refused. With it, the next sync asks for the rosters after it (`?after=`, 4) and continues from it exactly as verifying from version 1 would have. A record whose cache the worker refuses even over the chain from version 1 (one a newer release wrote, or a damaged one) would refuse the family on that device for good, so the data layer then accepts from version 1 with the record's cache left out but its device pin kept as a mark (`groupAccept`'s `withoutCache`, `acceptServed`). The pin is what keeps this from being a rollback: the settings document a server serves can be an older one, so a third attempt against the settings pin alone would let a server get the cache refused, serve a chain cut before a removal with the settings from before it, and have the device take the removed member back. The server chooses when this path runs: any chain it serves that the worker refuses twice, junk included, sends the device down it, so it is no evidence that the cache was at fault. What bounds it is the record's pin: the chain may never end below the record's version or leave its digest, whatever the server serves. The record is replaced only by that acceptance, and a chain refused on its own merits leaves it in place. The cache is one of the person's marks: every roster digest and group key it holds is fixed, so a served chain that does not pass through its last roster, or a pin it disagrees with, raises the hard warning, and successions served beside the ones it verified are ignored.

**Key history.** Every set of keys each member's entries named, in order, is part of what the device verified (and of its cache). It is not trusted on its own: an entry's keys are a holder's claim (2.4). Its first set per member, the one a words check admitted, is the only earlier set a reader relying on the roster (2.8) or a seal's opener (2.4) starts the member's succession chain from.

### 2.8 What readers show

Roster trust is scoped to its group: **a roster vouches only for records in that group's areas and for grants naming that group.** Elsewhere, such as a colleague's personal share, a colleague who is not personally checked shows as Unverified with the hint "In Acme". One click, "Trust as Acme does", writes a version 3 personal pin from the roster's entry (its X25519 and Ed25519 keys and its ML-DSA and ML-KEM digests) and the served keys that match them, as an explicit act by the reader. The pin is only as good as the chain the reader accepted: a newcomer the server keeps on a removed holder's branch, where that holder planted their own keys as member X, writes a personal pin of the planted keys, and it outlives the branch, reaching X's personal shares to the reader (the join code, 2.4, covers a newcomer on such a branch once 1c ships it; until then the button should not be offered to a member admitted in the last few rosters without a second words check). The pin records where it came from: `trustAsGroupDoes` writes `trustedVia: groupId` on it (Rust `VerifiedPin.trusted_via`), a new words check over the keys clears it, and `newRosterEntry` refuses such a pin (a member is admitted only from their own words check). Inside the group, links from a pin trusted through a group need the successor's consent up to the entry (below), so planted keys pinned that way give no bridge once the entry is put right. Every shipped client keeps pin fields it does not know when it rewrites a pin (the web spreads the old pin, iOS writes known fields over the raw dictionary, Android edits the JSON in place, and none rejects an unknown field), so the field needs no pin version; an older client's own words check keeps it, which only asks consent where none was needed.

**Rotations never claim authorship here.** A rotation keeps each record's origin and the writer's signature and signs only the binding (docs/integrity-design.md, "Re-keyed records"), so a removal's rotation leaves the removed member's files reading `former-member` by them, never "re-locked by" the admin who rotated. Once the server stores origins, it accepts in a group's area only a rekeyed record or a legacy `resealed` one, never `ordinary` or `saved`, and the re-keyer's own signature is judged with the group's trust too. A verified re-keyer appears in Info only; a missing or bad re-key signature, or a re-keyer in key conflict, is an Unverified mark (the re-key isn't attested), never a mismatch. The record is the re-keyer's fault (`bound: false`) only when the bytes differ, or when the wrap or origin fails under their verified signature; anything a server alone could cause reads couldn't-confirm.

A former member still holds their keys, and a signature carries no trustworthy date, so their work is marked: it may be old and genuine, or planted. That holds even for a reader who pinned them personally: inside the group's areas, leaving is what matters.

**Retired keys and what did not load.** A member's earlier keys read as retired only along a succession chain the reader verified to the member's served identity, and only the links the verifier itself followed count (never another link served beside them):

- a reader with a personal pin of the member retires keys along the chain from that pin and, when the pin is at a later identity of the member, the keys before the pin on the member's verified chain from the entry's keys or their first keys up to the pinned keys (they were the member's before the identity the reader pinned); never from a set a holder wrote into an entry later. When the pin was trusted through a group (`trustedVia`, carried on the pin group verdicts take: `WriterPin`, its keys and origin together, so a caller cannot drop the origin; an empty one reads unchecked), the walk from it asks the successor's consent up to the entry, as the walk from the first keys does, wherever its keys sit in the member's history (a planted first entry included): a planter's one-sided link from his planted keys to the member's real ones then bridges nothing, and the pinned reader sees `key-conflict`, never the planted keys retired. A pin from the reader's own words check takes the version 2 signature, so an honest member's later one-sided rotation, folded in, is no conflict for them (round 10 keyed this on the pin's place in the history instead, which raised false conflicts for honest members and missed planted first entries);
- a reader relying on the roster retires them along the chain from the entry's keys (when no roster has folded in the change yet), and along the chain from the member's first set of keys on the chain, the one a words check admitted (2.7), up to the entry's keys and never past them (past the entry, a chain is no evidence the first keys were the member's: a planter consents to his own successor); never from a set a holder wrote into an entry later.

The group core does not use the personal-pin verifier (`verifySuccessionChain`, which takes the list in the order served), and that verifier never reads the group walk's verification cache. The group walk verifies each served link once per proof and follows the verified links as a graph from the start keys (`succession-path.ts`, `succession_path.rs`). The proof depends on where the walk starts: from the member's first keys, each link up to the entry's keys must carry the successor's consent (2.8 below, `docs/identity-pq-design.md` 2), and after them its version 2 signature suffices; from the entry's keys (the roster lag), from a reader's personal pin and in `foldInEntry`, the version 2 signature under the old keys the link names suffices, as for personal pins. A consented link's version 2 signature is never checked. Only links that could join the member's chain count toward the cap: those whose old keys are the walk's start, a key set the chain lists for the member, or a link the walk already followed; more than 64 of them are checked no further (`too-many`). Links with any other old keys are never verified and never counted. The member's own keys are public, so a server can always serve 65 junk links from them; on the lag and pin walks `too-many` therefore reads as links that did not load, never as a fork: the entry's key stays current, nothing is retired, and a signature under an unknown key reads `unchecked`. So junk from keys the member never held suppresses nothing, and junk from their own keys costs retirement and the verdict on keys only their chain would vouch for, never the verdict on records under the entry's key. The cache of verifications is keyed by the SHA-256 of the member, the proof and the link's fields, named one by one (no serialization hook or field order can make two links share an entry), holds at most 4,096 results (the least recently used dropped first), and is locked only to look up or store, never while a link is verified; callers may pass one per session (`groupWriterTrust`'s `verified`, Rust `SuccessionCache`) so each record read does not verify the same links again. junk served before, between or after the member's own links, links out of order and duplicates change no verdict. Otherwise the walk keeps the strict verifier's rules: it starts only at a link naming the start's X25519 and Ed25519 keys and its ML-DSA key by digest, versions only rise along it, and it ends only at all four served keys. The served identity's key version is not signed, so the walk never reads it, and neither does the conflict decision below. A verified link leaving the served keys means the server serves an identity the member has already replaced (a rollback): the walk says `stale`, and the record reads `unchecked`, neither verified under the stale key nor bad under the newer one. `stale` fires only when the walk passes through the served identity (its start included: the server serving the entry's keys while a link the member signed leaves them); a link leaving the served keys that the walk never reaches changes nothing. A personal pin older than the member's first keys on the chain retires keys from the pin on. The work is one verification per link and one step per link.

**Identity forks.** Two verified links leaving one of the member's key sets for different keys mean two successors the member signed from one identity, and nothing tells which is theirs now. On the walk from the entry's keys or from a personal pin, their records in the group's areas then read `unchecked`, whatever order the links were served in and whether or not the reader pinned them, and their seals open only under their entry's own keys. How it happens: two of the member's devices succeed at once, or a device retries a succession with freshly made keys. The server stores one link per old key (the second gets `stale`), but it has seen the second, signed, and a server that serves both later forks the member on purpose. That costs verdicts (a denial), never a forgery. Making `createSuccessor` reuse a pending successor on retry is out of scope for milestone 1a. A fork (or a rollback) on the walk from the first keys voids only that walk's retirement and never the member's verdicts: whoever holds the first keys (a holder who planted them, or provisioned the member's first device) can mint two consented links leaving them, and would otherwise turn every record of the member, forgeries included, to `unchecked`. A genuine fork before the entry then costs only the retirement of the keys before it, which read bad-signature, the conservative outcome.

**Planted keys.** A malicious `members` holder who writes keys they hold into a member's entry vouches for them while that entry is the latest (the existing insider power to swap a member's keys). Once the entry is put right, the planted keys read as nothing: a link the planter signs from them to the member's real keys starts no chain, since chains start only from the member's first keys, so no record under them reads as retired and no seal signed with them opens (2.4).

**Successor consent, only where it buys something.** From a member's first keys up to their entry's, the walk follows a link only when the new keys it names co-signed it. Without that, keys planted as a member's _first_ entry (where every chain starts) could bridge to the member's real identity: the planter signs a link from the planted keys, the walk crosses it, and records and grants under the planted keys read as the member's (retired-key, or a grant that opens). The planter holds the planted keys but not the member's, so the consent half under the new keys is the one thing they cannot make; a link without it (one-sided, or with only the planter's half) is refused there, and a record under the planted keys reads bad-signature. A self-consented link from the planted keys to keys of the planter's own (both halves his) is a valid edge, but it never reaches the entry, and retirement from the first keys stops at the entry, so the planted keys still read bad-signature. Elsewhere consent buys nothing: a personal pin from the reader's own words check is the reader's own anchor (one trusted through a group is not, above), and the roster-lag walk and `foldInEntry` start at the entry's current keys, which a planter already vouches for (a stated residual) and from which he could consent to his own successor anyway. There the version 2 signature suffices, so every honest rotation a shipped client signed keeps its verdicts: verified on the lag, and no false key conflict for a pinned reader after a fold-in.

What it costs: the web uploads `consent` with every succession and backfills the account's earlier links (`docs/identity-pq-design.md` 2), but iOS and Android do not send it yet. For a link without consent (one a native app made, or one from a version 1 identity, which cannot carry it), a member whose entry has moved on from their first keys does not have those pre-entry keys retired, and seals they made under them do not open through history.

**Withholding links.** A server that serves a member's identity with their links withheld, or cut short, makes their genuine records under keys it hides read `bad-signature` in group areas (with no links served at all, `unchecked`), and a pinned reader's verdict `key-conflict`: `bad-signature` there can be server-triggered, which the readers' copy says ("couldn't verify this signature"). A writer statement that names its signing key (the planned writer upgrade, `docs/identity-pq-design.md` 7) would let an unknown key read `unchecked` instead.

**What that costs.** Only a member's first keys on the chain start a chain. A member who started over without a succession link (their entry rewritten from a new words check) leaves those first keys with no chain to their current identity, so records they signed and seals they made under any key but their current one (or a successor no roster has folded in yet) read as bad signatures or stop opening: everything from before the restart, and, once a later identity of theirs is folded in, what they signed with the restarted keys too. What they sign with their current keys is unaffected. Re-sealing what is still needed is the remedy; a version 3 identity succession that binds its predecessor would make the restart itself a link (future work). A signature none of the member's known keys holds is a bad signature when their served identity and succession links loaded, and `unchecked` when either did not, since the key it needs may be one their chain retired.

### 2.9 Guardian seals (child accounts)

**Not in milestone 1.** This section is the plan for child accounts, a later milestone. The code, fixtures and tests for guardian seals were removed from milestone 1 (2026-10-16); nothing below is built.

A child account's root is sealed to each guardian with the suite 4 construction, under HKDF `info` `hushos/account/guardian-seal/v1` and associated data equal to the statement without its digest:

```
["hushos/account/guardian-seal",1,groupId,childUserId,childRootVersion,guardianUserId,guardianKeyVersion,sealerUserId,sha256(sealed)]
```

- `groupId` is the family whose roster named the guardian; a seal made through one family's roster does not open as another's.
- The sealer is the child's own device. It seals only to entries with the `guardian` role, `active`, on a family roster it verified after the family was checked at sign-up (3.6), so neither the server nor a roster without that role picks a guardian.
- A guardian opens a seal only while active with the `guardian` role on a verified family roster, and only if the sealer is the child. The child's own status on the roster is not asked: a `members` holder marking the child left would otherwise lock the guardians out; release and conversion re-key the account instead.
- **Adding a guardian later** needs an explicit act on the child's device, which seals to the new guardian after verifying their roster entry.
- `childRootVersion` is the child account's root revision. **A guardian's identity succession** makes the child's device re-seal to the new key on its next sign-in, deleting the old seal.
- **A guardian removed** from the family, or from the `guardian` role, makes the child's device run a full re-key (3.6) on its next sign-in, since that guardian once held the root.
- **The record** shows each time a guardian's device fetches a seal. Guardian clients drop an opened child root when the session ends; a modified client could keep it, and the record cannot show that.

### 2.10 Roster format 2: area roots and retired areas

Roster format 2 does two things in one reviewed change (owner decision, 2026-10-17): every new area version also commits to the key of the area's **root** (closing F14), and an area can be **retired** by a tombstone row (closing F11, so a family folder can be deleted). Everything else in 2.4 to 2.6 holds as written; only the `areas` rows and the statement's version change.

```
["hushos/group/roster",2,groupId,kind,rosterVersion,previousRosterDigest,groupKeyVersion,signerUserId,members,areas]
members = as format 1
areas   = [[workspaceId,workspaceKeyVersion,"key",commitment,rootCommitment] | [workspaceId,workspaceKeyVersion,"retired"], ...]

rootCommitment = HKDF-SHA-256(ikm = rootNodeKey, salt = 32 zero bytes, info = "hushos/group/area-root/v1", length = 32), base64url
```

- **The statement's version is the format.** Format 1 is `["hushos/group/roster",1,…]` with three-field rows, exactly as shipped; format 2 is `["hushos/group/roster",2,…]` with tagged rows. The signatures cover the version, so a statement of one format never verifies as the other. Rows are still sorted by workspace id, one per area, at most 1,024 (`MAX_ROSTER_AREA_ROWS`, retirement rows included), and every field keeps the canonical encoding (2.1): the tag is the literal `"key"` or `"retired"`, a key row has exactly five fields and a retirement row exactly three.
- **The root commitment has its own label.** `hushos/group/area-root/v1` is not the area key's `hushos/group/area-key/v2`, so a root key and an area key never share a commitment even when their bytes are equal, and neither can be passed off as the other. Like the area key's, it is of the key alone and reveals only whether two root keys are equal. It is not in either twin's exports to apps: `nextRoster` and `firstRoster` compute it from the root key they are given, as they compute the area key's.
- **What it commits to.** `rootNodeKey` is the 32-byte node key of the area's root folder at that area version: the key the root's own key envelope (context `hushos/drive/node-key`, `parentKeyEpoch` = the area version) holds. A new area's row carries its root's first key; a rotation's row (route 24, or a family roster's rotations) carries the root's new key, the one sealed in the same call. The root's previous envelope (option A, `hushos/drive/previous-root-key`) holds an earlier root key and is never compared with the commitment.

**The format on a chain.** A chain may switch from format 1 to format 2 at any roster, version 1 included, and **never back**: a format 1 roster after a format 2 roster is refused by acceptance (`This member list is in an older format than the one before it.`), by `checkNextRoster`, and so by the server. `nextRoster` builds the chain's latest format unless asked for a higher one, and refuses a lower one; `firstRoster` builds the format it is asked for. Old format 1 chains verify unchanged in both twins, so a device that verified a format 1 chain and caches it continues from that cache into format 2.

**Root commitments.** The server also refuses (`invalid` (`area-commitment`)) any area key or root commitment another group's stored roster listed (`group_area_commitments`), so no family folder's key or top-folder key is ever another group's. Acceptance refuses a format 2 key row whose root commitment the chain listed before, in any area at any version, or twice in one roster, as it refuses a repeated area key commitment (one set lookup per row, `rootCommitments` beside `commitments`): a rotation that keeps the root's key would leave the removed member able to open the root, and the commitment makes that hollow rotation visible to every device. The accepted chain keeps every version's root commitment (`AcceptedRosters.areaRoots`, cached), `null` for a version a format 1 roster listed.

**Readers decide an area root is current from the commitment, not from "the envelope opens".** The crypto worker opens the root's own key envelope under the area key at the area's write version (`areaWriteVersion`), as before, and then asks `checkAreaRoot(chain, workspaceId, workspaceKeyVersion, rootKey)` (Rust `area_root_check`):

- the chain lists a root commitment for that version: the opened key must have it, or the root is not current. The worker then refuses to write in the area and reads the root as couldn't-check; a server that rolls the root back to an earlier key wrapped under the same area key version (one a revoked share recipient holds) is caught here, whatever the envelope opens to;
- the version was listed by a format 1 roster (`null`): the previous rule stands (the envelope opening under the write version), and F14's residual remains for that area until its next rotation lists a root commitment;
- the version is not listed, or the area is retired: refused.

A root commitment binds only the root's key: the node id, area and area version are bound by where the roster lists it and by the root envelope's own context.

**Writes need a path rooted at the committed root.** Option A's previous-root envelope keeps the root's previous key openable after a rotation, so a server colluding with a removed member could serve a folder's pre-rotation envelope, say no walk is running, and have devices write new children under a key the removed member holds. The worker therefore tracks, for every node key it holds in a group area, the area key version its path is rooted at (the root opened under that version, each child under its parent's current key); a key reached through any previous key (the previous-root envelope, a parent's previous key, a walk's old key) is rooted nowhere. A write in a group area (a new node, an upload or new version, a rename, a share or link, a move's re-wrap) needs a key rooted at the area's write version, so such keys, and keys cached under a root a rotation replaced, read but write nothing; a folder takes writes again once the walk re-keys it under the new root. The worker's refusal (`KEY_CHANGE_PENDING`) is a wait to the upload queue, as the server's 409 `rotating` is, so an upload into such a folder waits for the walk even when the server says no key change is running. A write in a folder this device last opened under an earlier area version than the committed one waits this way until the next listing roots it at the committed root; a folder never opened, a server whose area version is behind or ahead of the chain, or a top folder whose key doesn't match the root commitment answers "keys changed" (`KEYS_CHANGED`) instead. A server can flip a device between the two, serving a mismatching root and then the old one again, but that only denies writes: no key a removed member holds becomes writable. Reading old content through the previous root stays allowed. A walk is held to the same rule. Its fresh key is a write like any other: its parent must be re-keyed earlier in the same walk or rooted at the write version, and the fresh key is rooted where that parent is, so a server that leaves a folder out of the walk cannot have a device wrap a fresh key under the folder's old key, which the removed member may hold, and then write under it. A walk's pending key also takes nothing once the area's next roster has landed, since it is rooted at the version before. And a walk's re-wrap of a node already at the target carries only a key already rooted at the write version, under a parent that is too: a key reached through one the rotation replaces is refused (`NOT_CARRIED`), because a removed member and the server can plant a node at the target under a folder's old key, with a key of the member's choosing, and a re-wrap would carry it into the new tree, where every device then roots it by its envelope's path. An honest walk never needs to carry such a key: the target is above every epoch a node carries (`startRotation`), and while it runs the server refuses nodes made or moved under a folder the walk has not reached (`underUnrotatedParent`), so a node at the target always sits under a parent already re-keyed. Personal workspaces keep their previous rule.

**The root's key changes only with a roster.** For the commitment to describe the root, the root's node key in a group area may change only together with an area version on the roster. The server therefore refuses a Drive rotation started at a group area's root on the Drive routes (403 `forbidden`: "Replace this family folder's keys from the family page instead."), and refuses the root as an item of any Drive rotation batch (`forbidden`), even during the walk a roster rotation started there, since the batch's re-wrap check compares a node epoch with an area version and could not tell; a rotation started at a folder below the root is unaffected, and a roster rotation (route 24, or a family roster's) is the one way to re-key the root. Before format 2 a holder's Drive rotation of the root was allowed and looked like a roster rotation to every device's walk (`docs/groups-server.md` 8, "Walks no longer claim authorship"); that case is gone.

**Retired areas (tombstones).** A retirement row `[workspaceId, workspaceKeyVersion, "retired"]` stands at the area's next version (the latest version the chain lists, plus one) and carries no key. The rules (`checkAreas`, Rust `check_areas`):

- **Who writes one:** a roster is signed only by an active `members` holder (2.4), so only managers retire areas. The server adds that a retirement comes only through the delete route (4), exactly one row, for the area that route names, and the roster changes nothing else: no entry, succession, rotation, grant or seal (`invalid` (`area-delete`)).
- **It must retire something:** a retirement row for an area the chain has never listed, at a version other than latest + 1, or for an area already retired, is refused.
- **No revival:** after the tombstone, any row for that area is refused, at any version: no rotation, no new key, no second tombstone. Its workspace id stays spent for good.
- **No grants:** `sealAreaGrant` refuses every version of a retired area, and the server refuses grants naming it. Grants made before still open (`openAreaGrant` checks a key against the version the chain listed, which stays listed), since a reader may still hold files under it; nothing is ever served from it again (below).
- **No writes:** `areaWriteVersion` is `null` for a retired area, so no client writes there.
- **Removals skip it:** in a family, a roster that marks someone `left` must rotate every area the chain has **that is not retired** (an area this very roster retires counts as handled), and `areasToRotate` lists only those. Retiring and then removing leaks nothing new: the removed member already held the retired folder's keys (every member opens every family folder), and from the tombstone on nothing is written, granted or served under those keys by any honest device or the server, so skipping its rotation leaves them only what they had the moment it was deleted.
- **It does not count:** `MAX_FAMILY_AREAS` counts live areas (listed and not retired) after the roster's own rows, so a family at the cap that retires one can create one, and a removal still always fits one roster. The server's `GROUP_AREA_LIMIT` counts live areas the same way.

The cache keeps the retired areas (`retiredAreas`, sorted) beside `areaKeys` and `areaRoots`, and says its own format (`cacheVersion` 2, both twins). On input, the last roster's rows must agree with them as for key rows: a key row's commitment and root commitment (or `null` for a format 1 row) are its area's last, and a retirement row's area is retired one version above its last key. A version 2 cache must list every area's roots (an emptied list is refused, never read as uncommitted); a cache with no version was written before format 2, carries neither field, and reads as no root commitments and no retired areas, which is what it described. A reader asked about a version with no root entry at all refuses; only an explicit `null` reads as uncommitted.

**Deleting a family folder** (3.3, 4): a manager's client builds the next roster with the area's tombstone (`nextRoster(chain, members, { retireAreas: [workspaceId] })`), signs it and sends it on the delete route. The server stores the roster, marks the area deleted in the same transaction (`workspaces.deleted_at`) and from then serves it to nobody: it leaves `GET /api/drive/spaces`, every Drive route answers it as not found and the group routes refuse it (grants, self-grants, rotations, the root and its previous envelope), its grants and self-grants are no longer served, shares and links in it are revoked, and it stops counting toward `GROUP_AREA_LIMIT`. Its files are kept 30 days, exactly as Drive keeps a trashed node (`TRASH_RETENTION_DAYS`), and longer while any open or held report names the folder (the purge skips it, as the deletion outbox keeps a reported object), and then the worker's purge deletes its objects from storage and its rows (nodes, versions, grants, documents, rotations, the workspace row), releasing its storage. Until then its bytes still count toward the family's storage pool (`freeBytes`): they are still stored, and a folder deleted when full must not free room to fill another while they are. An upload still completing in it is released, not published, when the expiry job finishes it (`finishCompleting`). Within those 30 days nothing restores it: the tombstone is final on the chain, so a restore would need a new area. What the 30 days buys is only Drive's usual retention before anything is destroyed (and room for a read-only Trash listing later, since earlier grants still open to the keys the chain listed): nothing in this release reads a deleted folder within it, and the server cannot, since it holds no key; the dialog says the folder disappears for everyone now, that its files are deleted from the server, normally after 30 days, and their space freed when they are, that anyone who kept copies or keys keeps them, as after a removal (deleting destroys no key: members' devices and earlier grants still hold the folder's keys), and that the folder cannot be restored (3.3). It does not promise the files are gone at day 30: a report's hold keeps the folder past it (below), and a storage replica deletes its copy on its own later schedule. The family's Trash page does not list a deleted folder: it lists what each live folder's own trash holds, and a deleted folder is no folder any more.

**Compatibility.** Only the web verifies family rosters today (and the server, through the same TypeScript core); the iOS and Android apps have no families, call no group route and never parse a roster (they carry a contact pin's `trustedVia` and nothing else of groups), so no shipped app sees format 2. The Rust core reads and builds both formats now, so the phone apps' families (1d) start on format 2. The web writes format 2 from a family's first roster and on an existing family's next roster: every client that reads family rosters is the web this same server serves, so the release that writes format 2 is the release that reads it. A tab still running the previous release refuses a format 2 roster ("Invalid roster.") and treats the family as unchecked until it reloads, which the release notice (`release.ts`) offers; its device cache, if a newer tab already wrote one through a format 2 roster, is refused the same way and accepted again from version 1 after the reload. Families are on by default only since #46 (`GROUPS_ENABLED`), so few stored chains are format 1; they verify unchanged and switch to format 2 at their next roster, and format 1 stays verifiable for them, for development data and for caches written before this release. Area versions a format 1 roster listed keep the envelope rule (F14's residual) until their next rotation.

## 3. Flows

### 3.1 Creating a family

The organizer's client derives the group id, makes the group key, signs roster version 1 with only the organizer (roles `billing` and `members`; no `guardian` until child accounts exist (3.6), when granting it is a role change on a later roster), seals the seed to itself, and calls `POST /api/groups`. Creating the first shared area ("Family") is part of the same flow. The roster comes from `firstRoster` (Rust `roster_first`), which takes the creator's own entry (`ownRosterEntry`, Rust `roster_entry_own`: from the account's own current identity as its device opened it, whose keys statement must hold; an entry naming keys the creator does not sign with fails acceptance's signer check) and the first area's key, computes the area's row and refuses anything acceptance would refuse of a roster version 1, so a creator never signs one the group cannot take. The client accepts that roster as a staged chain (2.4) to seal the seed and grant the area against, with `firstKeysChecked` over the keys it just made (2.4, the only place besides the join flow that sets it), and holds the group as committed only from what the server serves once the call succeeds. Before it sends the call, `groupCreate` runs that staged acceptance with the account's own identities freshly fetched (`me.identities`), and refuses to POST unless it reports empty `ownEntryWrongAt` and `ownEntryBehindAt`: `ownRosterEntry` proves only that the entry and roster version 1's signer are the same identity, not that it is the account's newest (a device that missed its own succession would otherwise found the group on a replaced identity).

### 3.2 Joining (invitation, acceptance, admission)

1. A `members` holder invites an email address; the server mails a link with a one-time token in its fragment (`/join#invite=<token>`), hashed at rest as sign-up tokens are.
2. The invitee signs in or signs up, opens the invitation and accepts. Membership moves to `accepted`; nothing opens yet, and no seat is taken.
3. The newcomer reads their twelve words to the admitting admin, from their join screen, in person or on a call through another service, never in a message sent through HushOS. The admin compares them with the words over the keys the server serves for the newcomer and confirms, which writes the admin's version 3 contact pin of them, the one the roster entry is built from. There is no skip: "Let them in" stays disabled until then.
4. "Let them in": the admin's client signs the next roster with the newcomer added, locally, seals the shared areas' keys to the newcomer (and the group seed, if they get `members`) and calls admit with them, in one step. The admitting roster never removes a key holder (the core refuses it, 2.4): a removal goes first, with its succession. A retry resends the same bytes, never a re-signed roster; on 409 `stale` (another roster was stored at that version) the client discards the unsent roster and signs a new one over the new head. The server applies membership, roster, grants and the seat in one transaction.
5. Once admit has succeeded, both screens show the join code of the roster at which the newcomer's entry last became active (2.4): the admin's client works it out from its committed chain after re-syncing, so over the stored roster, and the newcomer's client over the chain route 5 serves, verified from version 1 with the succession chain (against their marks if they have any, a rejoin's settings pin; else over the served version 1 keys), keeping nothing (`groupJoinPreview`). The admin reads all twelve words; the newcomer's screen hides two, at positions the newcomer's device picks at random for that showing and never sends anywhere, and the newcomer checks the other ten and types the two. The page never says the newcomer was let in: when route 2 says so is the server's call, and comparing alone could be finished by someone who never waited for the admin, on a family the server made up the moment it said so. Typing two words only the admin's screen shows cannot: guessing them is 22 bits, at positions the server does not know. That bounds finishing alone; it is no bound on a server grinding a made-up family whose code matches the admin's in words a person who compares nothing would skip, where the ten compared words are the defence, as good as the comparing. The positions are the ones the newcomer's device issued for that showing (a caller cannot name others), and after a wrong word they stay the same for that code until the page is left.
6. "They match": the newcomer's client works the code out again over what route 5 serves now. Another code keeps nothing (below). Then the two typed words must be the code's at the hidden positions, or nothing is kept and the page says not to use the family yet. Only then does it record the code (in a sealed joins record, so a reload finishes the join) and accept the chain from version 1 with it as the join mark (`firstKeysChecked` when there is no other mark, 2.4); then it writes its cache and pins the group. Another code (the member list changed, or the server is showing something else) keeps nothing, and the new code is the one to compare. "They don't match" keeps nothing either, and says not to use the family until the two have sorted it out: HushOS may be showing the newcomer a different member list. This flow and creation (3.1, over keys the creating device made itself) are the only places that vouch for version 1 keys.

### 3.3 Leaving and removal

- **Leaving:** the member calls leave. Their membership becomes `left` at once and the server stops serving them the group's areas and grants. The next `members` holder to open the group signs a roster marking them `left` (the server reports it as due). In a family that roster carries the rotation of every area in the same statement (2.4; the core refuses it otherwise), and the holder's client uploads it with the rotations and the new keys' grants to every remaining member in one call.
- **Removal:** a `members` holder removes someone with the next roster in the same call, which in a family carries every area's rotation and the new grants as above. In a company the roster does not say who opens what, so the rotations of the areas the person could open stay queued, each listed on a roster first (2.6).
- **A `members` holder leaving or removed** also makes a group key succession due before the next roster (2.5). The roster that marks a holder `left` is signed by another holder who stays (the core refuses a signer who leaves on their own roster), and no roster may leave the group without an active `members` holder: the last holder hands `members` on first.
- **A family member who leaves keeps their files:** their personal space was always theirs. They lose the family folders, and their personal space moves from the family pool back to their own allowance (3.5); over it, uploads are refused until they make room or buy a plan, and nothing is deleted.
- **The organizer** must hand `members` and `billing` to another adult member before leaving. Dissolving a family deletes its shared areas 30 days later (below), with notice to every member (not built yet); personal spaces are untouched.
- **Dissolving and the purge (as built, 20 October 2026):** the last active member leaving (or deleting their account) dissolves the family: `groups.dissolved_at` is set and, in the same transaction, every family folder is retired as deleting one retires it (2.10: `deleted_at`, no rotation due, shares and links revoked). From that moment nothing reopens it: every chain write, leave, invitation and acceptance refuses it (`lockGroup`, `createInvitation`, `openInvitation` and `acceptUnder` all read `dissolved_at`), no space lists it and Drive serves its folders to nobody. The folders then go the way any deleted family folder goes: 30 days later Drive's purge job (`purgeDeletedAreas`) queues their objects on the deletion outbox and deletes each workspace row with its nodes, versions, origin drops, rotations, grants, self-grants, documents and storage row, skipping a folder an open or held report names until the report lets go. The worker's `groups.purge-dissolved` job does the rest: it retires the folders of a family dissolved without that (by a container of the previous release during a rollout) as of now, never as of its dissolve, and deletes the group row, with its memberships, rosters, successions, seals, invitations, departures, holds, chain cache and pool, once it was dissolved more than `DISSOLVED_FAMILY_RETENTION_DAYS` (30, the trash's period, long enough to look into a dissolve made by mistake) ago, none of its folders is left (so a report on one holds the family's records too) and, with billing on, none of its subscriptions can still become active (anything not ended, `canceled` or `incomplete_expired`; a plan set to cancel runs to its period's end, and its folders still go on time); with billing off, it never had a billing customer (one that did waits for a run with billing on). That last check is a statement of its own after the group's row is locked, since billing writes a subscription holding that row. Families dissolved before the release get 30 days from the upgrade: its migration retires their folders and sets `dissolved_at` to the upgrade time. A plan of a dissolved family that can still charge is set to end at its period's end by the worker's `billing.cancel-dissolved` job (`cancelDissolvedPlan`, queued by the leave route and by every `reconcileGroup`), never revoked or refunded: the payer keeps what they paid for, as when they cancel (3.5); the prorated refund of `docs/families-shared-pool.md` 5.1 is for a personal plan ended early, not this. Each plan is set under its change claim and read again first. One resumed in the portal is set to end again, every time (a resume is the payer's own click; nothing loops), and its payer is emailed the date once per plan per period, once the plan shows as ending (so a set whose answer was lost, or a mail that failed, is mailed by a later run). Only 403 `InactiveSubscription` is a refusal: recorded with the plan's state, logged at error level and listed for operators until the plan is set to end, and not asked again until the state changes. Every other error (409 `SubscriptionLocked` during a renewal, a token error, 402, 422, 429, 5xx, a timeout) is retried; the first failed run is recorded (`dissolve_failing_since`), and a plan no reconcile has seen ending a day later (at once within two days of its renewal) is listed for operators as failing, so a failure Polar always repeats is not retried unseen while the plan renews. `paused`, `unpaid` and `incomplete` count as able to charge: billing's full reconcile records every subscription Polar answers for with Polar's own status and `ended_at`, and ends only one Polar no longer has (404) or answers as `canceled` or `incomplete_expired` without an end, so the job and the purge see such a plan until Polar ends it (3.5, Polar's statuses). Polar sets only an active plan to end, so the job revokes such a plan (the family `revokeLapsed`: its ending first, a payment taken afterwards refunded whole; nothing paid for it is in force); a revoke Polar refuses is recorded with the plan's state and listed for operators as `dissolved-inactive` until it has ended, since the purge waits for the end. A scheduled change given up on (`reissue_gave_up_at`) is listed only while its plan is live. It keeps the family's billing records (`group_billing_customers`, `group_billing_subscriptions`, `personal_plan_endings` and refunds, by the group's id: those tables no longer have a foreign key to `groups`), reports and their snapshots, the deletion outbox's rows, and `group_area_commitments`, so no key the family used is ever another group's. `createGroup` refuses (`taken`) an id that any area commitment or billing record still names, so a resent creation call cannot make the same family again; one whose first roster listed no folder key and that never had a billing record leaves nothing naming its id, and only its creator could make a new, empty family under it (every family the clients make lists one). Each family's row is deleted under an advisory lock keyed by it, so two runs never work on the same family at once. A plan of a purged family that Polar bills again (reinstated or resumed) is revoked by the next `reconcileGroup` that finds no group row for `group:<id>`, and what it took after that plan had ended is refunded whole by the plan-ending job (docs/self-hosting.md, Dissolved families). The notice to members is not built.
- **Deleting a family folder** (2.10): a `members` holder chooses "Delete family folder" in the folder's row menu and confirms; their client signs the next roster with the folder's tombstone and sends it on the delete route. It is gone for everyone at once (no member's spaces list it, no Drive route serves it, shares and links in it are revoked, nothing more is granted or rotated there), its files are kept 30 days as the trash keeps things, then the worker purges them. A member whose client still has the folder open gets "not found" on their next request. A family folder cannot be deleted while someone who left is still to be marked left (409 `left-due`: that roster rotates every live folder, which the delete route does not carry), nor while a removal's succession is due.

### 3.4 Spaces

`GET /api/drive/spaces` lists the account's personal space and every group it is active in, each with the areas it can open and their grants. Clients switch between spaces (web: a switcher at the top of the sidebar and the space in the URL, `/app/s/<space>/…`; iOS: one Files location per space, each tied to its owner as the 13 October Files fix does; Android: one provider root per space). Leaving a space wipes its local state on every device.

#### Shares inside family folders (proposed, not in 1c)

The web hides Share and links in family folders in milestone 1c, and the server refuses them there (409 `family-sharing`). A Drive walk re-seals a node's shares and links under its new key only when the walker can tell that each was made by someone entitled to make it, to keys that person vouched for. In one's own Drive that is the owner's sealed sharing ledger; in a family folder the ledger is each member's own, so a manager's walk after a removal can re-seal only the shares the manager made, and every other member's share is closed silently. Re-sealing what the server lists instead would let the server add recipients.

The proposal: **share records signed at family level.** A member who shares a node in a family folder signs a share record (`["hushos/group/share",1,groupId,workspaceId,nodeId,granteeUserId,granteeKeyDigest,role,granterUserId,granterKeyVersion]`, hybrid, under their identity) and stores it beside the share. A walker re-seals a share only when its record verifies under a granter who is active on the member list the walk is judged by (the staged one for a removal's rotation), to the grantee keys the record names (checked against the served identity), and drops it otherwise; a link carries the same kind of record over its link id. Revoking deletes the record with the share, so a revoked share cannot come back through a walk. Open: whether a member without `members` may see others' records (they name outsiders), and records for shares made before the change (none exist: Share is hidden until this lands).

### 3.5 Storage and the payer

Rewritten on 20 October 2026 to match `docs/families-shared-pool.md` (decided 19 October), which has the detail: when someone is pooled, the lock order, admission, moves, and how a personal plan is ended and refunded. Where the two disagree, the addendum wins.

- **One pool per family.** A family plan's quota covers every member's own files (their personal space, My files) and every family folder. `poolUsage` (`packages/db/src/pool.ts`) is the one count: `freeBytes` for any workspace in the pool, `/api/auth/storage`, the family's billing summary and its downgrade and first-purchase guards all read it.
- **When a member's own files draw from it:** with Polar billing, while they are an active member of a family whose plan is live (until its period ends plus `BILLING_GRACE_DAYS`). Without billing nothing is pooled: members keep their own allowance and each family folder its own (addendum 8).
- **A renewing plan whose payer is no longer in the family (as built, 27 October 2026):** beside the dissolved family's rule, the same job (`billing.cancel-dissolved`, `cancelDissolvedPlan`, queued by every `reconcileGroup` and so by the daily reconcile) sets to end at its period's end any live plan (`active`, `trialing`, `past_due`) that isn't set to end, of a family that isn't dissolved, whose payer on record (`group_billing_customers.payer_user_id`) is no longer an active member: they left or were removed. Never revoked or refunded: the payer keeps what they paid for. It is the backstop for every way such a plan comes to renew: a resume Polar kept whose reconcile failed before the payer left on the stale reading, and a resume the payer made in Polar's portal after leaving. Each plan is set under its change claim, read again first, and only while it still renews and its payer is still away. The same retries, refusals and failing record as the dissolved family's apply, and the payer is emailed once per plan per period (the plan-ending mail, saying they're no longer in the family). A family with no payer at all (their account deleted) goes through `revokeWithoutPayer`, as before.
- **Polar's statuses** (decided 21 October 2026). A plan is live, giving the pool and its places, only while `active`, `trialing` or `past_due` with no `ended_at`; the pool lasts until its period ends plus `BILLING_GRACE_DAYS`. `past_due` is Polar retrying a renewal, so it keeps them: the grace days cover a renewal that is late, not a payment that has lapsed. `unpaid` (Polar's retries ran out, and its docs revoke benefits then), `incomplete` (the first payment never went through, so nothing was paid) and `paused` give no pool and no places from the reconcile that sees them, mid-period too; the family reads as having no plan. They are still not ended: Polar may yet take a payment or a resume, so the mirror keeps each with Polar's status, the reconcile reads it again every time, and a dissolved family's job and purge wait for it (3.3). A plan is recorded as ended only when Polar says so (`ended_at`, or `canceled`/`incomplete_expired`) or no longer has it (404). A payer of a plan that isn't live can delete their account or dissolve the family, as one whose plan is set to cancel can. Such a plan is revoked, its ending recorded before Polar is asked so a payment taken for it afterwards is refunded whole, before a family checkout (once confirmed, after the payer takeover), before its payer leaves, is removed or deletes their account, and by a dissolved family's job; one whose current period Polar shows paid, and an `incomplete` one younger than a day, are kept (docs/self-hosting.md, Family plans). Personal plans follow the same rule (docs/self-hosting.md, When a personal plan's payment fails): kept with Polar's status, giving nothing, and revoked by HushOS before a new checkout, when their owner's files join a family's pool, or when the account is deleted.
- **One family per account,** with billing or without, held by a unique index on active family memberships (addendum 4). Company memberships, later, are outside it.
- **One storage source per person.** A member who pays for a personal plan stops paying for it when their files join the pool: the worker revokes it at Polar and refunds the unused days, prorated (addendum 5.1). While pooled, buying or resuming a personal plan is refused (`409 in-family`).
- **No stacking:** the pool is the plan's size. A member's free allowance, referral bonuses and operator grants are set aside while they are pooled and count again when they leave, are removed or the plan ends.
- **Leaving, removal, or the plan ending:** their own files go back to their own allowance. Over it, they can read, download and delete; uploads are refused until they make room or buy a plan. Nothing is deleted, and there is no grace period, since nothing has a deadline.
- **Admission** refuses a newcomer whose own files don't fit in the pool's free space (`409 pool-full`), before any place is bought.
- **What managers see:** the organizer and every `members` or `billing` holder see each member's own usage rounded up to the whole GiB ("Under 1 GB" below 1 GiB), never names, counts or contents. Every member sees their own exact usage, the family's total and the family folders' total. Every figure about the pool and every check against it counts the pool in parts, the folders together and each member's own files, each rounded up to a whole GiB, so no figure gives away one person's exact usage (addendum 3.6, 3.9).
- **Per-member limits** are deferred. When they come they are one nullable column on `group_memberships`; until then one member's own files can fill the pool for everyone.
- The payer is a billing customer keyed by owner kind and id: in Polar, a team customer per group (`external_id: "group:<groupId>"`) whose owner is the paying member (`docs/polar-group-billing-spike.md` 5). Polar products carry `hushos_plan`, `quota_bytes`, `hushos_group_kind`, `included_members` and, for a family tier, `hushos_tier` metadata, and Business products `quota_bytes_per_member`: a company's pool grows with each paid member. Members beyond those included are a quantity on the group's one subscription (a unit-based price beside the fixed base, free up to the included members), with no upper limit; companies have a minimum. Polar never learns who the members are.
- **Family tiers** (owner, 2026-10-18): Family Plus 800 GB, Family Pro 2 TB and Family Max 4 TB (in 1024s, as the app counts), 10, 20 and 30 USD a month. Four members are included on every tier, then 1.50 USD a member a month (15 a year), the same on each, up to 20 members. EUR is at parity, GBP at 0.8 (8, 16, 24 and 1.20), INR on the personal plans' ratio (399, 799 and 1,399 rupees, 59 a member). A year (owner, 2026-10-19; it was ten months before) is a round total that splits evenly into twelve: 96, 192 and 288 USD or EUR, 72, 144 and 216 GBP, 3,900, 7,800 and 13,800 INR; the member price stays at ten months a year. Each tier is a monthly and a yearly product carrying `hushos_tier` (`plus`, `pro`, `max`) beside the metadata above; the catalogue orders them by pool. The single Family plan before them (2 TB, six included, 15 USD) is archived once the tiers are on sale (`seed.ts --archive-legacy-family`), and still read for anyone on it.
- **Changing tiers** (the payer, between tiers billed the same way): a bigger pool starts now, the product changed at Polar with `invoice` proration so the difference for the rest of the period is charged at once, as a personal plan switch is. A smaller pool starts at the renewal (`next_period`): nothing is credited, since Polar's wallet credit cannot be paid out, and the family keeps what it paid for until then. A move to a smaller tier is refused while the family (its members' own files and its folders) stores more than its pool, and says how much to free; a family that grows past it before the renewal pauses everyone's uploads then, deleting nothing. Places carry over (a product change keeps `units`, and every tier includes the same members). The tier paid for comes from Polar's orders on every reconcile: the product of the newest paid, unrefunded checkout, renewal or change order, so an unpaid upgrade leaves the last paid tier in force, a paid renewal of the bigger tier gives it, and a refund falls back; no places are bought while the product differs from it, and a product bigger than the tier paid for for more than seven days is moved back at the period's end, as an unpaid raise is cut back. Portal unit changes stay off (spike E7). The move is recorded, like a cut; Polar keeps both side by side (spike 8, T1), and an upgrade drops both, after which only the cut is asked for again. Re-issues are idempotent, and a reconcile does not repeat the same one within 15 minutes but queues it for then (one pending retry per family), so webhook deliveries cannot loop and nothing needed is dropped; failures are retried with backoff indefinitely, and after five answers of 200 Polar did not keep, HushOS stops and lists the family on the management page. An upgrade paid only after its revert took effect is not credited back automatically: the operator refunds that order in Polar (see docs/self-hosting.md, Family plans). Monthly to yearly is not offered yet.
- **Billing handover** completes only once the new payer has added a card in Polar's portal; until then the old payer stays the payer and is told so, since the card does not move with the subscription.
- **A payer's account cannot be deleted** while they pay for a group: they hand billing over or cancel the group plan first, and the deletion screen says how.
- Seats are counted at admission, never at invitation; a seat cut blocks new admissions and never removes anyone.

### 3.6 Child accounts

**Not in milestone 1** (2.9). Built after the family core. A child account is a separate account type; a family stays without any browse of its adult members.

1. **Created only as child accounts.** A `guardian` starts "Add a child" in the family; the child signs up through a link, choosing a password. The flow asks for the child's own device, but nothing enforces it: the link is returned to the guardian, and whoever opens it registers the enrolment device (`docs/devices-design.md` 6). Each device the child signs in on registers a device signing key. An existing account can never become a child account.
2. **Ages.** Teens 13 to 17 first: `adult_from` must fall within five years of sign-up. Accounts for children under 13 come later, once verifiable parental consent, the terms and the privacy policy are in place (COPPA in the US, GDPR in the EU).
3. **The family check comes before the root is sealed** (decided; nothing is built yet). The join code exists only once someone is admitted (3.2), so a child's sign-up runs in this order: (a) the child's account is created but its registration is not finished, and it can store nothing; (b) the guardian checks the child's twelve words, read from the child's screen, and admits them, as for any newcomer; (c) the child's device and the guardian compare the join code of the admitting roster, the same ten compared and two typed (3.2), and the child's device accepts the chain with it as its join mark; (d) only then does the child's device seal its root to the `guardian` entries on that accepted chain (2.9); (e) registration finishes. The server refuses to finish a child registration without a seal for every `guardian` entry. A comparison that fails stops before (d): nothing of the root is sealed, the child is an admitted member whose registration never finishes, and the guardian turns the sign-up down. The family's version 1 words are not compared here either (2.4, the residual after a succession before the admission).
4. **What a guardian can do before `adult_from`:** reset the child's password (the guardian's device re-wraps the child's root under the new password's key; the reset ends the child's password sessions and tells them), open the child's personal space, and loosen the child's sharing defaults. **From `adult_from`, the server refuses guardian resets and policy changes.**
5. **Defaults:** no public links and no shares outside the family, enforced by the server, until a guardian allows them.
6. **Always disclosed.** The child sees a permanent notice: "Your parent can see your files." The record shows every time a guardian's device fetches a seal.
7. **Adulthood.** Access does not end on its own. From `adult_from`, the account holder may convert at any time; a guardian has no control that blocks or undoes it, and every conversion waits 7 days, with notices to the account's email and devices (`docs/envelope-migrations.md` 7). A hostile guardian who holds a device of the account or its mailbox can still cancel each attempt; that is a stated residual (`docs/groups-threat-model.md`), not something this design prevents. Conversion is authorised by a device key the child's devices registered, so it works even if a guardian reset the password earlier (the device still holds the root through its device memory). The person is prompted on `adult_from`, the notice then also says how to make the account fully theirs, and they stay in the family plan as an adult member.
8. **Conversion is a full re-key**, because a guardian who opened the root holds everything it wraps. In one resumable run the child's device:
    1. makes a new account root;
    2. makes new identity keys and signs an identity succession with the old ones;
    3. makes a new settings key and re-seals the settings;
    4. bumps the personal workspace key version and runs a full `drive_rotations` of the personal tree;
    5. re-seals its outgoing shares (the sharing ledger) to their grantees.

    The run also registers a new password and a new recovery phrase, rewraps every workspace grant and self-grant, and signs out every other device in the switch, in that order (switch first, rotation after); see `docs/envelope-migrations.md` 7, which also sets the 7-day hold and lists what conversion does not stop against a hostile guardian.

    The server deletes every guardian seal in the transaction that switches the account to the new root; family holders then fold the new identity into the next roster (its succession chain verifies) and re-grant the family areas to it.

9. **Early release and guardian removal** run the same full re-key, on the child's device at its next sign-in; the seals are deleted at once.

    - "Trust as Acme does";

## 6. What the server learns

Who is in which group and their roles, which accounts are child accounts with their `adult_from` dates and guardians, when guardians fetch a child's seal, who invited and admitted whom and when, who signed each roster, invitation addresses until accepted or expired, how many areas a group has and their padded sizes, and the group's name. Rosters and successions carry only public keys, which the server already serves.

The group name is plaintext because it appears in invitation emails and on bills. A group that does not want its name known can choose a neutral one.

## 7. Tests that must exist

Each fails on a defect a person would notice (see AGENTS.md):

- **Encoding:**
    - TS and Rust produce identical bytes for every statement in the fixtures;
    - a document that parses but re-encodes differently is refused;
    - a version above 2^53−1, an uppercase id and a hex digest are refused;
    - both twins' parsers and encoders keep one grammar (no byte-order mark, escapes, lone surrogates, floats, `-0`, objects; at most four deep; 4 MiB), pinned by shared raw-byte cases; a roster of more than 10,000 entries is refused; identity key versions beyond 2^53−1 are refused in both twins.
- **Group signatures:**
    - a roster or succession whose Ed25519 signature is valid but whose ML-DSA signature is not, or the reverse, is refused;
    - the fingerprint changes when either public key changes.
- **Roster:**
    - a member signature checked through the roster is refused when its ML-DSA half verifies only under a served key whose digest is not the entry's `mlDsaPublicKeyDigest`;
    - "Trust as Acme does" writes a version 3 pin with the roster's ML-DSA and ML-KEM digests;
    - refused: a forged signature, a version that is not previous + 1, a wrong previous digest, a signer who is not an active `members` holder on the previous roster, and a missing or wrong signer identity signature;
    - an entry whose identity changed without a verifiable succession chain stays unchanged;
    - rosters served beside the chain are dead branches, never a warning; two latest rosters or a chain that does not reach version 1 are refused;
    - the hard warning only when the person's marks (pins, cache, a join mark) disagree with each other or with the chain, listing both sides and naming no culprit, and still shown when the server adds malformed or foreign statements (the marks are compared before anything served is parsed);
    - a join code other than twelve lowercase words is refused; one over another roster, group key or key version, or at a succession's tie under the wrong key, is the warning; a chain short of it is refused;
    - a roster whose signer leaves on it, or that leaves no active `members` holder, is refused, and a rival-key roster breaking those rules is refused, never the warning;
    - an area key commitment is HKDF of the key alone (a known answer in both twins), and a row repeating any commitment on the chain is refused (a no-op rotation, another area's key, one key for two areas);
    - a pin trusted through a group that agrees with the entry names the group as `via`, and an empty origin reads unchecked and admits no one;
    - roster format 2 (2.10): format 1 rosters parse and verify unchanged; a chain switches up at a roster boundary and a format 1 roster after a format 2 one is refused; the root commitment has its own label (a known answer, never the area key's); a root commitment the chain listed before is refused; a reader's root key that does not match the commitment at its version is refused, one at a version a format 1 roster listed is uncommitted; a tombstone stands only at an area's next version and only for an area the chain lists; after it, any row for the area (a second tombstone, a new key) is refused, no grant is sealed for it, its write version is none, a family removal does not rotate it (one retired in the removal's own roster counts as handled), and it no longer counts toward the 1,024; a cache that dropped a retirement or changed the last root commitment is refused, and one from before format 2 reads as no roots and no retired areas;
    - the area rules: delta rows, sorted, at most 1,024; a family past 1,024 areas is refused, and a family at the cap can still remove someone (`nextRoster` builds the 1,024-row removal); a row at a version already listed, a version skipped, or a new area (or roster 1's) above version 1 is refused; a rotation and a new area at 1 are accepted; in a family a roster that marks anyone left rotates every area or is refused (a company's is not held to it); a roster that drops a holder admits no one;
    - a cache whose last roster's rows are not its areas' latest commitments, or (at roster 1) that carries an area roster 1 did not create, is refused;
    - only the server entry makes a stored chain, and no seal, opening, write version, row, pin or verdict takes one; its record is the server's (`origin: 'server'`), which a reader's acceptance refuses as a cache, and a device's cache is no server record; the web's client modules never import the server entry, and the entry refuses to load in a browser;
    - with no pin and no cache, nothing is accepted without a join mark the person compared (or creation's own seed), and the preview that works the code out keeps nothing;
    - the entry rules: an entry dropped or a wrong `sinceVersion` is refused; key versions are free, and an inflated entry leaves the member followable;
    - a server alone (unsigned or unchained rosters, other first keys with the real chain, an extension that does not continue the cache) gets a refusal, never the warning; a side of the warning names a signer only for a verified statement;
    - a removed holder's rival succession tied early waits for the marked one, and is the warning only if a roster needing the next key holds under it, signed by a holder; with the marked one withheld it is a refusal (missing succession, or a rollback at the end);
    - an own entry naming a replaced identity of the reader is reported;
    - a roster `nextRoster` builds is always accepted, and `checkNextRoster` refuses exactly what acceptance refuses, plus (with the members' identities) an entry naming keys its member never had;
    - a served chain shorter than a pin is refused;
    - a local cache outside its form, of another group, or not through its own roster is refused.
- **Succession:**
    - two successions from one `oldVersion` that both hold are refused unless a group key mark chooses; a mark neither meets is refused unless a roster holds under one of them;
    - a succession whose new key is the old one, or an earlier one, is refused;
    - `checkNextSuccession` refuses a succession tied before the latest roster under its old key;
    - a roster signed by an old key after its succession is refused;
    - a roster after a `members` holder's removal without a succession is refused.
- **Seals and grants:**
    - a key seal whose seed does not derive the published keys, or whose sealer is not an active `members` holder (the creator's key 1 seal only while they are active), is refused, and no such seal is made; nor a grant by a member who has left, nor a seal under an Ed25519 key with another ML-DSA key than the entry's;
    - a grant from a `left` granter, for another group or workspace, or under another seal kind's `info`, does not open; an earlier version's grant opens after a later one has (no floor);
    - a seal or grant made at a roster the opener's chain does not hold (another history, or a newer roster) does not open, and a sealer names only its latest accepted roster;
    - a grant only of a key the latest roster lists (by its commitment; an earlier version by the chain's): a granter kept behind cannot seal a version its roster does not list, and a grant delivering another key under a listed version, or a version above the latest roster's, opens nothing on the real chain; a grant of an earlier version's key still opens after a rotation.
- **Verdicts:**
    - roster trust gives `verified` inside the group's areas and nothing outside them;
    - a legitimate identity succession is followed, not reported as `key-conflict`, before and after a roster folds it in;
    - a forged or bit-flipped record reads as a bad signature on every device, a new one included, and `unchecked` when the writer's identity or links did not load;
    - an earlier key reads retired only along verified links (junk links before, between or after, out of order or repeated change nothing); a pinned reader retires from their pin and, before a pin at a later identity, along the member's verified chain to it; a planted key never reads retired, even with a link its planter signed;
    - two verified successions from one of the member's keys are an identity fork: `unchecked`, whatever the order, and their seals lend no history;
    - the personal-pin verifier is unchanged: junk after the chain, or links out of order, and it does not hold;
    - a seal or grant made before the sealer's identity was folded in, or under their entry's keys after they moved on, still opens with their history; one under keys no roster has folded in does not; one signed by a planted key does not, link or no link; a member seals only with their entry's keys; a key seal opens only for the holder it names;
    - successor consent: a planted first entry's link without the member's consent (one-sided, or with only the planted keys' valid half, or only the new keys' half) bridges nothing, so a record under the planted keys reads bad-signature, not retired-key, and the planted keys' grant opens nothing, while the same link with the member's consent bridges; a self-consented link from the planted keys to the planter's own, served as the member's identity, still leaves the planted keys bad-signature (retirement stops at the entry); two self-consented links leaving the first keys leave the member's records verified and a forgery bad-signature; a genuine one-sided link holds on the lag, a personal pin's walk and a fold-in, and in a seal's history after the entry's keys;
    - a served identity equal to the walk's start with a verified link leaving it is a rollback (unchecked); more than 64 links that could join the member's chain are checked no further and read as links that did not load (a record under the entry's key still verifies; one under a key only the chain vouches for reads unchecked), while links from keys the member never held are not counted; the verification cache tells members apart, two links whose fields would join alike are remembered apart, a link's serialization hook cannot borrow another's entry, a per-session cache carries across verdicts without vouching for a forged copy, and it keeps at most 4,096 results;
    - a reader whose pin was trusted through the group (`trustedVia`) sees a one-sided link from planted keys, later or first in the history, as `key-conflict`, never the planted keys retired, once the entry is put right; a reader who checked words over an honest member's earlier identity gets the roster's verdict after a one-sided rotation is folded in;
    - the person's own marks disagreeing are the warning even when what is served is junk; served version 1 keys other than the marks' are refused, never the warning;
    - a disagreeing pin with no chain is `key-conflict`;
    - a `left` writer is marked;
    - a roster that fails to load gives `unchecked`.
- **Admission:**
    - the transaction lands whole or not at all (membership, roster, grants, seat);
    - a concurrent second admission on the last seat gets 402;
    - admission with a stale roster version gets 409.
- **Leaving and removal:**
    - the server stops serving grants at once;
    - rotation gives the area root a new node key in the same request and grants only to remaining members;
    - in a family the removal's roster, rotations and grants land in one transaction, and a roster marking someone left without every area's rotation is refused.
- **Storage:**
    - a member's personal uploads count against the pool while the family's plan is live, whatever plan of their own they had, and against their own allowance otherwise;
    - a newcomer whose own files don't fit in the pool's free space is refused at admission;
    - a per-member cap, when caps exist, refuses uploads only;
    - after leaving, uploads count against the member's own allowance and, over it, are refused while nothing is deleted.
- **Child accounts:**
    - registration without a seal for every `guardian` entry is refused;
    - no seal is made to an entry without the `guardian` role;
    - guardian resets and policy changes from `adult_from` are refused;
    - conversion authorised by a registered device key succeeds after a guardian reset;
    - every conversion completes only after 7 days, and the email link or any device cancels it;
    - after conversion the old identity, settings key and personal workspace key open nothing new;
    - every seal fetch appears in the child's record;
    - an existing adult account cannot become a child account.
- **Ids:** a group or area id not derived from its seed and scope is refused.

## 9. Still open after the families release

Families (milestone 1c) are released on the web: create, invite, join with the join code, family folders, removal and leaving with every folder's keys replaced, and re-keyed records that keep each writer's signature. Family billing (1e, 3.5) is built: the payer is charged for each place and the family folders draw on the plan's pool (PR #50), and since the shared pool (`docs/families-shared-pool.md`) so do members' own files; the family's page chooses, changes, renews and cancels a plan and adds or removes places (PR #53); families choose Family Plus, Pro or Max (PR #65); and the pricing page offers the Family plan (PR #57). What is not done, and what it costs; server-side detail is in `docs/groups-server.md`, "Still open", and the core's open flags in `docs/groups-invariants.md`, "Flags".

- **Mobile families (1d) are in progress:** the native core has the family write rules (Core 1) and walks, re-keyed records and verdicts (Core 2), but iOS and Android show no families yet, so family folders open only in a browser (`docs/groups-mobile-plan.md`).
- **iOS and Android billing is read only:** the phones are to show the plan, the pool and who pays, with no purchase and no link out (`docs/groups-mobile-plan.md`, iOS 7), so a family chooses, changes and pays for its plan only on the web.
- **Polar's `PaymentActionRequired` path is unreproduced:** a bank that asks the payer to confirm an off-session charge sends them to the portal, but no sandbox card has produced that answer (`docs/polar-group-billing-spike.md`, E3), so that path is built against Polar's documentation, not an observed response.
- **Billing handover of a live plan is not built:** while a plan is live its payer can't leave, be removed or delete their account, even when another member holds `billing`; they must cancel it first (`docs/self-hosting.md`, Family plans).
- **The shared pool is built, and families are off on hushos.com until it is rolled out** (`docs/families-shared-pool.md`, step 9). What it leaves open: no per-member limits, so one member can fill the pool for everyone; moves between My files and the family folders go down and back up through the device, up to 256 MiB a file; and no personal plan's refund has yet gone through Polar for real, only against the fake (addendum 13).
- **Native clients don't read re-keyed records yet:** re-keyed records stay in family folders only, since a shipped app would stall on one in a personal folder.
- **Personal folders still re-attribute on rotation:** after a personal rotation, an editor's verified record reads as the owner's.
- **Copies outside family folders judge the legacy columns:** a copy in a personal folder vouches for the rotation's re-signature rather than the writer, and copies or moves between spaces re-sign as the copier.
- **`drive_origin_drops` has no reader:** dropped origins are kept as evidence, but nobody can view or settle a drop in an app.
- **A rotating member can drop writers' origins:** the record then reads as re-sealed by the dropper for good, with the drop shown in Info.
- **Successor consent is web only (flag F8):** for links a native app made, a member's pre-entry keys are not retired and seals made under them do not open through history.
- **Sharing in family folders is hidden** until share records signed at family level exist (3.4): members cannot share family-folder files.
- **Areas cannot be deleted (flag F11):** there is no retirement row, so area deletion cannot ship yet.
- **Rosters do not commit to an area root's key (flag F14):** a server can roll an area root back to an earlier key at the same area key version without any check seeing it.
- **A master-key rotation loses unsent family changes on the rotating device:** its sealed family records are dropped and accepted again, not re-sealed.
- **Hostile guardians are out of scope beyond the re-key and the 7-day hold:** child accounts are not built (2.9, 3.6), and when they are, a guardian holding a device or the mailbox can still cancel each conversion (threat model 3.7).
