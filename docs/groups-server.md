# Groups: the server contract

This document fixes what the server stores and serves for groups. It was written for milestone 1b and is kept current through the families release (1c). **It supersedes section 4 (API contract) of `docs/groups-design.md`, and the server-side rows of its section 1 table.** Everything about statements, signatures and what readers accept stays in `docs/groups-design.md`, `docs/groups-invariants.md` and `docs/groups-threat-model.md`; nothing here weakens them.

Families are released on the web: `GROUPS_ENABLED` defaults to `true`, and a deployment sets it `false` to hide them. hushos.com sets it `false` until paid family plans are on sale there. Without billing an area's allowance is free storage, bounded only by the counts in section 7; with billing on (1e), a family's areas draw on its plan's pool. The server was built in two phases: phase A, the schema, the repository and successor consent; phase B, the domain (`@hushos/groups`: every statement checked with the merged crypto core before the repository stores it), the routes behind the switch with their caps, limits and logging, invitations with their email, Drive's group areas (roots and rotations in the group's transaction) and spaces. With the switch off every `/api/groups` and `/api/invitations` path answers 501 `unsupported` before anything is read, `/api/drive/spaces` lists only the personal space and `/api/drive/capabilities` reports `groups: false`. The data stays, and Drive's own routes still serve a group area to its active members (section 3, "One definition of a member", which does not read the switch); no client asks while the switch is off.

## 0. What changed from the design's section 4, and why

1. **The server accepts its own chain.** It keeps the chain cache its own acceptance produced and checks each new roster or succession against it, rather than re-verifying from version 1 on every write (two hybrid verifies and a parse per roster: seconds of CPU at a thousand rosters). The core gives it a server-only entry for this: `acceptStoredChain` anchors on the version 1 keys stored at creation, with no reader, no pins and no words check, and returns a branded `StoredChain` that `checkNextRoster` and `checkNextSuccession` take and extend. A reader never calls it.
2. **Writes compare and set on `chain_revision`, not on the roster version.** A succession moves the chain without a new roster version, so a roster checked before it would otherwise land under a replaced key. Every write names `expectedRevision`; every read that a writer builds on returns `head.revision`.
3. **A removal carries everything it makes due, in one call:** the roster marking the person left, the group key succession when they held `members`, and the rotations of the areas they could open (the core's round 10 rule: a roster that marks someone left lists those areas' next keys). A client that dies between separate calls would otherwise leave the group stalled on a due succession, or a removed member holding a current area key. The same holds for taking `members` away in a role change, and for marking a departed holder left on route 7: **any roster that drops a `members` holder carries its succession, on every route**, so a succession is never left due (one left due could be wedged for good by the next holder's departure, since its seals would have to name someone the server no longer seals to).
4. **Area keys are created and rotated through a roster.** Only `members` holders sign rosters, so only they create or rotate areas, and the rotation route moves from `/api/drive/workspaces/:id/key-rotations` to the group (route 24). The roster lists only the areas created or rotated in it (round 10's delta rows, capped per roster), so it no longer grows with every rotation.
5. **`POST /api/invitations/open` needs a session and returns no chain.** A forwarded invitation email would otherwise hand the member list to whoever holds it. The newcomer's client reads the chain from route 5 after accepting, as an accepted member.
6. **Accepting needs the invited address.** The signed-in account's email must be the one invited; the inviter re-invites another address if that is wrong.
7. **New routes the flows already needed:** members' identities and succession links in bulk (route 6), re-sealing the group seed to holders whose identity changed (route 9), and an area self-grant (route 23).
8. **The server refuses an entry rolled back to an older identity** (section 6), as server policy. Only the member's own client would notice otherwise.
9. **404 never means "you left".** Group routes answer strangers and former members alike with 404 and the code `not-member`, and that code is the only one a client may wipe local state on, as Drive learned (404 and 501 from an old or misrouted server are not "gone"). A wipe forgets the device's own state (the chain, keys, cache, outbox, pending join and the family folders' mirrors) and **keeps the settings pin**: a server could otherwise answer `not-member` to erase a fork warning, list the person again, and walk them back in through a fresh join onto the history the pin contradicts. Kept, the pin is still a mark when the family reappears, so the chain is checked against it and joining stays refused (1c, `wipeGroup` in `apps/web/src/lib/groups/sync.ts`).
10. **Successor consent is stored and served** (F8, section 5): optional until a later gate, with a backfill route for links made without it.

## 1. Storage

Every signed statement is stored as its exact bytes and parsed only through `@hushos/crypto`. The columns beside it are projections the server indexes and locks on, written from the parsed statement, never from a request body, so a change to a statement's layout changes no column. Rosters and successions are history: nothing rewrites or deletes them while the group exists, and their signers carry no foreign key, because the account that signed one may be deleted.

The migration refuses to run if any workspace has no `personal_workspaces` row, then adds `owner_kind` with the default `personal` (metadata-only) and its three checks `NOT VALID` (every existing row satisfies them; nothing is scanned). The default is for containers of the previous release, which insert no owner kind, during the rolling update; this release's own inserts (sign-up, account setup, group areas) all name it. **The next release drops the default and validates the three checks**, so no later code path can create a workspace labelled personal without saying so, which `isMember`'s personal branch would then trust. Join requests for company domains are a separate table in the company phase.

`account_identity_history` gains `succession_consent` (section 5).

## 2. How the server checks a write

1. Load the chain cache at revision R (rebuild it with `acceptStoredChain` if it is missing or behind).
2. Outside any transaction, run `checkNextRoster` and/or `checkNextSuccession` on it; they return the extended `StoredChain`. For a roster, pass the identities only of members whose entry is new or changed (the diff of `parseRoster` over the head and the new roster): each such member's version 2 identities, current and history, as served identities. Version 1 identities cannot be in a roster.
3. Apply the route's diff policy (section 6).
4. Check every seal and grant statement under the sealer's entry keys at the roster it names, with the ML-DSA key matched by digest.
5. Hand the bytes, the parsed fields and the new cache to the repository, which writes under one lock (section 3).

The repository takes a roster or succession only as `ParsedRoster` / `ParsedSuccession`, branded types defined in `packages/db/src/groups.ts`. The brand alone stops nothing: TypeScript lets any object be cast to it. What holds it is a test, `packages/db/src/groups.brands.test.ts`, that fails on a cast to either type anywhere but `packages/groups/` and the database package's tests. Phase B's `@hushos/groups` mints them, by that cast, from what `parseRoster` and acceptance returned (the bytes, version, previous digest, group key version, signer, the entries changed at that version, and whether it drops a holder). So no route can fill the signer or the changed entries from a request body without the test naming it. The repository also derives "drops a holder" from its own stored roles and refuses a roster where acceptance's answer differs.

The ML-DSA keys a check needs are every key the signer has had, current and history, keyed by SHA-256 computed in the server; that set is small, so no column indexes it.

## 3. Concurrency

- **One lock per group, and one order.** Every chain write, admission, departure, acceptance and account deletion takes the `groups` row `for update` first; then the `workspaces` rows it touches (any roster with changed entries, and every departure, locks all the group's areas `for no key update`, in id order, which leaves inserts referencing them unblocked); then membership rows; then storage; an account deletion locks the `users` row last. Drive writes lock an area's `workspaces` row (taking the change sequence) and then read the writer's membership under it (`requireStillWriter`), so anything that updates both takes the workspaces first. A deadlock or serialization failure that slips through is answered `unavailable` (503), which a client retries, never a 500.
- **In order, under the lock:** the uploader must be an active `members` holder and the statements' signer; a call whose every statement is already stored (the roster at its version, the succession at its old key) is a **replay**, answered with the head and nothing written, and a call only partly stored (the roster stored, another succession beside it) is **stale**, so a client never believes a succession landed that did not; an admission must fit the seats; `expectedRevision` must be the chain's; departures come first (below); the route's policy holds (section 6); then everything is written, the head moves and `chain_revision` goes up by one, with the new cache.
- **Two holders upload version n at once.** The first commits; the second, under the lock, either resends the stored bytes (a replay: 200, nothing applied twice) or is **stale**: 409 carrying the stored winner's statement and signatures and the head, so its client can tell "mine landed" from "I lost" and re-sign only on top of the winner. A losing statement is neither stored nor logged. The primary keys on `group_rosters (group_id, version)` and `group_key_successions (group_id, old_version)` are the backstop, and only those two count as stale: any other unique or foreign key (an area id already in use, a seal naming a roster not stored) is `invalid` (`taken`, never the constraint's name, which would describe the schema to a caller), since a client re-signing on a stale answer for those would loop for ever.
- **Seats are counted under the lock, before the revision compare,** so the second of two admissions racing for the last seat gets 402 `seats`, not a 409 it would re-sign into a 402 anyway. The count is active memberships.
- **One definition of a member.** `packages/db/src/membership.ts` says who is a member of a workspace: they hold its key and it is their own, or an area of a group they are active in. `isMember` and Drive's authorization walk (`accessFor`, behind every node read and write) both ask it, so a key the server still holds for someone no longer active opens nothing through it.
- **Departures end access at once, through Drive too.** Leaving, removal and account deletion, in the same transaction: delete the person's area grants, seals and area self-grants; revoke every share and link they granted in the group's areas (a link they kept would otherwise outlive them, re-sealed by each rotation); revoke every share granted to them there (they leave the group's files, not just its keys); and mark those areas due for rotation. **Shares other members made to people outside the group stay**: they are the sharer's to stop. The backstop is in rotation itself: it re-seals a share or link in a group area only while its granter is an active member (`grantedByMember`), so one that escaped revocation is left unsealed and revoked as the rotation passes. A Drive write in a group area checks again, inside its own transaction and after it has locked the area's row (`requireStillWriter`, from `nextChangeSeq`, the share and link writes, workspace documents and the first step of completing an upload), that the writer still holds the area or a live editor share there; a departure takes the same row lock, so a write the domain authorised before a removal committed is refused (404 `not-found`) instead of landing after it.
- **Stopping a share or link in a group area marks the area due for rotation, whoever stops it.** Revoking a share or link does not take back the node key its recipient already has; only a rotation does. So every revocation in a group area (`revokeShare`, `revokeLink`) sets the area's `rotation_due_at` in the same transaction (keeping an earlier mark's time), and holders see the area in route 3's `due.rotations`. That includes a holder's own revocation, and one by a holder on hold (stopping a share is not a held write): a member without `members` may not rotate at all, and a holder whose device stops before it rotates would otherwise leave no trace of the rotation owed. Only a roster rotation of the area (route 24, or a removal's) clears the mark; a Drive subtree rotation does not. The area's row is locked before the share's or link's, in the order a departure takes them.
- **Removing someone who may resist: hold, finish, remove.** A remover's client (any active holder's) does it in this order:
    1. **Hold** the target (route 27). From then their Drive writes, epoch draws and rotation starts in the group's areas are refused under the area lock, so they can no longer create a node above the remover's drawn epoch (`epoch-stale` for ever) or start a rotation the removal must wait on.
    2. **Finish** any Drive rotation running in the group's areas (the removal would answer `rotating` with it): walk it on `/api/drive/…/rotation/*` to the end.
    3. **Remove**: draw each area's target epoch, seal the roots, and send route 19 with the roster, the succession when they held `members`, the rotations and the grants. The hold ends when it lands; it lapses on its own after 15 minutes if the client never gets there.
- **No one is admitted on the roster that drops a holder** (the core's rule, I10: the join code binds a group key no removed holder held). An admission while a departed holder waits to be marked left therefore takes two calls: route 7 marking them left (with the succession), then route 17. Promoting someone to holder in the roster that marks a holder left is one call: the succession's seals cover the `members` holders as that roster leaves the group (its active `members` entries who are active members, or the person admitted), so the promoted member is sealed to and the departed one is not.
- **A departure is marked on the roster before anything else.** Leaving, or the deletion of an active member's account, records a departure while the head roster still lists the person active. While a group has any, only a roster that marks every departed person left is accepted (409 `left-due`, naming them), and a departed `members` holder makes that roster drop a holder, which therefore carries the succession I10 asks for. Without this a holder's own departure would make nothing due: rosters that do not touch them would keep landing under a group key they still hold.
- **Account deletion departs first.** `deleteAccount` departs every group the person is in, as leaving would, before it locks the account. The only `billing` holder, or the last `members` holder of a group with others active, is refused (409, `group-holder`) and nothing changes; "last" counts only other active holders with a seal of the current group key, since a holder without one could never sign; the last active member dissolves the group. The deletion flow asks the same rule first (`deletionBlockers`), when deletion starts and again before `beforeDelete` stops their billing, so a holder is refused before anything is cancelled. Between that check and the delete another holder can still leave (H1 deletes, H2 leaves, H1 is now the last holder): then the plan has stopped and the account stays, and the refusal says exactly that. Family billing (1e) did not close that window; the fix is still a reservation: lock the person's groups and set a `deletion_pending_at` on the account (with a time limit) before billing stops, refuse other holders' leaves and demotions while it is set, then delete.
- **Every refusal rolls back the whole call.** An admission with one bad grant leaves the membership `accepted`, no roster and the seat free.

## 4. API contract

Base64url without padding everywhere; ids lowercase UUIDs. A signed statement `S` is `{ statement, signature: { ed25519, mlDsa }, signerSignature }`. Every route needs a session (`requireClient`); mutations also pass `guardAuthMutation`. "accepted" and "active" are membership states; **members** is the role.

Every roster route (7, 17, 18, 19, 21, 24, 30) takes `{ expectedRevision, roster, succession?, seals?, grants?, rotations? }` beside its own fields, and answers with the head `{ version, digest, revision, groupKeyVersion, replayed }`; a family roster that marks anyone left carries a rotation per area (`{ workspaceId, fromVersion, toVersion, targetEpoch, root, previousRootKeyEnvelope, selfGrant, documents }`, as route 24's), and the new keys' grants with them.

A grant or seal names its recipient's key version, which may not be above their current identity's. A seal already stored (route 9, and those riding on rosters) is never moved to an older key version, by anyone. **Grants are kept one per recipient identity**: `area_grants` is keyed by area, area key version, grantee and grantee key version, so a grant for a newer identity is a row of its own and one for an older identity can only ever replace that older row; readers take the newest that opens. At the same identity a grant is replaced only by the recipient or a `members` holder, and a member without `members` only fills a gap (their grant is stored only while the recipient has none at all at that area version), since the newest identity's grant is the one spaces serve and the one the grants-due gate counts; `stored` counts those written. Otherwise any member could overwrite a working grant with a signed one that opens nothing, or claim a future version no honest grant could beat. Route 22 refuses a grant to the uploader (`self-grant`): there a member's own wrap of an area key is their self-grant (route 23). **Roster calls are different: they carry a grant to the uploader too.** Route 1 carries the creator's grant to themselves, and a call that creates or rotates an area owes the new key's grant to every active member, the uploader included (`requireGrantsOwed`), so the grants table does hold rows whose granter is their grantee. A call that leaves it out is refused (`rotation-grants`), and the grants-due gate (`missingGrants`) counts it like any other grant.

**Grants owed (families).** Every member opens every area, so a call that creates or rotates an area carries the new key's grant to every member still active on the head roster and in the group (its uploader included), and an admission carries the newcomer's grant of every area's current key. When those owed grants do not fit in one call (`MAX_GRANTS_PER_CALL`, 256), the call carries a full 256 and the rest follow on route 22. **No roster lands while an active member lacks a grant of an area's current key** that the call itself does not carry: 409 `grants-due` with `data: { missing: [{ workspaceId, userId }] }`. Otherwise a remover whose device dies after the call would leave the others unable to read the area, or to finish its rotation, for good.

**A new holder gets the key.** A roster that newly gives someone `members` (an admission or a role change) carries a seal of the current group key to them, or is refused (`holder-seal`): a holder without the seed could never sign, and might one day be counted as the last one.

Read as a stream before Elysia, as the auth wrapper does (`apps/web/src/lib/group-requests.ts`, tested on its own in `group-requests.test.ts`). ### Rate limits

Through `consumeRateLimit`, buckets named by digest:

- `groups:create:user` 5 a day; an identical resend of a creation that landed is answered before it, so the retry learns it landed;
- `groups:write:user` 120 a minute on every mutation, and `groups:read:user` 300 a minute on routes 5, 6 and 29 (both in the wrapper);
- `groups:roster:hour|day:<group>` 60 an hour and 500 a day, since rosters are kept forever. Checked before the work and **charged only for a roster stored**, so refused, stale and replayed calls cost nothing and one holder's junk cannot lock the others out; a resend on another revision is answered before the check, so a retry always learns whether it landed;
- invitations: 30 a day per group, 20 an hour per inviter, 3 a day per group and address (one group's invitations never use up another's), and 10 mails a day to an address across all groups, charged only when a mail is actually sent;
- `invitations:open:address|user` 30 per 15 minutes each; `invitations:accept:address` 30 and `invitations:accept:user` 10 per 15 minutes.

### Logs

Group and user ids in paths would write the social graph into drained logs: group routes are private routes, logged by pattern (`/api/groups/:id/members/:userId/admit`) with a `group: { action, outcome }` field, never the path. A result's data never goes on the wide event either: a `stale` answer carries other members' signed rosters, which are the member list, and `left-due` names accounts.

## 5. Successor consent (F8)

`POST /api/auth/identity/succession` takes an optional `consent`: the old identity's hybrid signature over `["hushos/identity/succession-consent",1,"old",userId,…the version 2 fields…]`, then the new identity's over the same with `"new"` (6746 bytes). The server rebuilds both statements itself and verifies each half under the keys the link names; a consent that fails is refused like a bad signature (400), and nothing is stored. It is stored on the history row beside the version 2 signature and served with the link (`/api/auth/contacts/:userId/succession`, and route 6), null on links without it. A master-key rotation re-wraps the history row and leaves the consent as it was.

**Optional in 1b; required at a later gate**, once the web and both apps send it: a succession without consent then gets 409 "Update HushOS". The gate stays off until iOS and Android send consent, since turning it on earlier would stop shipped apps from replacing their keys.

**Backfill: `POST /api/auth/identity/succession/consent { oldKeyVersion, consent }`.** A client uploads consent for one of its own account's earlier successions that landed without it. The link is the signed-in account's history row at `oldKeyVersion`; the server rebuilds both consent statements from that row and verifies each half under the keys it names, exactly as `/succession` does, so a forged consent is refused (400) even when one is stored already. It is stored only where the row has none: a stored consent is never replaced, by anyone, and an upload that holds for a link that has one answers `{ stored: false }` (`{ stored: true }` when it wrote). Under the account's row lock and only for a current session (401 otherwise); 404 for a key version that replaced nothing on the account; 409 for a link from a version 1 identity, which has no ML-DSA key to consent with. It is an auth route: on the auth edge's allowlist (`identity/succession/consent`), under its 16 KiB body cap and per-address budget, and limited to 60 an hour per account, since each check is two hybrid verifications.

The server's consent statement and check are pinned to the group core itself: `auth.consent.test.ts` builds the statement for every link with consent in the core's `crates/hushos-core/fixtures/web-groups.json` and compares it byte for byte with the core's `successionConsentStatement`, and requires the server's check to agree with the core's `verifySuccessionConsent` on each of them, the fixtures' forged consents included.

## 6. What the server checks, and what stays with clients

The server refuses (400 unless noted):

- bytes that are not canonical, or of another group or kind (through `parseRoster` and `parseGroupSuccession`);
- anything the chain rules refuse, through `checkNextRoster` and `checkNextSuccession` (F3);
- an entry naming keys its member never had, and a changed entry that goes back to an identity older than the one the previous entry named (decision Q6);
- an uploader who is not the signer (403);
- seals and grants not signed under the sealer's entry keys at the roster they name, naming a roster not on the stored chain, to someone not active at their exact key version (holders also with `members`), or of an area version no roster on the chain listed;
- group and area ids not derived from their seeds;
- a succession whose seals miss a remaining holder;
- seats, membership states, and the diff policy:

The repository enforces the table under the group lock, from a route discriminator each call names (`ChainRoute`), since membership changes (leave, accept, decline) move nothing a caller outside the lock could compare against.

| Route           | May add                                                                                           | Status changes                                                           | Role changes    | Area rows                                         |
| --------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | --------------- | ------------------------------------------------- |
| A. POST rosters | –                                                                                                 | active → left only for those the server has as left, removed or departed | –               | rotations of areas a left member could open       |
| Admit           | the target only (new, or left → active), roles within the invitation's, at their current identity | as A                                                                     | –               | as A                                              |
| PATCH member    | –                                                                                                 | as A                                                                     | the target only | as A, plus the target's areas when `members` goes |
| Remove          | –                                                                                                 | the target active → left, plus as A                                      | –               | the target's areas, plus as A                     |

Fold-ins (an entry moving to its member's newer identity, roles unchanged) are allowed on every route. Every roster keeps at least one active `members` holder and one active `billing` holder; the first roster names only its creator, holding both. A removal or role change that takes `members` from someone carries its succession in the same call.

The server cannot check that a words check happened (F1, F5), that an area commitment is the key's, that a seal or grant opens to what it claims, or split views and freshness: the server is the adversary there. Clients own pins and their cache, fork detection, verdicts, cross-device marks (F4) and the retry rule (F7: persist the signed bytes before uploading, resend them unchanged, re-sign only on top of an accepted winner). Under F7 the answers sort these ways:

- a replay or `ok` means it landed;
- `stale` means another statement won, so rebuild on the winner;
- **`members-changed` and `left-due` mean the membership moved, so re-read the group and rebuild, never resend the same bytes**;
- `grants-due` means send the named grants on route 22, then resend the same bytes;
- `rotating` means finish the named Drive rotation first, then rebuild the rotation and resend the same roster bytes;
- `epoch-stale` and `root-moved` mean the area moved under the rotation, not the chain: redraw the target epoch or re-read the root, rebuild the rotation, and resend it with the same roster bytes;
- `document-stale` means workspace documents moved under the rotations, or ones a rotation left out exist: re-read every document `data.stale` names (each `{ workspaceId, kind }`; `data.workspaceId` and `data.kind` repeat the first, for clients that read only those), re-seal each under its area's new key for its version + 1, and resend the rotations with the same roster bytes;
- `succession-due` is legacy-only: it comes only from a group stored before every holder-dropping roster carried its succession, which no release that served groups ever stored (each refused a holder-dropping roster without its succession). Clients treat it as final for those bytes; no client stages a succession on its own;
- `area-limit`, `group-limit` and `seats` are final until the operator or the plan changes;
- `unavailable` and `rate-limited` mean resend the same bytes later;
- `invalid` is final for those bytes.

## 7. Quota, seats and billing hooks

- `groups.seat_limit`, null meaning `GROUP_SEAT_LIMIT_DEFAULT` (6), or with billing on, 1 (the organizer alone). From 1e, reconciling the family's plan writes it: the places paid for (Polar's count while no order of the plan waits for payment, else the last count paid), or a scheduled cut if lower.
- Each area gets its own `workspace_storage` row of `GROUP_AREA_QUOTA_BYTES` (10 GiB) without billing. With billing on (1e), a group is created with an empty `group_storage` pool and its areas with no allowance of their own; Drive's free-space check reads the pool against the used and reserved bytes of all the group's areas, locking the pool row first. Members' personal spaces do not draw from the pool yet.
- With billing on, an admission that needs a place has the payer charged for it after every check and before the write (`ensureGroupSeat` in `@hushos/billing`); anything but Polar's 200 is 402 `seats` with `data.reason` (`no-plan`, `payer`, `cap`, `canceling`, `declined`, `confirm` with the portal's `url`, `payment`), and nothing is stored.
- Without billing, that storage is free, so it is bounded by count (the counts apply with billing on too): a group holds at most `GROUP_AREA_LIMIT` areas (default 10 and at most 50, since every roster's body cap makes room for each area's workspace documents; counted under the group lock when an area is created: 409 `area-limit`), and an account may create at most `GROUP_OWNED_LIMIT` live groups it still belongs to (default 3, counted under a lock on the creator's `users` row: 409 `group-limit`; a group handed on and left no longer counts). At the defaults one account can claim at most 300 GiB through groups without billing, and more with more accounts: **bounded, not solved**. With billing on, the areas draw on a paid pool instead. Operators raise or lower both; see `docs/self-hosting.md`.
- Account deletion is refused (409 `group-holder`) while the person is a group's only `billing` holder, or its last `members` holder with others active (section 3).

## 8. How phase B does what section 2 asks

- **Loading the stored chain.** The server's record (`storedRecord` of the last `StoredChain`) is continued with `acceptStoredChain`; when it is missing, behind the group's revision, or refused because it does not continue its own chain (a record a bug wrote would otherwise wedge every write), the chain is rebuilt from version 1 out of `group_rosters` and `group_key_successions`, with the signers' ML-DSA keys stored beside them, and stored back only if the revision has not moved. A stored history the server's own acceptance refuses is an operator problem: 503, never the caller's fault.
- **A call built on another revision**, older or newer than the chain's, is not checked at all: its statements are parsed only for their places and handed to `classifyResend`, which only compares them with what is stored under the group lock and never writes: a resend of what is stored is a replay, anything else stale. So a client's retry after a timeout gets "it landed", not "stale", and a call naming a revision the chain has not reached yet can never be stored by a write landing in between.
- **A resent creation (route 1) is answered before it is checked.** The server keeps the SHA-256 of each creation call as it landed (`groups.creation_digest`, over the body as canonical JSON with sorted keys). A call from the group's creator, still an active member, whose digest matches is a replay: 200 with the group, nothing checked and nothing written, before the rate limits, the creator's current identity, and the seal and grant checks, all of which can change after the call landed (the creator replacing their identity on another device would otherwise turn their retry into 400 `invalid`, and the client would drop its only copy of the seed). Anything else takes the full path unchanged: the same bytes from another account are refused there (`invalid`, the roster's signer is not them), a different call for a stored id gets that path's answer (409 `exists` for another first roster), and a group created before the digest was kept has none to match.
- **Marking a deleted account left needs no identity.** The core (`checkNextRoster`) asks a served identity only of entries whose keys changed from the head, so an entry marked left with the keys the head names passes with nothing to serve. The server's own rollback check (section 6) runs on the same entries. No tombstone of the account's identity rows is needed. A family roster that marks anyone left rotates every area in that statement (the core's `NOT_ROTATED`), so the call carries a rotation per area.
- **Area rows against the call.** The rows a roster carries must be exactly the call's writes: the new area at version 1 on route 21, one row per rotation at its new version. Any other row is refused (`area-rows`), so the chain never lists a key no file is under.
- **Seals and grants.** The sealer or granter is the uploader; the holder or grantee must be active on the head at the exact key version their entry names (holders also with `members`); the roster the seal names must be stored with that digest; and the envelope's hybrid signature (its last 3373 bytes, over the core's `groupKeySealStatement` / `areaGrantStatement` of the rest) must verify under the uploader's entry on that roster, the ML-DSA key one of their identities whose digest the entry names. A grant's area version must be one the chain lists. A succession's seals cover exactly the `members` holders active on the head roster **and** in the group: someone the roster still lists who has left, or whose account is gone, is due to be marked left, not sealed to.
- **Rotation in one transaction.** The rotator draws a target epoch from the area (`/api/drive/workspaces/:id/epochs`), seals the root's new key under it and the new workspace key, and sends the rotation with the roster that lists it. Under the group lock the repository starts the Drive rotation at that target (refused unless it is allocated and above every epoch a node in the area carries), re-keys the root as a rotation batch would (its metadata re-sealed and signed, its shares and links re-sealed or revoked), bumps the area's key version and clears its rotation-due mark. The rest of the subtree rotates through `/drive/nodes/:id/rotation/*`. The root's new parent epoch must be the area's new key version (`invalid('rotation-root')` otherwise; a root that changed since it was read is `root-moved`). **A roster rotation never takes over a Drive rotation that has made progress.** Once a run has re-keyed any node, those nodes and anything made under them since sit under keys only that run's envelopes hold, and re-rotating over it would keep each node's oldest envelope and lose those keys for good. So a run with any node at its target answers 409 `rotating` (with the run), and the roster waits; a run that has re-keyed nothing is closed under the group lock and the roster's takes the area over. In a group area only an active `members` holder may start a Drive rotation (403 otherwise), so a member cannot start one and walk away to stall every removal. The epoch target is drawn by the rotator because the node key envelope binds its epoch (it is in the envelope's associated data); a node created above it in the meantime makes the call 409 `epoch-stale`, which the rotator answers by drawing again.
- **Old area keys during a rotation (option A).** A roster rotation moves the area to the new key version at once, but the walk re-keys the rest of the subtree later, so until it finishes the root's children are still wrapped under the root's old key. The Drive batch keeps that old key as the root's previous envelope under the old area key, which a member given only the new version (a fresh device, someone admitted mid-walk) cannot open, and a grant of the old version from a granter who has since left does not open either. So every roster rotation carries `previousRootKeyEnvelope`: the root's old key wrapped again under the new area key, a node key envelope whose context is `{ workspaceId, nodeId: root, parentId: workspaceId, parentKeyEpoch: toVersion, keyEpoch: <the root's epoch before the rotation> }`. The repository stores it as the root's previous envelope with `prev_parent_key_epoch = toVersion` in the same transaction, and route 25 serves it with the root, so the current area key opens everything the walk has not reached. It tells the removed member nothing: they already held that old key. The finish clears it with the other previous envelopes. The server cannot check that the envelope opens to the old key, and a bad one is worse than a delay: once the rotator's device is gone, nobody holding only the new key can open the unrotated part or walk it, the run never finishes, and every later roster rotation of the area answers `rotating` for good. Three things stand against it:
    1. **A 1c client requirement:** before sending a rotation, the sender opens both envelopes it built with the new area key it is about to grant (the root's new key envelope, and `previousRootKeyEnvelope` under the context above) and refuses to send unless both give the keys it wrapped. The round trip itself is tested in the worker (PR 3: wrap in `driveRotateNodes`, open through the previous-envelope path of the listing), not here.
    2. **Repair (route 28):** while the run is active, any holder who still has the old root key (everyone who was a member before the rotation does) can replace the previous envelope with one that opens. Devices re-read the root through the change sequence.
    3. **Residual, not countered: a hostile holder can wedge an area.** They can send a rotation whose previous envelope is junk and keep overwriting the repair through route 28. Holds stop it (a held holder's route 28 is refused) and a demotion ends it, as for the other equal-holder races; the server cannot tell the honest envelope from the hostile one, so the last write wins until then.

    A root still carrying a previous envelope when a roster rotation lands (one no running rotation accounts for) is refused with its own 409, `root-mid-rotation`, since resending cannot fix it; one without a 72-byte envelope is `invalid` (`rotation-root-previous`).

- **Workspace documents ride on the rotation.** Option A covers the node tree only. Workspace documents (the tags registry, `/drive/workspaces/:id/documents/:kind`) are sealed under the area key itself, not under a node key, and clients open a group area's documents only under its current key version, so every rotation (route 24's, and each one a family roster carries on routes 7, 18 and 19) carries them re-sealed: `documents: [{ kind, version, envelope }]`, `version` being the version the rotator read (the precondition of `PUT /drive/workspaces/:id/documents/:kind`) and `envelope` sealed under the new area key for `version + 1`, opaque to the server; an empty list for an area that holds none. In the roster's transaction, after the area lock and taking the document rows after it (the order `putWorkspaceDocument` takes them in: it locks the workspace's row first), the repository requires exactly one entry per document the area holds at that moment. The server keeps only the kinds shipped clients write (`DOCUMENT_KINDS` in `@hushos/drive/protocol`, `tags` today; widened when a client ships a new kind), in a document write (400 `invalid` otherwise) and in a rotation (`invalid` (`rotation-documents`)), so no member can plant a kind other clients do not know; the 8-kind and 2 MiB limits stay as the backstop. A kind the area does not hold, or one named twice, is `invalid` (`rotation-documents`): documents are never deleted, so no race makes one. One left out, or one whose version is not the stored one, is 409 `document-stale`. Every rotation's documents are checked before any of the call is written, and the answer names every stale document across all of them in `data.stale` (with the first repeated as `data.workspaceId` and `data.kind`), so a family removal over ten areas needs one round trip, not ten; the whole call rolls back, roster and rotations included, and the client re-reads them and resends the same roster bytes. Leaving out a kind answers `document-stale`, not `invalid`, because it is a race (another member created it after the rotator read the area) or a kind the rotator's client has never heard of; no route lists an area's kinds, so naming it is the only way the client learns it. Each document is checked as a document write checks it (kind, padding, the 1 MiB cap), and together they must stay within what Drive lets a workspace hold (8 kinds, 2 MiB and 80 bytes of envelopes; `invalid` (`rotation-documents`) otherwise), so re-sealing at a larger padding cannot carry an area past the limit the next rotation's body cap is sized for. Each is stored at `version + 1` with `envelope_suite` 1 and `updated_at` moved, exactly as a document write stores it; documents are not on the change feed (drive-design, "Sealed workspace documents"), so nothing else moves. A write built on the version read before the rotation is then stale, as any write would be. Nothing re-seals documents after the roster lands, and the server cannot check that an envelope opens: a client must refuse to send one it has not opened with the new key it is about to grant. **A 1c client duty:** a document the rotator cannot open (bytes a member wrote that are not a document of its kind) cannot be re-sealed as it was, and the client sends a replacement for it, an empty document of its kind sealed under the new key, rather than abort the rotation: aborting would let one member's junk block every removal. Nobody could read the junk before either, and the server cannot tell the difference. The crypto worker does this itself when it builds a rotation (`openOrReplace` in `packages/crypto/src/session-groups.ts`), for the kinds it knows an empty form of (`tags`); a kind it does not know is still refused rather than invented.
- **Rosters on routes 17 and 21 carry no room for documents.** A family roster that marks someone left rotates every area, so it carries their documents; an admission (17) or a new area (21) that would also mark a departure left may not fit its cap. **A 1c client duty:** mark departures left on route 7 (or in the removal on 19) first, then admit or create the area.
- **A new area** lands with its root (key epoch 1 under workspace key version 1, signed by the creator, its id derived in the area) in the same transaction, so an area never exists without one.
- **A family folder's top folder is re-keyed only by a roster (format 2, design 2.10).** Every format 2 roster row commits to the area root's key, so `POST /api/drive/nodes/:id/rotation` started at a group area's root is refused (403 `forbidden`), and a rotation batch that names the root, even during the walk a roster rotation started, gets `forbidden` for it (`rotateNodeIn`, unless the roster's own transaction applies it); a roster rotation (route 24, or a family roster's) is the only way to re-key it. A Drive rotation started below the root is unchanged.
- **Commitments are never shared across groups.** Every area key and root commitment a stored roster lists goes into `group_area_commitments` with the roster; one already there from another group refuses the write (`invalid` (`area-commitment`)).
- **The option A envelope's context (1c).** `previousRootKeyEnvelope` (routes 24, 18, 19, 7, and the repair on route 28) is the root's old key wrapped under the new area key with a node-key context of its own, so it can never open as the root's current key: `["hushos/drive/previous-root-key",1,workspaceId,rootId,workspaceId,toVersion,<the root's key epoch before the rotation>]` (`previousRootKeyContext` in `packages/crypto/src/drive.ts`), not the plain `hushos/drive/node-key` context. A server serving it as the root's `keyEnvelope` gets an envelope that opens nothing, so a member's device never takes the key a removed member holds as the root's current key and never counts the area writable on it. The server stores the envelope as opaque bytes, as before; nothing on the server changes. Readers open an area root's previous envelope under this context first (a plain node-key envelope is still accepted there, as a Drive batch keeps one), and the worker counts an area root as current only after it opened the root's own envelope under the area's write version, never from a cached key or a field the caller passes.
- **Uploads wait while an area's rotation walks (a 1c client duty, PR 6/7; plan decision D9).** After a roster rotation lands, the area root is under the new key, but folders the Drive walk has not re-keyed yet are still under keys the removed member holds, and a new child wrapped under one of them is readable by that member until the walk reaches it. The client therefore makes uploads (attaches included) into a folder wait until the walk has reached it by the walk's own rule (`listRotationWork`: its key epoch at the running rotation's target, route 25's `rotation.targetEpoch`, and, below the top folder, its envelope under a parent epoch at the target too), showing "Finishing a key change…" (only while the tab stays open: a reload asks for the file again, as for any upload), and refuses new folders, copies and moves into it meanwhile. Any member's device walks the area (1c step 7), but only a roster rotation it saw for itself (the top folder opened under the area's latest key at the target epoch); another run is walked only when a call of its own meets it or a removal finishes it. The crypto worker enforces it on its own terms since roster format 2 (design 2.10): it writes in a group area only under a key path rooted at the area's write version, so a folder still under the root's old key takes nothing, whether its key was cached under the replaced root or opened through the previous-root envelope, and a walk gives a folder a fresh key only under a parent already re-keyed (`KEY_CHANGE_PENDING`, which the upload queue waits out). It does not know the target epoch. **The server enforces it too:** while a rotation runs in a group area, a node made under (folders, uploads, copies, an attach's sibling) or moved into a folder inside the run's subtree that the walk has not reached, a new version of a file it has not reached (an upload's existing-file begin, an attach to the same node), and a restore to a top folder it has not re-keyed are refused 409 `rotating` (`underUnrotatedParent` in `packages/db/src/drive.ts`), since the walk only re-wraps a node already at the target and never re-keys it.

### Still open

What the families release leaves open on the server side, each with what it costs. The product-level list is in `docs/groups-design.md` 9.

- **Families are web only (1d in progress).** The native core's family write rules and walks are merged (`docs/groups-mobile-plan.md`, Core 1 and 2), but iOS and Android show no families and keep reading `/drive/workspace`: a member reaches family folders only from a browser.
- **The pool covers areas only.** With billing on, a family's areas share its plan's pool (`group_storage`); members' personal spaces still have their own allowances, and "one storage source per person" (docs/groups-design.md 3.5) is not built. Each area keeps counting its own used and reserved bytes; only the free-space read is pooled.
- **An upload begun before a removal can finish under the old keys.** Its envelopes are sealed when it begins, and `finishCompleting` publishes without asking whether the walk has reached the folder, so a file started while the departing person was still a member can land under keys they held until the walk re-keys it. The bytes were sealed while they were a member, which rotation never protects (it covers only what is written after); closing it would take a completion refusal while the walk is short of the folder and a client restart with a fresh content key.
- **Native clients don't read re-keyed records.** `rekeyedFor` stays group-only because a shipped app would stall on a row that carries an origin (decision D9): the server refuses the re-keyed form in personal workspaces until the native PR widens the switch.
- **Personal folders still re-attribute on rotation.** A personal rotation writes the legacy form as before, so a verified editor's record there reads as the owner's after a rotation (`docs/integrity-design.md`, "Re-keyed records").
- **Copies outside family folders judge the legacy columns.** A copy in a personal folder vouches for what the legacy signature says (after a rotation, the owner's re-signature), and copies or moves between spaces re-sign as the copier (decision D12): authorship does not survive either.
- **`drive_origin_drops` has no reader.** Every drop is kept with the dropped origin, its wrap, the previous re-key signature and the rest of the statement it covers (the envelope the previous re-keyer sealed, its epoch, the kind or the version's object and suite; ciphertext, signatures and uuids only), so the row alone rebuilds and verifies that statement. Drops recorded before `20261017153848_origin_drop_evidence` lack those fields and cannot be checked against their re-keyer. All are kept until the workspace is deleted, but no client or operator tool reads it: the evidence that would settle a poisoned wrap against a lying dropper sits unused.
- **A rotating member can erase writers' origins, with a trace.** The server holds no key, so it cannot tell an honest drop of an unbound origin (`dropOrigin`) from a dishonest one: any member who rotates a family folder, or a departing one who left poisoned wraps behind, can make records read as re-sealed by the dropper for good. Info says the signature was dropped, naming the dropper only under their own checked signature; nothing restores the origin.
- **Report snapshots keep no origin** (decision D10): an operator sees a reported family-folder record by its legacy columns only, which there carry no signature at all.
- **Successor consent is optional.** The gate that would require it stays off until iOS and Android send it (section 5, flag F8): their links carry none, so on the walk from a member's first keys those keys are not retired.
- **Sharing in family folders is not offered.** A walk re-seals only the shares and links in the walker's own sharing ledger, so another member's share would be closed silently at the next removal (and a share any API client makes there still is); members cannot share family-folder files until share records signed at family level exist (`docs/groups-design.md` 3.4). The server refuses making a share or link in a group area, and sealing one again or changing its password or expiry, with 409 `family-sharing` (the repository checks the workspace's owner in the write's transaction); the worker refuses to seal either there, and the web's share upgrade skips them. Both clients' walks refuse a node the server lists any on, the walker's own included. Rows a server before this stored (self-hosters with families on; see `docs/self-hosting.md`, "No sharing in family folders") stay stoppable; a roster rotation still re-seals those on an area root that it carries, and the web carries none, so its rotation closes them. Stopping a share there marks the area due, and only a holder's rotation of the whole area clears it.
- **The walk-scope rule stays.** `ownReasonToWalk` (`apps/web/src/lib/groups/walks.ts`) walks in the background only a roster rotation the device saw re-key the top folder; a member's device walking a holder's own Drive run on the server's word would close shares and links the holder's ledger keeps.
- **A master-key rotation does not re-seal this device's family records.** The device store (`hushos-groups`) is sealed under a key from the account root; after a rotation the data layer deletes chain records (accepting again from version 1 against the settings pin), outbox and joins rows, and says so (`changes-lost`): an unsent roster call, or a committed creation's seed before its first pin, is lost on the rotating device. The security-change flow (`securityStart`/`securityFinish`) should re-seal them in the same change.
- **Equal holders race (a residual, not countered).** A holder about to be removed can hold their remover first, demote them, or keep rewriting an area's tags so the removal's rotation answers `document-stale`; the honest way out is demote, then hold, then remove. Holds are unsigned and availability is trusted to the server.
- **A hostile holder can wedge an area** with a junk previous-root envelope and keep overwriting the repair (route 28) until held or demoted (section 8); the repair also needs a device that held the old root key in this unlock, so after a reload the hostile envelope stands until such a device opens the family.
- **A node made under a folder the walk has not reached keeps a key the removed member can open**, if a server that does not enforce `underUnrotatedParent` let it be made. This is not only an honest device's slip: a server and a removed member can plant such a node themselves, already at the walk's target, with a key of the member's choosing. Since roster format 2 the worker does not carry it into the new tree (a walk re-wraps only a key rooted at the area's write version, `NOT_CARRIED`, design 2.10), so nothing new is ever written under it and no device takes it as current. What is left: it stays under the folder's old key, readable to whoever held that key, and the walk reports it on every pass and cannot finish, so every later roster rotation of the area answers `rotating` until it goes. The walk then stops with "One item in this folder can't take the new keys. A manager can move it to Trash and delete it forever, then the key change finishes." That is the way out: moving the item to Trash and deleting it forever purges it, the walk's work no longer lists it, and the next pass finishes the run. Healing it in place needs the walk to give fresh keys to such nodes, a Drive protocol change.
- **Seal and grant fields are the caller's.** The domain and repository check them, but no brand marks them as checked, as `ParsedRoster` does: a new route could store unchecked fields without a test naming it.
- **Roster bodies are large for what they usually carry.** Routes 7, 18 and 19 make room for every area's documents at Drive's limits: about 34.7 MiB per holder call at the default ten areas, 141 MiB at 50, two in flight per account per server process, so several app instances multiply it.
- **The chain cache is large.** `GroupChainCache` (up to about 5.6 MB as base64) is rewritten on every chain write under the group lock; the core should leave the statement out of the server's record or store it by reference.
- **Area locks.** Every roster with changes locks all the group's areas, so Drive writes across a family pause for the roster's insert and cache rewrite: fine for families, to revisit for companies.
- **Documents from development builds.** A deployment that ran a development build with `GROUPS_ENABLED=true` before the document kind allowlist and limits landed must check its group areas before rotations can carry their documents; no release that served groups is affected.
