# Groups milestone 1d: families on iOS and Android

Milestone 1c shipped families on the web (`docs/groups-design.md` 9). The phones show none: a member reaches family folders only in a browser, the iOS Files location and the Android DocumentsProvider list the personal drive only, and the native apps' identity successions carry no successor consent (flag F8). This plan brings families to both apps without a second implementation of any rule the web worker enforces: every rule lives once in `crates/hushos-core`, pinned to its TypeScript twin by shared fixtures in both directions and by the differential fuzzer, and the apps only fetch, store and draw.

Each step below is one pull request with the full review (an independent review, then a `verify-hushos` live run where the web is touched, then a maintain-verification pass), and lists what it tests and what screenshot or simulator check proves it. Steps are ordered by dependency; a step never ships a code path a later step is needed to make safe.

## What already exists, and what does not

**In the Rust core already** (`crates/hushos-core/AGENTS.md`): roster acceptance with marks, the join mark and join code, both formats, area grants and key seals, `area_write_version`, `area_root_check`, group writer trust and the rekeyed verdicts (`group_metadata_rekeyed_integrity`, `metadata_origin_carry`, `*_compat_sign`), `roster_first`, `roster_next`, `roster_entry_own`, `pin_after`, `trust_as_group_does`, and `identity_succeed` co-signing consent.

**Only in the web worker** (`packages/crypto/src/session.ts`, `session-groups.ts`) until this plan:

1. the family write rules: which key a write may use (root-path rooting, `KEY_CHANGE_PENDING`), a walk's pending keys and `NOT_CARRIED`, the area root decided by its commitment (`rootSeen`), the write version and its block reasons (F9, F14);
2. a rotation's per-record decision (`rekeyRecord`: carry the origin after `carryOrigin`, drop it, make the record its own origin, or re-seal) and the verdict glue around the rekeyed readers (own records by personal trust, others by the roster);
3. the device store: the sealed chain record (`hushos/group/device-store/v1`), the cache with `cacheVersion` 2, the record's own pin, and the `withoutCache` fallback; the settings-pin rules (`apps/web/src/lib/groups/pins.ts`: never lower, compare and set, areas only from opened grants);
4. the join preview (`groupJoinPreview`) and the ten-compared, two-typed check (`join.ts:confirmJoin`);
5. consent for earlier links (the backfill signer);
6. staged chains and the roster calls a manager sends (admit with grants and a key seal, removal with every area's rotation and a succession, a folder's key replacement, a folder's deletion), with the outbox's resend-the-same-bytes rule (F7).

## Steps

### Core 1: the family write rules (this branch)

`crates/hushos-core/src/area_ledger.rs`: `AreaLedger`, a `uniffi::Object` holding an unlocked session's workspace and node keys and deciding every write in a family folder exactly as the worker does. The worker's key store moved into `packages/crypto/src/area-ledger.ts` so the twin is the code the web runs; `session.ts` and `session-groups.ts` call it. Also `previous_root_key_wrap`/`_open` (option A's label) and a node-key context checked as the web checks it.

The review of the first commit (Opus and Fable) found a critical defect the port had copied from the web worker: area state was keyed by area alone, so any committed chain listing an area set its write version, and another family's `uncommit` or forget touched it. A removed member who manages a second family the victim is in could list the area at an old version and, with the server serving the old top level, have the victim write under a key the removed member holds. Fixed in both twins in this PR:

- write version, block reason, root-seen version and root node are kept per (family, area); an area resolves only through the family `openArea` derived its id under, and another family's listing of it, or of the account's own personal workspace (`openPersonalWorkspace`, at the drive's unlock), is ignored and reported (`foreignListings`), never a lock; commit, uncommit and forget touch only their own family's areas; only a root at the write version names the root node;
- a chain older than the one held is refused (`OLDER_CHAIN`), so a background acceptance that loses a race with the foreground's writes no record or pin, and the web's data layer reads again quietly (`lib/groups/sync.ts`, three tries, then it says the server keeps serving an older member list); another chain at the version held is never committed (`SPLIT_CHAIN`), and the worker passes its committed chain to acceptance as a mark, so a split view within a session is the fork, the hard warning;
- an old top level served again never lowers the root-seen version, and once the root node is known any other top-level node is refused without touching it;
- a walk runs `requireWritable` first in both twins; the core gains `rotate_drop_all` (Core 2's `rotate_node` moved the pending mark after the records, as the web's `rotateKey` marks it).

- **Tests:** 22 Rust unit tests in `area_ledger.rs` and one in `drive.rs` (each rule, refused and allowed); 29 shared scenarios (`fixtures/area-ledger-scenarios.json`), the reviewers' two-family attack, another family's refusal and another family forgotten among them (each fails on the first commit's code), whose stated outcomes both twins must give and whose full outcomes each twin's fixture holds for the other to match step for step; every key envelope one twin made or served (option A's previous-root label included) opened by the other; two rule oracles on every run (each successful create, re-wrap or walk key under a parent rooted at the write version; each node a write made writable at once); a worker test of the lost race (`session.groups.test.ts`); fuzz target `area_ledger` in both twins asserting the oracles, with a fast-check generator of random step sequences (two families included) in the differential; break-checks of every rule in Rust. The TypeScript runner calls the worker's own ledger functions (`commit`, `uncommit`, `forgetGroup`, `openArea`, `openListedNode`, `newNodeKey`, `rewrapNode`, `rotateKey`); it does not reach the worker's grant opening (`openAreaGrant` needs an unlocked account and a holder's seal, and has its own shared cases) or `rekeyNode`'s records (Core 2).
- **Proof:** `core:check`, the crypto suite, the web's groups and drive tests, `fuzz:diff`, 30 s of cargo-fuzz and Jazzer on `area_ledger`, bindings regenerated and both apps built. No simulator: nothing user-visible changes.
- **Apps write family folders only through the ledger.** `node_wrap`, `node_open` and `previous_root_key_open` stay exported (personal folders, shares, the shipped apps) but check none of these rules. Every wrap, re-wrap, create and walk in a family folder goes through `new_node_key`, `rewrap_node` and `rotate_key` (since Core 2, `rotate_node`), and keys for writes come from `writable_node_key` only; app reviews reject anything else.

### Core 2: walks, re-keyed records and verdicts

The rotation's record half, twin of `rekeyRecord`/`legacyRecord`/`rekeyNode` (extracted from `session.ts` into a pure module the worker calls, as Core 1 did): `AreaLedger::rotate_node(ws, node, target, signer)` returns the whole rotated node (key envelope, metadata and versions each re-keyed raw, the origin carried after the bound check, dropped with `drop_origin`, or made from the writer's record; no legacy signature in a family folder). A node with shares or links in a family folder is refused (sharing there is hidden, design 3.4). `AreaLedger::record_verdict` is the verdict glue of `session-groups.ts:verdicts` (this account's records by its own keys, everyone else's by `group_writer_trust`, a rekeyed record with the node key at its epoch from the ledger), and `copy_form` is `judgeWith` for copies out of a family folder. `rotate_key`'s early pending mark goes away: `rotate_node` marks pending only after the records are re-keyed, as the worker does.

- **Tests:** shared fixtures: nodes rotated by each twin read by the other's rekeyed verdict (`bound: true`, the origin's verdict kept, a removed member's file `former-member`), a carried origin, a dropped one (unbound wrap, a gone writer), an unsigned record re-sealed; fuzz: the `record_integrity` seeds extended with rotated nodes; Rust tests for each branch with break-checks.
- **Proof:** as Core 1. No simulator.
- **Built (PR #66, review fixes after it):** the worker's record half is `packages/crypto/src/rotation-records.ts` and its verdict glue `group-verdicts.ts`; the core's are `rotation_records.rs` and `group_verdicts.rs` behind `rotate_node`, `record_verdict` and `copy_form`, with `open_account` binding readers and seeds to the unlocked account and `uncommit(group_id, fork)` recording the fork; `rotate_key` is no longer exported. The review (Opus, Fable) found the web's walk re-sealing served shares in family folders: a hostile server could list a share to its own key and receive every re-keyed node key. Both twins now refuse a family-folder node with shares or links (`SHARED_IN_FAMILY`): sharing stays hidden in family folders (design 3.4, "Shares inside family folders") because a walker can vouch only for shares it can tell were made by someone entitled to, to keys they vouched for, and in a family folder that ledger is each member's own, so re-sealing whatever the server lists would let the server add recipients. The Drive walk reports the refusal and stops after its retries. Both twins also refuse a second walk of a pending node and a copy of a re-keyed record served without its epoch (a refusal of unsigned records under a replaced key was tried and reverted: it would stall honest walks at a deleted member's records; the residual is in docs/integrity-design.md); `groupVerify` and `record_verdict` take the family from the ledger. Remaining twin differences: the core walks family folders only (no `legacyRecord`); `record_verdict` takes the account from `open_account`, the web from its session; personal keys come from the writers passed, not the Drive trust set. Fixtures `rotations` in both area-ledger files (eleven cases, read across and walked across), Rust unit tests with break-checks, `record_integrity` seeds from every re-keyed record.

### Core 3: the device record and the pins

Twins of the device store and the pin rules: `group_device_record_seal/open` (HKDF from the account root, info `hushos/group/device-store/v1`, associated data `["hushos/group/device-store",1,userId,groupId,store]`), `GroupChainCache` read and written as the web writes it (`cacheVersion` 2, `areaRoots`, `retiredAreas`), and `accept_served(record, settings_pin, served)`: accept continuing from the record's cache; if that is refused, accept from roster version 1 with the cache left out and **the record's own pin kept as a mark**, never against the settings pin alone (design 2.7: a server can serve older settings). `merge_pin` and `pin_ahead` move from `apps/web/src/lib/groups/pins.ts` into `packages/crypto` so they have a twin. A pin's areas come only from `open_area`'s result.

- **Tests:** shared fixtures: a record sealed by each twin opens in the other; a record from another account or group, or after a master-key rotation, refused; a cache refused (damaged, a newer `cacheVersion`) takes the from-version-1 path and a chain cut below the record's pin is still a rollback; `merge_pin` conflict, lower and higher cases; fuzz kind `device_record` in `pins`.
- **Proof:** as Core 1.
- **Built:** `crates/hushos-core/src/device_record.rs`; the web's acceptance order moved into `packages/crypto/src/record-acceptance.ts` (`acceptFromRecord`, `sync.ts` calls it) and `mergePin`/`pinAhead` into `packages/crypto/src/pins.ts`. `accept_served` is an `AreaLedger` method (it needs the committed chain, the settings and the account's store key) and answers `FetchFromVersionOne` where the web fetches again. The review (two, "merge after fixes") added: a per-family floor (the highest chain committed this session) that a refusal's uncommit never drops, in both twins, so a run that lost to a background commit can never take an older chain after a refusal; `Overtaken { split }` and `served_race_message`; a race on the continuation fetching from version 1 once; the account's root held by `open_account`, re-checked at commit; `use_settings` with the downgrade refusal; records written in commit order (the web's `putChain` refuses a lower version); `OpenedArea` carrying its family.

### Core 4: the join preview and successor consent

`group_join_preview(served, marks)` (the served chain verified as acceptance would, nothing kept; the join code of the roster where this account's entry last became active) and `join_check(code, hidden, typed)` (two hidden positions the app draws with the system CSPRNG, kept only for that showing; the typed words must be the code's there). `succession_consent_sign(user_id, link, old, new)` and `links_needing_consent(history)`, twins of the web's backfill (only links between two version 2 identities, each uploaded at its own key version).

- **Tests:** shared fixtures: a preview over a made-up first key or another admission gives another code (`join-mark-made-up-first-keys` probes reused); consent signed by the core verifies in the web and in the server's check (`packages/db/src/auth.consent.test.ts` reads the core's fixture); a version 1 link is never offered for consent.
- **Proof:** as Core 1.

- **Built:** the whole newcomer side is in the core (`crates/hushos-core/src/join.rs`, `consent.rs`), with the web worker as its twin (`packages/crypto/src/session-groups.ts`, the escalation in `join-session.ts`, the bare typed-words rule in `join-check.ts`, the backfill's filter in `consent-due.ts`); `apps/web/src/lib/groups/join.ts` now only fetches, stores and words outcomes, so neither phone writes a join rule of its own.
    - **Preview and showing:** `AreaLedger::group_join_preview(me, group_id, record, served, holds) -> JoinPreview` (`Code { roster_version, code, session }`, `NotAdmitted`, `Fork`, `RecordUnreadable`). `holds` is the escalation the app stored (below), folded in first. The marks are the ones `accept_served` reads, plus a chain or fork this session holds (the worker's `marksOf`). A code's two hidden positions are drawn with `OsRng` (rejection-sampled below 2^32 − 4, distinct, ascending; the worker uses `crypto.getRandomValues`) only the first time the family's book sees that code, and stay until a match on it: showing it again, after a wrong pair or not, never redraws. A family keeps at most 64 codes (the earliest unheld goes). `JoinSession` is a `uniffi::Object` with no constructor carrying the account, the unlock's generation, the family, the mark and the positions; the worker's showing carries a `session` number the page passes back.
    - **"They match":** `AreaLedger::join_check(me, group_id, record, served, session, typed, now, holds) -> JoinCheck` (`Matched { matched, holds }`, `WrongWords { holds }`, `Mismatch { holds }`, `Incomplete`, `Changed { session }`, `NotAdmitted`, `Fork`, `RecordUnreadable`), in the web's `confirmJoin` order: the restore; a session this unlock's book does not hold with exactly those positions (never shown, from before a lock, or replaced by a restore) is refused (`Compare the join code again.`) and incomplete words answered before anything is verified; the served chain is worked out again and another code is `Changed` (the words are not checked against it); then the words at the issued positions. The first wrong pair for the family is `WrongWords` and holds the code; any later one, for any code, is `Mismatch`; a match clears the family's wrong pair and that code's hold. The sentences are `join_check_message(again, them)`.
    - **The escalation, kept:** each `WrongWords`, `Mismatch` and `Matched` returns `holds`, the escalation sealed under the device store key (store `holds`), or `None` once nothing is held. The app stores it in place of the one before and passes it back on the first preview after an unlock; restoring only ever holds more (held positions here are kept; unheld ones take the stored positions; roster versions 1 to 2^53 − 1). A blob that does not open on this account is refused with `HOLDS_UNREADABLE`, the only answer it is deleted on. The web keeps it in IndexedDB beside the joins record, per account and family (`store.ts`, database version 2), and deletes it only on that refusal or a check that returns none; a storage error leaves it held for as long as the worker.
    - **The join:** a match returns a `JoinMatched` (`uniffi::Object`, no constructor) carrying the joins record (`{v:3, groupId, joinMark, checkedAt}`), which only the core (worker) seals. `AreaLedger::accept_joining(me, group_id, record, served, matched) -> JoinAcceptance` (`Accepted`, `Changed`, `NotAdmitted`, `Fork`, `RecordUnreadable`, `Overtaken`): another account's token is refused as not this account's, a token from before a lock of the same account with "Open it again from its saved record" (`join_matched_open`), another family's as such. The record's digest is reserved under the lock before anything else and released unless the join is accepted, so a second submission within one unlock is refused. Then `Changed` only when the account was let in again at a later roster and the served chain still passes through the compared roster with the compared code; another code at the compared roster is the fork (acceptance with the code as join mark answers it), never `Changed`. The worker's `groupAccept` takes `joining: { joinsRecord }` and answers the same way.
    - **What single use and the binding are, honestly:** a joins record is a standing permission to commit the compared code for that family until the app deletes it; "used" only stops a double submission within one unlock (cleared by a lock, another account and `forget_group`; a relaunch starts with none). It is sealed under the account root with the family in its AD, so any ledger of the same account opens it: it is bound to the account and the family, not to the ledger instance that issued it.
    - **Joins records are version 3:** version 2 (round 1, when the escalation lived in the data layer) is refused, so a join in flight across this release is compared once more.
    - **Consent backfill:** `links_needing_consent(links, identities) -> Vec<ConsentDue>` and `AreaLedger::succession_consent_sign(me, link, old_identity, next_identity)`, signing with the account root the ledger opened (no account key crosses the FFI). `me` must be the open account (`Unlock your account first.`) holding the identity it opened (`Open your identity first.`), as `open_marks` checks; then two version 2 identities, both this account's, the link naming both and signed by the old identity (`This link is not one this account made.`), and the two adjacent in `me`. The worker's `identityConsent` takes the link too and refuses in the same order.
    - **Residual, to land before any phone admits anyone (the first task of iOS 1's and Android 1's follow-ups):** the phones still open the settings document themselves and pass its contact pins to `use_settings`, so a dishonest app could plant a pin. `AreaLedger::use_settings_envelope(user_id, key_envelope, settings_envelope)` must open the settings itself (`settings_key_open` with the root the ledger holds, then `settings_open`; group pins and contacts read from it; `legacy_settings` for a version 1 document), after which `use_settings(.., contacts)` and the app-built `VerifiedPin` leave the FFI. The web is already there: its worker opens the settings (`settingsOpen`).
    - **Deviations from the wording above, following the web:** the preview is an `AreaLedger` method reading its marks from the ledger, not a `marks` parameter; `join_check` takes the served chain and the record, because the web checks only after working the code out again; the bare `join_check(code, hidden, typed)` is gone from the FFI (it stays `join_words` behind the `fixtures` feature for the shared cases and the fuzz targets), since the core draws the positions; `succession_consent_sign` is a ledger method and takes the link (checked, not trusted) and the account's identities, not the account key; both twins check `me` in the worker's order (another account first, then the record, the settings, then `Open your identity first.`), `accept_served` included.
    - **A Core 1 gap closed here (found by iOS 1's fork test):** after `uncommit` (a refused acceptance or a fork) the ledger still handed out the family's held keys: `open_listed_node` opened cached and listed nodes, `node_key` and `key_at_epoch` returned keys. Neither twin allowed reads under a fork on purpose (the web hides a forked or unchecked family's space in `s/$groupId/route.tsx`; the worker itself never checked). Now, in both, while a family that opened a folder has no committed chain, `open_listed_node`, `writable_node_key` and every open through a parent key refuse (`Check the family’s member list first.`), `node_key` and `key_at_epoch` give none, and writes were already refused (`require_writable`); the keys stay held, so the next commit reads again without opening the grants again, and `forget_group` still drops them. The area's documents were already refused (`read_version`). Shared ledger scenarios: "after a refusal nothing of the family's folder opens, cached or listed, until a member list is committed again" and its fork twin (with a `nodeKey` op, what a cached read takes, and a previous key through `keyAt`). Apps may keep their own guard; the ledger no longer relies on it. **Product change:** a forked family's folders are no longer readable from keys this session already held; before, the worker answered such reads and only the web's UI hid the family.
    - **The ladder no longer holds the family back between attempts:** each refused attempt used to uncommit, so while the continuation waited for its fetch from version 1 the family was held back and the web's catalogue filed rows read in that window as unreadable. Now only the last attempt's refusal uncommits (or a fork): the worker's `groupAccept` takes `retried` (set by `acceptFromRecord` on every attempt but the last), and the core's ladder passes the same inside `accept_served` (a continuation's or a first attempt's refusal with a record is retried, so it keeps the chain; the session check still runs). The floor and fork rules are unchanged. Chosen over treating `NO_CHAIN` as transient in the catalogue because the held chain is still the verified one until the last attempt says otherwise, and it fixes the cause in both twins rather than one client's symptom. Residual: a final refusal still holds the family back until the next accepted sync, and catalogue rows read in that window stay filed unreadable until a reload, as any read that fails does.
    - **"They match" re-reads under the lock:** after the unlocked admission, `join_check` checks again that the session's generation and positions are the book's before counting the words (the worker already re-read its family); a lock, or a restore that replaced the positions, while the chain was verified is `NOT_SHOWN`.
    - **Deferred to Core 5a:** the admin's join code over the committed chain (the worker's `groupJoinCode`, for "Let them in" on the phones).
    - **Tests:** Rust unit tests with break-checks of every rule (positions drawn once and stable until a match, rejection at 2^32 − 4 and above, holding, the alarm, the clearing, restore only holding more and replacing a stale showing, the 64-code bound, a lock and a relaunch with the stored escalation, the session and token bindings, the same-version fork, the reservation released on refusal, the joins store and versions, every consent refusal including a→c with b omitted); TS: the shared fixtures fail on every reverted web rule, and `join.test.ts` runs the web flow on the real worker, a reload on a fresh worker restoring from IndexedDB. Shared fixtures (`fixtures/web-join.json`, `packages/crypto/src/__fixtures__/core-join.json`): 22 preview cases, 23 typed-words cases, 22 join session scenarios (`fixtures/join-session-scenarios.json`, run as an app drives them: a code change after a wrong pair, a server bouncing between two codes, a later readmission, the same-version fork, a lock and a relaunch with the stored escalation, a stale showing after a restore, a stale escalation restored before a preview, a token used twice, joins records an app or another family sealed, no join without a match, a rejoin's check time), each twin's joins record and kept escalation opened by the other, 9 due and 12 sign consent cases; `packages/db/src/auth.consent.test.ts` stores the core's consent through `backfillSuccessionConsent`. Fuzz: `join_check`, `join_preview` (with "They match" and the join), `join_draws` and the stateful `join_session` in `pins` (max length 32 KiB), `consent_due` and `consent_sign` (with the link) in `succession`.

App review rules for Core 4:

- Store the `holds` each check returns in place of the one before; delete it on `None`, or when a call answers `CoreError::Sealed` (`HOLDS_UNREADABLE`), never on any other error.
- Pass the stored `holds` once per unlock, on the first preview of that family, before anything is shown. Never pass it after a showing exists in this unlock (it would replace unheld positions on screen, and that showing is then refused).
- Keep the joins record only between `Matched` and `Accepted` (or a refusal that says to compare again); after an unlock or a relaunch reopen the `JoinMatched` from the record (`join_matched_open`), never from an object kept across the lock.
- Join calls fetch the served chain from version 1 and pass the stored chain record, as the web's `fetchServed(ctx, groupId, 0)`.
- A background sync treats "not checked" (no mark yet) as skip, not an error, and never clears or forgets a family while its join screen is open.
- Leave the join screen when the ledger or disk already holds the family (a chain record or a committed chain): that is a member, not a join.
- Consent's `me` is the full opened history (the current identity and every earlier one), never a filtered list.

### Core 5a: staged chains, admission and roles

Also the admin's side of the join code, deferred from Core 4: the code over the device's committed chain for the roster that let a newcomer in (the worker's `groupJoinCode`, with whether that entry is the admin's pin of them), so the phone's "Let them in" screen reads out what the newcomer's screen shows.

Twins of `groupStage`/`restage` and the call bodies that change who holds what: a staged acceptance of the device's own signed, unsent roster (never a mark, never cached), the admit body (roster, grants of every area's current key, a key seal for a new `members` holder), role changes (granting `members` with a key seal, taking it away with a group key succession and its seals), and the organizer handover (`billing` and `members` to another adult member before leaving). The app persists the outbox (sealed with the device record's key) and resends the same bytes until a definite answer (F7).

- **Tests:** shared fixtures: bodies built by each twin accepted by the other's `roster_check_next` and by the server's checks (`packages/groups/src/server.test.ts` reads the core's fixture); a staged chain refused as a cache and as a pin; a resend after an unknown outcome is byte-identical.
- **Proof:** as Core 1, plus a `verify-hushos` run where the web admits a member a core-built roster added.
- **Built:** `crates/hushos-core/src/roster_calls.rs`, twin of the worker's `groupStage` (admission and role changes), `groupOpenSeal`, `groupGrants`, `groupJoinCode`, and of the outbox rules now in `packages/crypto/src/outbox.ts` (`outboxStep`, `readOutboxEntry`), which `apps/web/src/lib/groups/outbox.ts` drives instead of its own copies.
    - **The seed lives in the ledger:** `AreaLedger::open_group_key(me, group, seal, sealer_ml_dsa_public_key, sealer_history, holder)` opens route 8's seal with the holder identity's KEM half (the envelope opened under the root `open_account` holds) against the committed chain, and keeps the seed while it is the committed chain's current key version, whatever roster that is (the worker's rule), re-checking the session under the lock; a commit to a later key, `forget_group` and `clear` drop it. No seed or identity key crosses the FFI.
    - **Pins come from the settings, never the app:** `use_settings(user_id, pins, contacts)` takes the settings document's contact pins with its group pins (a pin filed under another person is refused). `admit_body` takes the newcomer's `user_id` and their served identity, and admits only over this account's contact pin of them (`NOT_CHECKED` without one); `member_join_code` and `outbox_open` look the pin up the same way. The web worker reads `contacts` from the settings it opened itself (`settingsOpen`); its `groupStage` admission and `groupJoinCode` no longer take a pin.
    - **Bodies:** `admit_body`, `roles_body(.., user_id, MembersRole::{Grant, Take}, kems)` and `handover_body(.., Handover::{To { user_id }, StepDown}, kems)` answer `RosterCall` (`Staged { call }`, or what the device does first and then builds again: `SyncFirst`, `OpenKeyFirst`, `OpenFoldersFirst`; the worker throws its NO_CHAIN, NO_SEED and NOT_OPENED there, and its data layer syncs once and retries), in the worker's order: the account (`NO_ACCOUNT`), the committed chain (`SyncFirst`), `members` on it (`NOT_MANAGER`, before any key is asked for; acceptance's own rules refused a non-manager too, inside `roster_next`, so this is the sentence, not a hole closed), the seed (`OpenKeyFirst`), the identity (`OPEN_IDENTITY`), then the change's refusals (`This person is in the family already.`, `NOT_CHECKED`, the words-check refusal of `roster_entry_new`, `This person is not in the family now.`, `UNCHANGED` for a role change that changes nothing, `SELF_TAKE` for taking `members` from oneself, `ORGANIZER_FIRST`), `roster_next` at format 2, the signer's entry naming the open identity, every live folder open for an admission (`OpenFoldersFirst`, before anything is signed), then signing, the succession when a holder loses `members`, the **staged chain** (acceptance itself from the committed chain's cache; never committed, cached, a mark, or handed to the app), seals and grants made against it. Under the lock: still the session (`NOT_THIS_ACCOUNT`) and still the committed chain (`SyncFirst`), then the outbox entry is sealed into `StagedCall { outbox_id, route, body, entry }`. User ids are lowercased and checked as UUIDs on the way in.
    - **Owed grants (`SendGrants` is no dead end):** `grants_body(me, identity, group, missing: Vec<OwedGrant>) -> GrantsCall` (`Grants { requests }`, one route 22 body per folder and 256 grants, or `SyncFirst`, `OpenFoldersFirst`), from any active member, each grantee active on the committed chain, ids lowercased and each owed grant once, the twin of `groupGrants` plus `fillGrants`' batching.
    - **The outbox:** the entry is the web's `OutboxEntry` version 1 with the body kept as the exact text (returned verbatim) and `previousRosterDigest`/`rosterDigest` (the web's entries store both too, but nothing reads them on the web yet: `sendLocked` passes no head). `AreaLedger::outbox_open(group, outbox_id, user_id, entry)` (the `outbox_id` compared without ASCII case, in both twins) answers `Landed` when the committed chain holds the call's roster, `Superseded` when it passed through the head the call was built on and moved on (a head that never held it gives no local answer, and the bytes go), `Hold { AwaitingCheck | OtherKeys | Committed }` (no body), and only otherwise `Send { body }`. Another account's `user_id` is an `Input` error (an app bug never deletes another account's entries); another `outbox_id` or anything that is no entry is `CoreError::Sealed` (delete, say a change was lost). `outbox_step(status, code)` is the answer table. `group_device_record_seal`/`_open` and `DeviceStore` are fixtures-only: the outbox is the core's. The web's outbox now fails closed: an entry the shared reader refuses is dropped and reported lost, never sent.
    - **The admin's join code:** `member_join_code(group, user_id, rosters) -> MemberJoinCode` (`Code`, `OtherKeys`, `NotAdmitted`, `SyncFirst`, `NotPinned`), over the committed chain, only from served rosters on it.
    - **A web bug fixed in both twins:** an admission (and a fold-in's grants) asked for the key of every area the chain ever listed, deleted folders included, and threw `Open every family folder first.`: nobody could be let into a family that had deleted a folder. Both now skip retired areas. Shipped separately for production as the web fix on `fix/admit-after-delete`.
    - **Deviations from the wording above, following the web:** `stage_roster` is not exported (a staged `AcceptedRosters` in an app's hands could be passed as a cache or turned into a pin); there is no `restage` (no 5a resend needs staged secrets; 5b adds them); the handover is the web's two calls (`billing` to them, then the organizer steps down once that landed), not one body giving `billing` and `members`; milestone 1 has no child accounts, so "adult" is any active member; the admin's code is withheld unless the entry is the admin's pin of them.
    - **Tests:** 20 Rust unit tests in `roster_calls/tests.rs` (the shared family adds a third live folder rotated to key version 2: an admission grants exactly A1 at 1 and A3 at 2), with break-checks of every rule; survivors: `Give one person the role at a time.` and `stage_chain`'s version checks (unreachable through the typed changes), the grantee-active filter in `grants_body` and the pin's user-id filter in `member_join_code` (each duplicated by `area_grant_seal` and by `use_settings`' filing check, which are break-checked), and the admission's pin provenance itself (structural: no API takes a pin). Fuzz kinds `outbox_entry`, `member_join_code`, `roster_call` and the stateful `roster_call_session` in `pins`, both twins.

App review rules for Core 5a:

- **The outbox.** Keep `StagedCall.entry` (under `outbox_id`, per account and family) **before** the first send; send `body` exactly as returned; on every answer call `outbox_step` and drop the entry only on `Landed`, `Stale`, `MembershipMoved`, `Refused` or `Wiped` (after `SendGrants`, `Rebuild` or `Resend` the same bytes go again). Never sign a call again while its entry is kept. Before building any call, open and send every kept entry of that family first.
- After a lock or a relaunch, send kept entries only through `outbox_open` (with the entry's `outbox_id` and the account's `user_id`); drop on `Landed` or `Superseded`; never send a `Hold`. Delete an entry on `CoreError::Sealed` and tell the person a change was lost; keep it on any other error.
- **`SendGrants`:** fetch route 6 for the KEM keys of `missing`, call `grants_body`, post each request to route 22, then send the kept entry again. **`left-due`** (`MembershipMoved` with code `left-due`): marking someone left needs a removal body (Core 5b), so until then keep nothing, say "Someone left the family. Finish that on the web, then try again.", retry the call once per open of the family page, and never loop.
- **After `Stale` or `MembershipMoved`:** drop, sync, re-read, and rebuild only if the change still applies; "already in" or "not in the family now" after a `Stale` are the change having happened, not errors to show. **`Refused` with `forbidden`:** drop, sync, re-read this account's roles. **`Wiped`:** forget the family on this device.
- **The half-finished handover:** while this account and another active member both hold `billing`, the family page offers "Finish handing over to X" (`Handover::StepDown`) until it lands; sync under the writer lock before `StepDown`.
- **Pins:** pass the settings document's contact pins to `use_settings` on every settings read; no call takes a pin from anywhere else.
- **One writer per family at a time** (the web's Web Lock): sync, `open_group_key`, stage and send under the same lock, and sync before staging so `expected_revision` is the head's.
- On `SyncFirst` sync the family, on `OpenKeyFirst` open route 8's seal with `open_group_key`, on `OpenFoldersFirst` open every live family folder with `open_area`, then build the call again (once; the same answer again is Couldn't check). On `NOT_THIS_ACCOUNT` unlock and build again. Sync before `member_join_code`, and on `NotAdmitted` sync once more; show a join code only from its `Code`.

### iOS 6: family folders in Files

**Yes, one File Provider domain per family**, identifier `com.hushos.app.family.<groupId>`, display name the family's name, owned by (account, origin, group) exactly as the drive domain is owned today. Why: design 3.4 already promises one Files location per space; a family folder that exists only inside the app is the thing members will notice first; and the ledger makes the extension safe (it fills its own `AreaLedger` from listings, as the worker does after a reload, and runs the same acceptance from its record). Costs that decide the shape: the extension accepts from the device record (one chain read and a cache continuation, no ML-DSA from version 1 unless the record is refused); the domain is removed on leave, not-member, or a fork; Files writes that meet `KEY_CHANGE_PENDING` answer `NSFileProviderError(.serverUnreachable)` so Files retries instead of deleting the item (never `noSuchItem`, apps/ios/AGENTS.md). Read first, writes in the same step only if the PR stays reviewable; otherwise a step of their own after this one.

## Decisions

Taken by the owner (2026-10-18):

- **Manager actions:** the phones get every manager action the web has (invite, let in, remove, roles, organizer handover, replace keys, delete folder); billing is the exception.
