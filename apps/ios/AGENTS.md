# HushOS for iOS

SwiftUI app, iOS 26 and later, with the File Provider extension (`Files/`) and the sign-in action extension (`FilesUI/`). Everything the three targets share is the Swift package `Packages/HushOSKit` (keychain, Drive API, the vault that opens keys, OPAQUE sign-in) over `Packages/HushOSCore`, the UniFFI bindings of `crates/hushos-core`. The repository's root `AGENTS.md` applies here too.

## Building

```sh
bun run core:apple      # Rust -> Packages/HushOSCore (needed once, and after any core change)
bun run ios:project     # XcodeGen: project.yml -> HushOS.xcodeproj (not committed)
bun run ios:build       # simulator build into apps/ios/DerivedData
bun run ios:run         # install and launch on the iPhone 18 Pro simulator (SIMULATOR=<udid> to pick another)
```

The API is the web dev server on http://localhost:5173 (`bun dev` at the root); the simulator shares the host's network. The sign-in sheet has a field for another origin.

## How it fits together

- The session cookie, the remembered device (account key sealed under a device key) and the origin live in the shared keychain (access group `group.com.hushos.app`, service `com.hushos.files`), so the extensions read the same session the app signed in with. Signing out deletes the session, removes the Files domain and wipes everything of the account on the phone, the remembered device included, so the next sign-in starts from the password.
- `Vault` (an actor) opens the account key from the device memory, the workspace key from the grant, node keys under their parents, and keeps a node-to-parent index in the app group container so a cold extension process can find an item by listing its folder.
- Per account, never across: the queue's records (`BackgroundTransfers.Record.owner`) and Save to HushOS's notes (`ShareHandoff.owner`) say whose they are, and `TransferOwnership` runs them only for that account, keeps them while nobody is signed in, and drops another account's (or an unowned one's) without a request to the server. `AccountStore` keys the group's account data by `AccountOwner` (the same user id on another server is another account); `TemporaryCopies.claim` does the same for each process's temporary folder (the app at sign-in, the Files extension through its gate). The app checks the keychain's account when it comes back on screen (`AppModel.checkAccount`), so a sign-in from the Files sheet replaces what it shows.
- Files: `FileProviderExtension` is replicated (`NSFileProviderReplicatedExtension`), with writes (folders, renames, moves, trash, uploads with thumbnails), thumbnails and the change feed as sync anchor. `FileProviderUIController` shows the OPAQUE sign-in inside Files when the session is gone.
- One domain identifier (`com.hushos.app.drive`) serves every account, so the domain has an owner: the account (user id and origin, `AccountOwner`) it was added for, recorded in `local/files-domain-owner.json` (`FilesDomainOwner`) when `FilesDomain.register(for:)` adds it. At every sign-in and signed-in launch (and after a sign-in from the Files sheet) the same owner keeps the domain and what Files cached; another owner, or none on record, gets it removed with `.removeAll` (pending folders and edits included: they are the other account's) and a fresh one added, the new owner recorded only after the old domain is gone. Never `reimportItems` for another account: Files scans what it cached and calls `createItem` with `mayAlreadyExist`, and the extension created the last account's folders in the new account's drive (seen on the simulator after an expired session, and after a reinstall: uninstalling the app keeps the domain but drops the app group). The extension goes through `FilesGate` on every call (items, contents, writes, thumbnails, each enumerator pass): the session must match the recorded owner, else `NSFileProviderError(.notAuthenticated)` and nothing reaches the server. Sign-out removes the domain with `.removeAll` and then the record. A new domain on iOS starts disabled until the person turns it on in Files (Browse, the ... menu, Edit, the HushOS switch). Simulator debug builds skip that through `NSFileProviderDomain.testingModes = .alwaysEnabled`, which needs the `com.apple.developer.fileprovider.testing-mode` entitlement the app carries; a device build without that capability in its profile must drop the entitlement.
- Design: native structure and controls, Liquid Glass from the system, Paper only as the accent colour and the words. No custom cards or buttons.

## What the app does

Home (search pill, type chips, tags row with a manager, recent files), Files (the tree with search, tag filters, a floating add button, select mode with copy, cut, move and trash for many, a paste bar while the clipboard holds items, and the same replace, keep both or skip prompt the web shows for same-name uploads), Shared (what others gave you; opening needs the identity keys, not in the core yet), Account (name, plan and storage, read only with no way to buy (App Review 3.1.3(f)): while `/api/auth/storage` names a `pool` the card is the family's plan, "Shared with <family>", and the pool's figures (no Files row: the total is counted in whole GB), and "Not enough room" reads `StorageAllowance.free` (`availableBytes`), never quota less used, decided by HushOSKit's `PlanDisplay`, which falls back to the personal plan when `pool` is absent or unreadable, and names that plan only while it is live (`PlanStanding`, the web's `planStanding`: not ended and active, trialing or past_due); unpaid, incomplete or paused reads Free with the lapsed plan's words (`LapsedPlan`), said and never linked, and anything ended reads Free; change password and delete account through OPAQUE in the core, Contacts and Your twelve words, trash, sign out). People (a sheet from Account and from the Shared header) starts with Add someone and Your twelve words rows above the list, sorted by name, with Find someone from eight contacts; Your twelve words is `OwnWordsSheet` in `Sharing.swift`, which checks the served identity first (`Vault.currentOwnFingerprint`) and closes when the session ends. Uploads and downloads run a Live Activity (`Widgets/`, Dynamic Island and Lock Screen). Copies reseal the version envelope in the core (`version_reseal`); the server keeps the object.

## Things learned the hard way

- Never map an unknown error to `noSuchItem`: Files deletes the item locally. Only the server's "This item no longer exists." and its `trashed` code (`DriveAPIError.trashed`: the item or a folder above it is in the trash, which this location doesn't show) are that. Reporting `trashed` as a read error kept folders trashed on another device in Files indefinitely, retrying every few seconds, and a new folder of the same name showed up as "… 2".
- In `enumerateChanges`, report deletions before updates: a folder replaced by a new one of the same name arrives in one batch. The change feed marks a node deleted only on a verdict (gone, trashed, unopenable); a network or server failure fails the batch instead.
- The app signals Files after every live sync that changed something, so changes from other devices reach the Files location without a local write.
- Items advertise write capabilities even for read-only paths; the simulator's volume refuses the read-only flags.
- `documentStorageURL` asserts in a replicated extension; decrypt into the temp directory and let Files move the file.
- The two extension targets build in Swift 5 mode: the File Provider API is callback based and Swift 6's sending-closure checks reject it.
- Simulator builds embed entitlements in the binary's `__entitlements` section; `codesign -d --entitlements` shows an empty dictionary and that is fine.
- Extension logs: `xcrun simctl spawn <udid> log show --last 2m --predicate 'subsystem == "com.hushos.app.files"'`; fileproviderd's own view: predicate `process == "fileproviderd" AND eventMessage CONTAINS "hushos"`.
- Every failure a person reads goes through `ErrorWords.say` (HushOSKit): nil for a cancellation (show nothing), HushOS's own words (`WordedError`, the core's sentence) or the caller's fallback, never an error's `localizedDescription`. `DriveAPI` turns a request cancelled under a cancelled task into `CancellationError`, not `transport`: a tab switched mid-load once set the offline line or, through Shared's `.task`, marked every file "Couldn't check". A request the system cancelled (`URLError.cancelled` while the task runs: a torn-down session, a killed request) stays `transport`, retried and reported, or a failed upload looks finished. A save or upload loop never takes a cancellation for success: Save to HushOS stages through `StagedSave`, which puts the shared copy back and always has words. Store-wide state (trust, mounts) is never left to a view's task to finish.
- A replicated location lists from what Files cached, so an ended session only showed a dead-end "You need to authenticate" alert. The extension's first `.notAuthenticated` signals the working set (`SignInPrompt`), whose failure puts the location in its signed-out state, where Files offers the sign-in sheet. After a sign-in `FilesDomain.register` calls `signalErrorResolved`, or Files leaves the location "Syncing Paused" and read only. Files still keeps its "Authentication Required" page in the open folder until the folder is opened again; Authenticate there closes at once when the session is good (`prepare(forError:)` checks first, so nobody signs in twice), and sometimes that redraws the listing, sometimes not. Files may hand the UI controller a second request, so its once-only guard resets on every `prepare`. The app follows a sign-in made in the sheet when it comes back on screen (`AppModel.checkAccount` over `SessionChange`: the same account's new session is adopted in place, another account's stops the last one's queue and notices first; every change but none drops the last session's family sync, ledger keys and vault, `SessionChange.forgetLastSession`). Save to HushOS's plaintext is swept by owner, not by age alone: a staging folder, and a `transfers/<id>` folder before the copy moves in to be sealed (`StagedSave`), names the extension process that made it (`ShareHandoff.claim`, a marker, never a lock) and stays while that process may run: only ESRCH counts as gone, so a sheet suspended mid-seal, whose folder holds the only copy, is never swept for being quiet. A queue folder with no note and no transfer goes when its claimant is gone, or after a day (`sweepOrphans`, run by the app's queue). Adopting a note writes the queue's records first and only then removes the note and the part files it read (`ShareHandoff.adopt`). Known residual: `FamilySync.forget()` on a session change clears the ledger of a vault the queue may still hold, so a family upload sealing at that moment fails; its plaintext stays for Retry.
- Keychain items are replaced with `SecItemUpdate` (added only when missing), never deleted and added again: the app and both extensions read them, and a read between the two found no session.

## Sharing, links, reports, rotation (added 2026-09-22 evening)

- `HushOSKit/Shares.swift` mounts what others shared (identity opened once, `shareOpen`, the previous envelope during a rotation); `Links.swift` holds the owner's link routes, `PublicAPI` (no cookie) and `LinkVault` for a visitor; `Reports.swift` seals the node key to every operator; `Contacts.swift` keeps the pins in the account settings document with compare-and-set and seals shares to a pinned contact; `Account.swift` rotates the master key and reads the recovery key.
- A password change or key rotation ends every session on the server, so the sheets sign in again with the new password themselves.
- Writes land in the parent folder's workspace (a shared folder is the granter's); the server copies within one workspace only, so the paste bar refuses a cross-drive paste.
- Every screen uses the system navigation bar (`screenChrome` in Theme.swift), so the bars move where iOS puts them (iPhone Duo's vertical strip, the tab sidebar's toggle). A tab root (Home, Files, Shared, Account, Search, `root: true`) has its big title on the row with its buttons (`inlineLarge`); a pushed screen follows Apple's Files app: the browser toolbar role (title leading, after Back) with a 20pt bold title in the title slot, on the same row as its buttons. UIKit documents that a large inline title moves to its own row under the buttons once there is a Back button (`UINavigationItem.LargeTitleDisplayMode.inline`), so pushed screens never ask for one. What sits under the title (Shared's With me / By me, Home's chips) is a section's header: give such a section `listRowInsets` of zero and its rows explicit insets of 20, or the rows lose their margin. A folder's search is the system `.searchable` field under the bar. A link pushes onto a tab's stack only once that tab's screen has finished appearing (`onFinishedAppearing`, UIKit's viewDidAppear, Appeared.swift): Files (BrowseView), the Trash (AccountView) and a share link's page (SharedView). Pushed earlier, the pushed screen's bar could be laid out before the tab had its safe area.
- Info beside the list (`DriveStore.infoBeside`, HushOSKit's `InfoFollow`) follows the vault's rows, never the lists' caches: `Vault.standing(of:)` walks the item's folders in its own workspace and says live, held (trashed, or a trashed folder above it), removed (it or a folder above confirmed gone: `Vault.remove`, used for trash, purge and feed tombstones and marked in `removedRows`; `forget` only drops a row to be read again) or absent. `InfoLookup.decide` is Android's `infoLookup`: close on a confirmed removal or a share no longer listed, show a live row, close a held one, keep the last row while it is only absent.
- Known iOS residual, accepted by the owner on 2026-10-29: on iOS 26 and 27.0 a cold launch from a link can still draw the pushed screen's navigation bar over the status bar (Back over the clock, the buttons over the battery; about 1 launch in 4 in the simulator, none seen on the Duo's 27.1 or the owner's 27.2). It is an iOS bug with no fix in the app; a Feedback report is drafted in PR #233.
- Revoking a share rotates the subtree (`Vault+Rotation.swift`, the web's protocol: work in depth order, parents first, previous keys kept for children wrapped under them, shares re-sealed only to keys the pins vouch for, password links without a kept password key reported unsealable). Pasting into another drive re-uploads (`copyAcross`); a link made against a stale epoch reloads the item and retries once.
- Who can open what (`DriveStore.sharing`, from `/shares/mine`) is asked again through `SharingRefresh` (HushOSKit): at once after every restore (one row, many, a trash's Undo), on reconnecting, and after a sync that applied a change in the own drive, at most once per 10 s with one load at the interval's end (the server leaves trashed items out, and a change can't say it was a restore). `sharing` is replaced only when the marks changed, and `sharingVersion` moves when what the server lists changed (`SharingRefresh.listing`: share ids with roles, link ids; the marks miss a link replaced by another); Shared reloads By me on it through one `.task(id:)`, only while its tab is on screen. Tests: `SharingRefreshTests` (a restore loads even when the sync brought nothing; one load per sync with changes, none without; at most one per interval, with one at its end; a restore is never held and answers a change waiting for the interval; requests during a load get one load begun after them; By me follows the listing, not the marks).
- Keep downloaded is the app's own feature (`Offline.swift`, app group container, one folder per version, an Offline section on Home): iOS Files never offers "Keep Downloaded" to third-party providers, even with `NSExtensionFileProviderSupportsPinning` and `allowsEvicting`, and `contentPolicy`'s keep-downloaded case is macOS-only. Files' "Download Now" does work through `fetchContents`.
- The File Provider domain is kept across launches for the same account (removing it dropped Files' cache) and replaced for any other (see the domain's owner above). A Photos picker inside a Menu never presents; use a button and `.photosPicker`. Transfers hold a UIKit background task so a lock or Home press does not suspend them at once.
- Live Activity: requested, updated and ended correctly (ActivityKit log, SpringBoard aperture assertions), but the compact island content was not legible in simulator captures; check on a device.

## Running on a real iPhone (added 2026-09-22 evening)

- `DEVELOPMENT_TEAM=<team id> bun run ios:device` builds for the plugged-in iPhone with automatic signing and installs it through `devicectl`. Xcode must be signed in to an Apple Developer Program account: the app group and keychain sharing are not available to free accounts.
- Entitlements come from `App/HushOS.xcconfig`, not from the XcodeGen `entitlements:` block (a target-level setting would shadow the per-SDK choice): the simulator gets `App/HushOS-Simulator.entitlements` (adds the File Provider testing mode), a device gets `App/HushOS.entitlements`. Check what a simulator build embeds by reading the binary's `__TEXT,__entitlements` section; `codesign -d --entitlements` shows nothing there.
- On a device the Files location starts disabled: Files > Browse > the ... menu > Edit > turn HushOS on.
- A real phone defaults to `https://hushos.com` (`AppModel.defaultOrigin` under `#if !targetEnvironment(simulator)`); the simulator keeps `http://localhost:5173`. The origin can be changed on the sign-in screen either way.

## The mirror and the catalogue (added 2026-09-22 night)

- `Mirror.swift` is the web's IndexedDB tree mirror in SQLite (raw SQLite3, no dependency) in the app group: `nodes` (id, workspace, the row as served), `cursors` (feed cursor per workspace), `thumbnails` (sealed trailers by version id). `Vault+Catalogue.swift` builds the catalogue the way `packages/drive/src/client.ts` does: pull the whole feed once (a feed is state, not a log), open rows parents first, then `sync()` pulls only what changed since the cursor. `children(of:)`, `recents()`, `trash()` and thumbnails answer from it first; shared folders (other workspaces) still go to the network.
- The store builds the catalogue after `loadRoot()` and calls `sync()` before every refresh; `catalogueVersion` bumps when lists change. Inspect the mirror on the simulator with `sqlite3 <app group>/mirror.sqlite`.
- Design: colours are Paper's own in both appearances; tag pills lighten their ink in the dark. Icons: light = mark on sheet, dark = mark on transparent (iOS backs it), tinted = white mark on black (iOS's tinted and clear styles derive from it). Splash: black mark on white, white mark on black; the simulator caches launch screens, so reboot it after changing them.

## Out of backups (added 2026-10-11)

- `HushOSKit/Unbacked.swift` keeps the account's data on this phone and out of iCloud and computer backups: decrypted files (`offline`, the queue's `transfers`, Save to HushOS's `share-staging`) and anything naming what is in the drive (`state/` with the kept-file lists, the last folder, recent searches and the last email; `local/` with `files-parents.json`, `account-owner`, `files-domain-owner.json`, `mirror.sqlite*`, the families' records in `groups/` and the sealed rollback marks in `marks/`). Lists the app and its extensions share go in `state/` as JSON through `Unbacked.read`/`write`, never in the app group's `UserDefaults` or the app's own, which are plists a backup takes.
- Only folders carry the mark: an atomic write replaces a file and drops its mark, and SQLite makes its side files when it likes. So no loose file at the top of the group; put it in `local/` (an older version's loose files are moved there once by `apply()`). A folder sign-out removes is made again with `Unbacked.folder(_:)` before each write (the queue does), never with a bare `createDirectory`.
- Make any new top folder for such data with `Unbacked.folder(_:)` and add its name to `Unbacked.names` and, if it belongs to the account, `AccountStore.accountFiles`. A restore can drop `isExcludedFromBackup`, so `Unbacked.apply()` marks everything again at every launch of the app, the Files extension and the share extension. The temporary folder is never backed up and needs no mark.
- A received share opens only when its granter is pinned, the pin is `verified` (version 3, see below) and the served keys are the pinned ones (`ContactPin.granter`); anything else shows "Add <name>…" or "Check <name>’s words again…" on the row. Pins are made only after the words check.

## Keys, settings and the sharing ledger (added 2026-10-12)

- Node keys and opened nodes are kept by workspace and node (`NodeTable`): the server picks a share's ids, and keyed by id alone a share could replace one of the account's own folder keys. Look up a parent by `NodeRef(node.workspaceId, parentId)`; id-only lookups prefer the own workspace. A share into the own workspace, or whose node names another workspace, is refused before anything opens (`Vault.checkReceived`); a write's reply is adopted only for the workspace written into.
- The settings document is kept as JSON (`Settings` in `Settings.swift`) so fields other clients write survive every save; edit it only through `updateSettings`, which retries a 409. It holds the pins and the sharing ledger (`sharing.shares` node to grantees, `sharing.links` link to node): a share or link joins after the server takes it and leaves before it is stopped, and rotation re-seals only what the ledger holds.
- Rollback marks (`RollbackMarks.swift`, `RollbackMarkStore`): the highest settings sequence, identity key version and identity version this phone has seen, one record per account in `local/marks/<slot>.json`, sealed by the core under a key from the settings key (`rollback_marks_update`, the web's format) with the settings key's envelope beside it (`Vault.marksKey`: kept envelope, then the vault's key, then the server's; made only to keep a first mark). Checks are `SettingsMarks.check` (with `document`: once a version 2 document was opened or saved, none or a version 1 row is refused at any sequence)/`IdentityMarks.check` over what `read` returns, and again over what the write found. Every Auth request a vault makes passes `as: session`, so it never goes out under another stored session. A record that does not open is `MarksWords.unreadable`, a mark that can't be kept `MarksWords.unsaved`: the step it guards fails (an identity or settings are never taken without their mark). Deleted on every wipe with the rest of the account (`AccountStore.accountFiles`), the plaintext files earlier versions kept across sign-outs (`local/settings-marks.json`, `local/identity-marks.json`) too, which the first read folds in and removes. The app and its extensions share them, so every write is one open-raise-seal under `flock` on `local/marks.lock` (`FileLock`), made only while the vault's own session is still stored and no sign-out came since it began (`AccountStore` deletes the marks under the same lock, so a raise that waited through a sign-out writes nothing back; the lock file itself is never deleted), held only inside a `ProcessInfo.performExpiringActivity` assertion (a process suspended holding a lock in the group container is killed with 0xdead10cc), never waited on without end (`LOCK_NB`, about a second of retries; one try when the system grants no time). A raise counts in this process at once (`MarkFloor`, forgotten at sign-out), so one the system gave no time to write still refuses a rollback here and goes into the next write.
- Shares are sealed only hybrid, to a verified pin, with the KEM key whose digest the pin holds (`ContactPin.sealKeys`); rotation leaves out anyone who fails that and says who (`RotationOutcome.skipped`).
- Nothing names a file on the Lock Screen: the Live Activity and transfer notifications carry counts, and a finished summary's second line says where a tap goes (Android's words). The app covers itself in the app switcher (`PrivacyCover`, a window above sheets) and `PhraseGrid` hides the words while the screen is captured.

## Integrity: padded objects, signatures, successions (added 2026-10-13)

- The client speaks Drive protocol 3; `DriveAPI.clientHeader` sends the app's product version (`ios/1.0.0`, from `MARKETING_VERSION`), which the server compares with its minimum. Uploads write content suite 3: `chunkEncrypt` pads, `chunkDecrypt` returns only the file's bytes, and every chunk (padding included) is fetched on a full read; ranges and layouts take the version's suite (`OpenedVersion.layout`/`range`). Progress counts the file's own bytes (`FileProgress`), never chunks of padding.
- Every write that sets a metadata or content-key envelope is signed (`Vault.signMetadata`/`signVersion`, Vault+Identity): root, folders, upload begin, the replacement's metadata, rename (over `metadataVersion + 1`), copy, rotation. The signing identity is re-checked against the served one at most every five minutes, so a succession on another device does not leave writes failing.
- Reading: `TrustedSigners` (Integrity.swift) holds, per account, the current signing key (which alone verifies) and the keys it replaced (which yield only `retiredKey`): the account's own identities and every verified pin's. Writers are named from pins only (`Writer`: "you", the pin's name, "someone you haven't checked"); the server sends `{ id }`. `DriveStore.trust` is a `TrustState`: pending (no marks), loaded, or failed, which marks every record "Couldn't check" with Try again, never no mark. `VerdictCache` keys verdicts on everything they depend on, both envelopes included. Earlier versions carry their own marks in the versions list and the viewer.
- Rotation, copy, rename and a replacement's new metadata check each record first and sign by its verdict (`Signing.after` over the core's `*_reseal_sign` in place, `Signing.copy` over `*_copy_sign` for copies): ordinary only when it verified, saved when it verified as saved from a link, re-sealed otherwise. Without the trust set a rotation waits (`RotationError.untrusted`, run again once it loads) and the others refuse.
- Pins carry `keyVersion`, `previousSigningKeys` (oldest first), `keysReplacedAt` and, once a succession was followed, `resealShares: true` (agreed with web and Android; written only when set, never cleared from here). Previous keys come only from the verified chain: from the first link whose old X25519, Ed25519 and ML-DSA digest are the pin's, as the core starts it (`ContactPin.chainStart`). A pin follows a succession only when the person taps "Check again" (`Vault.checkAgain`), and the chain is always fetched whole (`from=1`). Followed grantees are queued (`ResealTo`) for the next `Vault.upgradeShares`, which also finishes a re-seal a succession left unfinished (`ResealPending`). The People notice is dismissed per device (`ReplacedKeysSeen`, in `state/`).
- Shares open in suite 4 only (see below), with the granter's current keys (`ShareOpener`); one signed with a key they replaced says "Ask <name> to share it again".
- Settings are sealed as version 2 under the settings key (made and stored on first save). `GET /api/auth/settings` always reports the stored sequence (`settingsVersion`, 0 for no row), with `settings` null for no row or a version 1 row: the mark is checked against that sequence, a version 1 row reads as empty, and every save names the sequence and is sealed one above it (the sequence is bound into the seal). Master-key rotation rewraps the identity history and the settings key.
- Link visitor routes send the token in `x-link-token`, never the path (`PublicAPI`).
- Platform: third-party keyboards are refused (`AppDelegate`); passwords are typed only into secure fields, the eye draws the characters over them (`revealed`); the recovery phrase goes into `PhraseEntry` (no autocorrection, predictions or Writing Tools); copies to the pasteboard are local-only and expire; group folders and the mirror are `completeUntilFirstUserAuthentication` (background transfers need them while locked); `TemporaryCopies.sweep` runs in the app and the Files extension.

## Scoped ids and saved copies (added 2026-10-13)

- Every id the app chooses (root, folders, uploads in the app, the queue, Save to HushOS and Files, copies, links, reports) comes from `Vault.mint(kind, in: workspace)` over the core's `new_id`, in the workspace the item lands in (the parent's, which is the granter's inside a share; a report's is the reported item's). Each create sends the seed beside the id (`idSeed`, `versionIdSeed`, `objectIdSeed`, `linkIdSeed`, `reportIdSeed`); the server refuses any other id with 400 "This id was not made for this workspace". A copy within a drive mints a node and a version only: the object stays the source's. Nothing persists an id before its create succeeds (the queue keeps `SealedUpload`, made after the begin), so a resumed transfer only completes and never re-sends a create.
- Saved copies are signed by where they came from: "Save a copy" from a link (its files and the folders it makes) uses `Signing.savedFromLink`, the saved statements; a copy out of someone's share or across drives uses `Signing.copy` with the original's verdict, so a checked contact's verified file stays clean and anything else stays re-sealed. `SavedFromLink` shows no mark on rows or in the versions list; Info and the viewer show `SavedCopy.line` ("Saved from a link by you. HushOS can’t confirm who made the original.", "by <pin name>" for a checked contact) in muted ink, never in a warning's colour, and only when nothing about the item carries a mark.

## Post-quantum identities (added 2026-10-15, docs/identity-pq-design.md)

- `Vault.identityKeys` opens the identity once (a `Task`, so concurrent callers never upgrade twice) and upgrades a version 1 identity before anything signs: `identity_upgrade`, `POST /api/auth/identity/upgrade`, open what the server stored; a 409 means another device won, so re-read and open that. `DriveStore.loadRoot` calls `prepareIdentity()` first; every signed write goes through `identityKeys` anyway.
- `IdentityMarks` keeps the key version and the identity version: once version 2 is opened, a version 1 identity for the account is refused at any key version (stricter than the web's same-key-version rule; every identity made since the release is version 2).
- Own words are `identity_fingerprint_of_keys` over the four public keys the core re-derived when it opened the identity. A contact's words come from a lookup only when `identity_verify_keys` holds (`Contact.upgraded`); otherwise the sheet says they need to sign in once more and They match is off.
- Pins are version 3 (`mlDsaPublicKeyHash` + `kemPublicKeyHash` hex, v3 fingerprint, written by `ContactPin.of`); `verified` is the core's `pin_verified`. `ContactPin.compare` mirrors `comparePin` in packages/drive/src/trust.ts: same, recheck (a pre-release pin over the same classical keys: "Check words again"), succession (followed only by "Check again", version 2 chains, `PinnedKeys` with the ML-DSA digest) or changed. A recheck pin trusts nothing: no signer, no share opened or sealed.
- Shares are suite 4 (4565 bytes); `ShareOpener` opens with `HybridPublicKey` (pinned Ed25519, served ML-DSA only if its digest is the pin's). The upgrade pass re-seals any ledger share not in suite 4 once the grantee has a version 3 pin, and runs again right after a words check.
- Settings documents are written as version 2 (`Settings.json`), read as 1 or 2. Report operators and rotation grantees use the served-identity shape (`ServedIdentity`, `ReportOperator.keys`); the core decides which operator KEM key counts.
- `forgetIdentity` raises `identityGeneration` and `forgetSigners` raises `signersGeneration`; `identityKeys`, `allIdentities` and `signers` keep what they read only if the generation they began under is still current, otherwise they read again. Any cache built from the identity across an `await` needs the same check.

## Families (groups 1d, iOS 1 to 3; docs/groups-mobile-plan.md)

- `GroupsAPI.swift` reads routes 2, 3, 5, 6 and 25 with the session cookie (`DriveAPI.apiRequest`/`send`); family ids go into paths and file names only as lowercase UUIDs (`FamilyRecords.valid`). A refusal is `GroupsAPIError` (status, code, words), status 0 is no answer. Only 404 `not-member` wipes a family.
- `FamilySync` (an actor, one per session per process: `FamilySync.shared(for: vault)`, one family at a time) is the web's `sync.ts` + `pins.ts` over the core's `AreaLedger` (`Vault.areaLedger`): `prepareLedger` opens the account and the personal workspace; the settings are read first (every `loadSettings` hands the served settings key and document envelopes to the ledger, `useForFamilies` → `use_settings_envelope`, which opens them under the account root and takes the family and contact pins from what it opened; no app-built pin reaches the core); `accept_served` with the device record, `FetchFromVersionOne` called again with the same record, `Overtaken` read again up to three times, then `served_race_message`, `RecordUnreadable` deleted and accepted again against the settings pin; the record written (`FamilyRecords`, `local/groups/<user>_<group>.json` made with `Unbacked.folder`, one compare under the folder's `flock`, never over a later roster version) before route 25's folders are opened in the ledger (`open_family_area`: this account's self-grant when current, else the area grant, the holder identity opened by the ledger; a self-grant it wraps is stored with route 23, `GroupsAPI.putSelfGrant`, refusals other than not-member ignored; a grant or granter key that doesn't decode is passed as none so a self-grant still opens; no answer while reading the identity history fails the sync without forgetting anything) and each top folder listed through the ledger (`Vault.openListed`); then the settings pin settled (`merge_pin` with the acceptance's pin and the ledger's `pinArea`s only, compare and set in `saveGroupPin`, accepting again when the stored pin is ahead, conflicts or another device saved; four tries).
- A folder is a family's only when route 25 lists it under the family and its id is derived under it (`checkId`); then it is a family folder for the session (`Vault.familyWorkspaces`, `FamilySync.familyAreas`, `DriveStore.familyAreaGroups`), whatever later syncs say, and the personal workspace never is. Nodes there open only through `open_listed_node`; after a refusal or a fork the core holds the family's keys back until the next acceptance (`open_listed_node` refuses with "Check the family’s member list first.", which `FamilyWords` says as "Open the family again, then try again."). Not-member, fork, a refusal, unchecked and waiting forget what was opened (`forgetWorkspaces`: keys, rows, ids in `files-parents.json`), and `DriveStore.clearFamily` drops lists, names, thumbnails, marks and `tmp/opened/<id>`. No answer at all (`FamilySync.unanswered`, `AuthError.unreachable` included) leaves things as they were.
- Writes in a family folder (iOS 2) go through the ledger: `Vault.familyTarget` (`require_writable`; a folder route 25 named that the ledger doesn't hold is `FamilyWriteError.notOpen`, never the personal key path) gates `createFolder`, `rename`, `move` within the folder, `copy` within the folder, `trash`, `restore` back in place (a trash's Undo) and upload begin and completion; new keys come from `new_node_key` (forgotten with `forget_node_key` when the server refuses), keys a write seals under from `writable_node_key` at the epoch opened, re-wraps from `rewrap_node`. Records signed again (a rename, a copy, a replacement's name, a copy out of the folder) take their form from `FamilySync.prior` (the core's `copy_form` over the committed chain), never the personal trust set; FamilySync registers itself as the vault's weak `familyJudge` on every sync. Share, links, report, keep, versions and `rotate` still call `refuseFamilyWrite` (`FamilyWriteError.unavailable`, "This isn’t available in family folders."). A family folder row the server serves differently from what this process opened is opened through the ledger again (`Vault.open`), so a walk's re-key reaches the ledger's lineage.
- Uploads into a family folder go through the background queue with `Record.family` (group and workspace). Every decision is HushOSKit's `FamilyUploads` (`seal`, `finish`, `discard` over a `FamilyUpload` record, returning a `FamilyUploadStep`); BackgroundTransfers only applies the step (`apply`) and runs URLSession, so keep new recovery logic in the kit where `FamilyQueueTests` can reach it. `seal` runs off the pump (`FamilySync.ensureOpen`, the folder listed in its own workspace, then `Vault.sealUpload(waiting:)`). The ledger's KEY_CHANGE_PENDING and "older workspace key", the server's 409 `rotating` (`DriveAPIError.rotating`) and a 409 `stale` after a wait (`DriveAPIError.stale`) are one wait (`KeyChangeWait`): the folder is listed again and the upload sealed afresh after each pause (5 s doubling to a minute), the family checked again between (`familyJudge.recheck`, sharing a check already running), the row says "Finishing a key change…" (`Record.keyChangeSince`, kept across launches), and it gives up after 30 minutes with the web's words. Two seal at a time. The plaintext stays in the queue until the upload lands: a completion refused by a key change reached mid-flight (409 `conflict` with `data.conflicted`, `DriveAPIError.conflicted`; a late `rotating`/`stale`; KEY_CHANGE_PENDING) aborts, deletes the `part-N` files and seals afresh from `content` (`FamilyUploads.finish`, which also opens the family after a background launch); `UploadLanded` lands, never fails: a completed upload whose row doesn't open in this process, or a new version whose name record was refused after it went live (`published`; the queue keeps the record and `Vault.repairLanded` signs the name again on later passes). Once `completeUpload` returns, no error after it may fail, abort or re-seal the upload, and a replacement's name is re-signed only while `SealedUpload.landing` (its version id and the metadata version it replaced) still holds: a repeated completion is answered with the node as it is now, which may carry another member's rename or newer version. Callers of the foreground `Vault.upload` treat `UploadLanded` as done. An API 403 with a `code` is `DriveAPIError.forbidden` (a group manager's pause): final, never retried; only the store's 403 (an expired part address) is retried. Part tasks are described `<record>|<piece>|<server upload id>`; a callback naming another upload than the record's is dropped. A sync that wipes a family calls `BackgroundTransfers.endFamily`, which fails its queued uploads and removes their plaintext. Any other write that meets the wait says "HushOS is finishing a key change for this folder. Try again in a moment." (`FamilyWords.core`). Moves and pastes across spaces (`Vault.relocate`, `movesAcross`) upload again under the destination's keys and trash the original; the server's in-workspace move and copy are used only within one workspace. The move picker reaches writable family folders from Files' top level and Files from a family folder.
- The screens offer writes only while `DriveStore.familyWritable` (the area is openable and `write == .writable`); family items read as `.editor` then, `.viewer` otherwise, and never as own (no Share, Tags, Versions, Report, Keep or Save a copy; Select's Share and Tags are off).
- Self-grants (route 23) are opened and stored through the ledger (Core 6): a folder whose granter's identity is gone opens once this phone (or the web) stored a self-grant at the current key. No key of a family folder crosses the FFI; `area_grant_open` and `open_area` are no longer exported.
- Marks and Info (`FamilyIntegrity.swift`, twins of trust.ts `recordIssues`/`sortIssues` and integrity-lines.ts): `FamilySync.verdicts(of:groupId:)` runs `record_verdict` on the name and current version with writers built from route 6 and the current trust set at every call, then the web's issues, lines, label (`Keys don’t match` in the danger colour, `Couldn’t check` with Try again), `Changed by`/`Written by`, `Keys replaced by`, and `Checked: Verified by <family>` only when nothing is marked. Members nobody checked are named as route 3 names them, with the address (D10). Errors are worded by `FamilyWords` (never a `CoreError`'s description). The store judges again after every accepted sync and every `refreshSigners`.
- UI (`App/Families.swift`): Account's Families section (route 2, hidden on a server without families or with none; a pass within a minute is reused, pull to refresh always checks), the family page (the hard warning with Technical details, Couldn't check with Try again, not in it any more, the join screen while waiting or unchecked (iOS 3), previous keys, folders the member list names that aren't its own, Family folders, Members with roles from the accepted list and names from route 3, Technical details), and each folder as `FolderView`, read only (no Add, Select, paste bar) unless this device may write there (iOS 2, above). Family items read as `.viewer` and never as own. A family folder that can't be opened (cleared by a fork or refusal, or refused on listing) shows `FolderProblem.family` with FamilyWords' words and Try again (the family checked again), never "Nothing here yet". A family folder on screen checks its family again when the last check is over three minutes old, and on returning to the foreground at most once a minute. Sign-out calls `FamilySync.forget()`, which drops the session's sync and wipes its ledger.
- Joining (iOS 3): `FamilyJoin.swift` is the web's `join.ts` over the core's join calls (`FamilySync.joinStatus`, `confirmJoin`); the two hidden positions are drawn and kept by the core and never leave the ledger, so never put them (or the typed words) in a request, a log or the settings. The joins record and the escalation (`holds`) sit beside the device record (`FamilyRecords.read/put/delete(.joins|.holds, …)`); store the `holds` every check returns in place of the last, delete it only on none or `HOLDS_UNREADABLE`; keep the joins record only between `Matched` and the end of the join. The kept escalation goes into the ledger once per `FamilySync` (`restoredHolds`), which is only right because a `FamilySync` lives exactly as long as its ledger: never call `areaLedger.clear()` without replacing the sync (`FamilySync.forget` does both). The join's steps and syncs share one turn per family (`FamilySync.exclusive`). The `.holds` files go on every wipe (sign-out, deletion, the removed-device wipe, `claim`), as the web's do (owner, 2026-10-28); the accepted cost is that a server answering "removed" resets the alarm. `Vault.fromKeychain` gives one vault per session per process (the app and the background queue must share it, or the family syncs and ledgers split); `FamilySync.forget` lets it go. `/join` is parsed but goes into the web's apple-app-site-association only with the first release that handles it (an older installed build would dead-end the invitation). Screens: `App/Join.swift` (`InvitationSheet` for `/join#invite=` links, which MainView opens, with `InvitationNotice` deciding the note and Accept; `JoinSections`, which the family page shows for `waiting` and `unchecked`); while a join screen is open `DriveStore.familyJoining` (a count) keeps background checks off the family, and `DriveStore.joined` adopts the joined state.
