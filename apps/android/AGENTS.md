# HushOS for Android

Jetpack Compose app with Material 3 Expressive, minSdk 29, and the DocumentsProvider that puts HushOS in the system file picker (Storage Access Framework) and in Files by Google; Samsung's My Files never lists third-party providers. `:core` holds the UniFFI Kotlin bindings of `crates/hushos-core` and its shared libraries; `:app` is the app. The repository's root `AGENTS.md` applies here too.

## Building

```sh
bun run core:android    # Rust -> core/src/main/jniLibs and the generated Kotlin (needed once, and after any core change)
bun run android:build   # debug APK
bun run android:run     # boots the Pixel_9_API_36 emulator if needed, installs, forwards ports, launches
```

Toolchain on this Mac: SDK at `~/Library/Android/sdk` (platform 37, build-tools 37), NDK 27, JDK 21 at `/opt/homebrew/opt/openjdk@21`, Gradle 9.6 through the wrapper, AGP 9.4 (built-in Kotlin: do not apply `kotlin.android`). `adb reverse tcp:5173` and `tcp:9000` let the emulator reach the web dev server and Garage on the host as localhost; the run script does it.

## How it fits together

- The session, the remembered device and the origin live in `EncryptedSharedPreferences` under an Android Keystore master key. The provider runs in the app's process and reads the same file; a missing session becomes `AuthenticationRequiredException`, which the system shows as a sign-in affordance that opens the app.
- `Vault` mirrors the iOS one: keys opened on demand, a node-to-parent index in `filesDir`, downloads and uploads chunk by chunk through the core, thumbnails as JPEG at upload.
- `HushOSDocumentsProvider`: roots, children, recents (from the change feed), open (download to cache), write-back on close (a new version), thumbnails, create, rename, move, delete (to the trash).
- The UI keeps Material's own shapes and colours (dynamic colour when the device offers it, Paper's blue on the desk otherwise). Material 3 Expressive APIs need the 1.5.0 alpha line; the stable 1.4.0 hides them.

## What the app does

The same four tabs as iOS: Home (search, type chips, tags row and manager with presets plus any hex colour), Files (search, tag filters, floating add menu, long-press selection with a contextual bar for copy, cut, move and trash, a paste bar while the clipboard holds items, the replace, keep both or skip prompt for same-name uploads), Shared, Account (name, plan and storage, read only with no way to buy; while `/api/auth/storage` names a `pool` the card is the family's plan, "Shared with <family>", and the pool's figures (no Files row: the total is counted in whole GB), and "Not enough room" reads `availableBytes`, never quota less used, decided by `PlanDisplay` in `data/Auth.kt`, which falls back to the personal plan when `pool` is absent or unreadable, and names that plan only while it is live (`PlanStanding`, the web's `planStanding`: not ended and active, trialing or past_due); unpaid, incomplete or paused reads Free with the lapsed plan's words (`LapsedPlan`), said and never linked, and anything ended reads Free; change password, delete account, Contacts and Your twelve words, trash, sign out). People (`PeopleSheet` in `ui/LinksUi.kt`, from Account and the Shared header) has the add-by-email field, then a Your twelve words row, then the list sorted by name with Find someone from eight contacts; Your twelve words is one `OwnWordsSheet` drawn by `Main` while `DriveViewModel.showingOwnWords`, which checks the served identity first (`Vault.currentOwnFingerprint`). Nested screens pass `contentWindowInsets = WindowInsets(0)` because the outer Scaffold already pays the navigation bar inset.

## Things learned the hard way

- `adb shell content` cannot query the provider (it needs `MANAGE_DOCUMENTS`); verify through the system Files app or a picker.
- Files keeps a folder's listing until that folder's children URI is notified. Every `Vault` write and every `Vault.sync` that touched something notifies the folders it changed through `FilesRoots.foldersChanged` (the top folder by both `root` and its node id); a new write path that bypasses `Vault` must do the same. Each `Vault` pulls the feed from its own `catalogueCursor`: the app, the provider and the transfer jobs share one mirror, and the mirror's cursor once let the app's sync swallow the changes the provider's catalogue never filed. That own cursor counts only within the mirror generation it was taken under (`Mirror.FeedState`: every clear bumps it and marks a refill owed until one reaches the head), so a refill that failed partway is carried on from the mirror's cursor, never jumped by a vault that was already current; pulls hold `Mirror.feedLock`, and `resync` is heeded only on a pull's first page, as the web client does (later refill pages sit below the dropped tombstones by nature). A refill carries no tombstones, so a build from a whole mirror at the head evicts (and marks gone) every cached row the mirror no longer holds; any build over an existing catalogue (a reset, a failed rebuild, rows under an unseen folder) goes through `rebuildCatalogue`, which tells Files what differs. Once Files has its listing, Android caches the HushOS process and freezes it within seconds, so a provider thread can't poll; `FilesPollService` (a `JobService`, not WorkManager, which may run work in the process without a job) polls every 30 s until 2 minutes after the last listing or the screen goes off (the owner chose this over 10 s for 5 minutes, 2026-11-01). DocumentsUI itself waits about 10 s after a notification before it asks again. Its swipe-down calls the provider's `refresh` (logcat `RefreshTask: Provider supports refresh and has refreshed`): a sync queued behind any running pull, the folder told, the binder held at most 5 s (`ProviderRefresh`); a false answer makes DocumentsUI reload by itself. Whether Files by Google's pull-down calls it is unverified (the emulator images have no Files by Google). Tests: `FilesChangesTest`, `FilesRootsTest`, `FeedPullsTest`, `ProviderRefreshTest`.
- `adb shell input text` into a focused field then tapping the next field mixes the two; move between fields with keyevent 61 (Tab) and submit with 66 (Enter).
- `Vault` is tested whole against `FakeDrive` (app/src/test, a JDK `HttpServer` on loopback serving the Drive, auth, link and object-store routes it calls) under Robolectric, which gives it a real `Context` for its files, SQLite mirror and preferences; the real `DriveApi`, `Auth` and `PublicApi` do the HTTP. `Shared`'s Keystore-backed preferences have no JVM provider, so the test swaps plain ones into `Shared.opened`. `FakeDrive.record` opens what the server holds under keys unwrapped from its envelopes, as another device would. It keeps the settings key (stored once) and the settings document (compare-and-set) as the server does, since the vault's sealed rollback marks need a settings key before anything opens. `VaultAttributesTest` uses it for every re-save path. Run the unit tests on JDK 21: on JDK 26 Robolectric 4.16 fails every test with "Unsupported class file major version 70".

## Sharing, links, reports, rotation (added 2026-09-22 evening)

- `data/Links.kt` (owner link views, `PublicApi` without a cookie, `LinkVault` for a visitor, `Reports`), `data/Contacts.kt` (pins, owned shares, shared-by-me rows) and the matching `Vault` functions; `Auth.rotateKeys` and `Auth.recoveryKey`. The UI lives in `ui/LinksUi.kt` (share sheet with People and Links, link browser, report dialog, contacts sheet, phrase grid).
- Long press opens the item sheet, whose first row is Select; the FAB also offers "Select items".
- Writes use `workspaceOf(parentId)` so an editor can add to a shared folder; the paste bar refuses a cross-drive paste.
- `SegmentedButton` must be called inside `SingleChoiceSegmentedButtonRow` unqualified: it is a member of the row scope.
- Revoking a share rotates the subtree (`data/Rotation.kt`, same protocol as the web), never a node beside its parent in one batch (`deferChildren`: the server judges each node on its own, so another device can win the parent while this one wins the child, sealed under a key nobody kept); a parent another device re-keyed is read from the server (`adoptServedKey`) before its children are wrapped under it. Test: `RotationRaceTest` (FakeDrive judges each node, `rekeyedElsewhere` and `beforeRotationSend` stand in for the other device). Shared folders open through `BrowseScreen(start = root)`, so they get search, select, the paste bar and the add button in the granter's workspace; pasting across drives re-uploads (`copyAcross`).
- Who can open what (`DriveState.access`, from `/shares/mine`) is asked again through `ui/SharingRefresh.kt`: at once after every restore (`write(restored = true)`, the batch, a trash's Undo) and after a sync that applied a change in the own drive, at most once per 10 s with one load at the interval's end (the server leaves trashed items out, and a change can't say it was a restore). `access` is replaced only when the marks changed; `accessLoads` moves when what the server lists changed (`SharingRefresh.listing`: share ids with roles, link ids; the marks leave out expired links and count links), and an open By me reloads on it. The trailing load is launched lazy and recorded before it starts (viewModelScope runs a body inline). Tests: `SharingRefreshTest` (iOS's `SharingRefreshTests` cases, plus a load due at once on an immediate dispatcher is neither lost nor left blocking the next).
- Transfer jobs carry no file or folder name in WorkManager (input, tags, output): its SQLite file keeps pruned jobs in free pages and sign-out can't empty it. Names live in `JobNames` (`job-names.json`, an account file), which the panel and workers read; `JobNamesTest` holds the requests to it.
- Keep downloaded lives in `data/Offline.kt` (private storage, one folder per version) with an Offline section on Home; the item sheet scrolls, and the action sits right under Rename so it is reachable without scrolling.
- Every folder handed to another app through `FileProvider` must be listed in `res/xml/shared_paths.xml` (`opened/` and `links/` under cache, `offline/` under files); a missing entry crashes with "Failed to find configured root".
- Compose dialogs shift up when the keyboard opens: read positions again after typing, and hide the keyboard with Back (not Escape, which dismisses the dialog) before tapping a dialog button.

## Running on a real phone (added 2026-09-22 evening)

- Enable Developer options and USB debugging on the phone, plug it in, accept the debugging prompt, then `bun run android:device` (builds the shrunk release APK, 6.6 MB against 77 MB for debug, and `adb install -r`s it). The release build type is signed with the debug key until a release key exists; `bun run android:release` just builds it, to sideload from `apps/android/app/build/outputs/apk/release/app-release.apk`. R8 needs the keep rules in `app/proguard-rules.pro` (JNA and the generated `com.hushos.core` bindings are reached by name).
- A real phone defaults to `https://hushos.com` (`defaultOrigin()` in `DriveViewModel.kt` checks the build fingerprint); the emulator keeps `http://localhost:5173` through `adb reverse`.

## The mirror and the catalogue (added 2026-09-22 night)

- `data/Mirror.kt` (SQLiteOpenHelper: nodes, cursors, thumbnails) and `data/Catalogue.kt` mirror the web: pull the whole feed once, open rows parents first, then `sync()` pulls only changes. `listChildren`, `recents`, `trash` and `thumbnail` answer from the catalogue first. `NodeView.rawJson` keeps the row as served for the mirror.
- The view model builds the catalogue after `loadRoot()` and syncs before every refresh. A `Surface` in `HushOSTheme` paints the background, and `values-night/themes.xml` gives the window a dark theme; without both, dark mode showed grey text on white.

## Post-quantum identities (added 2026-10-15, docs/identity-pq-design.md)

- `data/OwnIdentity.kt`: `openOwnIdentity` opens the identity and upgrades a version 1 one (`identity_upgrade`, `POST /api/auth/identity/upgrade`, a 409 adopts the identity another device stored) before anything is signed; `Vault.identityKeys()` goes through it and `loadRoot` calls it first. `SettingsMark` keeps the settings sequence, whether a version 2 settings document was seen, and `(keyVersion, identityVersion)`, and refuses the version 1 form once version 2 was seen. The marks are one record per account in `noBackupFilesDir/marks/<slot>.json`, sealed by the core under a key from the settings key (`rollbackMarksUpdate`, the web's format; `Vault.marksKey`: the envelope kept beside them, then the vault's key, then the server's, made only to keep a first mark); a record that does not open is `MarksUnreadable` and a mark that can't be kept `MarksUnsaved`, and either fails the step. `AccountStore.wipe` (sign-out, deletion, removal) deletes them and the plaintext `settings-seen.json` earlier versions kept across sign-outs, which the first read folds in and removes. Own words are `identity_fingerprint_of_keys` over the four opened keys.
- `OpenedIdentities` (in `OwnIdentity.kt`) keeps the opened identity and the history for `Vault`: opened under its lock, `forget` waits for an open under way, and a history read is kept only while the identity it was read beside is still the one in use (`OpenedIdentitiesTest` holds the fake server's reply to prove both). Trust loads overlap: the view model's `refreshTrust` (each call follows a change) keeps only the latest one begun (`TrustLoads`), while the provider's `trustFor` (asked from many threads per listing) shares one load (`SharedLoad`: `reset` names the current vault under the provider's `vaultLock`, one Vault per session; a request still holding a dropped vault loads for itself, never shared or kept); both in `Integrity.kt`, tested by `TrustLoadsTest` and `SharedLoadTest`. A followed pin always keeps its own signing key among the previous ones (`previousKeysAfter`).
- `data/Contacts.kt` mirrors `packages/drive/src/trust.ts`: `ServedIdentity` is the served shape everywhere (lookups, granters, grantees, rotation work, operators); `ContactPin.trust` is the core's `pin_trust` (verified, seen, legacy, invalid), `compare` its `compare_pin`, `commitment` its `key_commitment` (never `fingerprint`, which every first-seen pin holds as `""`); `granterKeysOf` opens suite 4 with the pinned Ed25519 key and the served ML-DSA key whose digest the pin holds. A pin is written only over a contact whose keys statement holds (`Contact.upgraded`).
- Shares are suite 4 (`SHARE_SUITE`); the re-seal pass seals anything older and runs after this device's upgrade and after every words check. The web test fixtures (`crates/hushos-core/fixtures/web.json`) are parsed with `Auth.identityEnvelope`, as the app parses served ones.
- The dev tools need `ANDROID_HOME=$HOME/Library/Android/sdk` in a fresh worktree (no `local.properties`).

## Foldables and large screens (added 2026-10-29)

- `ui/Adaptive.kt` decides the frame from the window in dp (`navKind`, `tabletopSheetMax`, tested in `AdaptiveTest`): the bottom bar below 600dp wide, below 480dp tall or in tabletop; the collapsed `WideNavigationRail` from medium; its labels from expanded until Info beside the list would leave the list under 360dp (the Fold opened flat: rail folds to icons while Info is open). `Main` draws it through `NavigationSuiteScaffoldLayout` with the app's own bar and rail (the bar is the phone's unchanged `NavigationBar`), and the tabs inside one `SupportingPaneScaffold`, so every window size has the same composition tree and a fold, an unfold or a resize finds each screen's saved state where it left it. Never add a size-dependent branch around a screen: its `rememberSaveable` keys change and the folder, selection and sheets reset.
- Info is the navigator's Supporting destination (`rememberSupportingPaneScaffoldNavigator<String>`, the item id; saved across configuration changes): beside the list while the directive has two partitions (expanded, or book posture, where the panes split at the hinge), otherwise `Main` draws `InfoSheet`. `ItemActions` hands Info to `LocalInfo` instead of drawing it; `Main`'s own sheets provide no `LocalInfo`. Share and Tags from Info are `Main`'s `infoSheet`, so they survive a fold too. Info closes only on a removal the server confirmed (`infoLookup`): the row held but not `NodeCache.live` (trashed, or a trashed folder above it in its own workspace), `NodeCache.gone` (trashed from here, a feed tombstone, a purge: `remove`, never `forget`, which drops a row to be read again; marked per workspace and node, and once Info has shown a row it asks only about that workspace's node), or its workspace no longer among the listed shares, or (a received share's item only) its absence from the list its own parent shows after a refresh (`missingFromShareList`): a decision for Info alone, which never removes or evicts a cache row (versions that did lost trashed rows from the Trash and brought concurrent removals back; trash, tombstone and purge keep `remove`). Residual: in a received share, a folder above Info's item trashed elsewhere leaves Info open until it is closed (the item's own parent still lists it, and the owner's feed never reaches this device). Only explicit folder refreshes count (`refresh`, a pull or a first load of the folder the item is in now, `ParentRefresh`); the reloads after a write or a settle don't, which only leaves Info open. A row merely absent (a rotation's `forgetRows`, a catalogue update reopening it) keeps the last one shown; one this process never held (after a restart) is looked up once. In tabletop `Sheet` bounds its content to the space below the fold less what Material lays out around it (handle, bottom inset; `sheetContentMax`), never the sheet's own modifier, which sits ahead of Material's anchors and would open a full sheet at the top of the window; with the keyboard up the limit lifts (`sheetLimit`).
- Continuity: sheet and dialog targets, typed passwords and links, and upload questions are `retain`ed (Compose runtime-retain: kept in memory across a configuration change, never written to the saved-state bundle); ids and choices without names are `rememberSaveable`. Folding locks this emulator whatever `fold_lock_behavior_setting` says: swipe the keyguard away.
- Emulator: `HushOS_Fold` (pixel_fold, android-36 google_apis arm64) in `~/.android/avd` (avdmanager writes to `~/.config/.android/avd` unless `ANDROID_AVD_HOME` is set). `adb emu fold` / `adb emu unfold`, `adb emu posture 2` half open (`3` flat), rotation with `settings put system user_rotation`; two displays, so `screencap -d` the inner (`4619827259835644672`) or outer (`4619827551948147201`) one.

## Contacts without comparing words (added 2026-10-30, docs/optional-verification.md 2 and 6)

- Twin of iOS 5a (`Vault+Trust.swift`, `ContactGuard.swift`). `data/ContactGuard.kt` is the contact guard: one record per account in `noBackupFilesDir/guard/<contact_guard_slot>.json`, sealed by the core (`contact_guard_seal`/`_open`, HKDF from the settings key) with the settings key's envelope beside it, found through the vault's `marksKey` as the rollback marks are. A record there that won't open is `GuardUnreadable` (everyone pauses: "HushOS couldn’t check this right now."), never first use; a write that can't be kept is `GuardUnsaved`; a commit over a stale revision is `GuardRaced`. Writes are read-change-write under one process-wide lock (the provider shares the process) and a sign-out generation; `AccountStore.wipe` deletes it (`ContactGuard.deleteAll`). `GuardTurn` serialises acts and the readers that judge from the guard across the app's and the provider's Vaults.
- `data/ContactTrust.kt` orders the reads and writes; every rule is the core's (`pin_of_served`, `pin_trust`, `compare_pin`, `key_commitment`, `pin_first_seen_of_legacy`, `guard_agrees`, `guard_entry_next`). `stand` says where this phone stands with one person; `commitTrust` writes the pending act (again before each compare-and-set attempt, `updateSettings(beforeSend =)`), saves, then commits the guard; `guardFor` finishes a pending act whose save landed. Anything that leaves shares on older keys (`resealShares`: Continue, They match over new keys, a followed succession) is queued in `ShareSeals.queue` before the save that owes it, and again when a later read finishes the act; the re-seal pass seals queued people regardless of the seal record.
- Acts: `addContact` (no words), `lookup`, `continueWith`, `theyMatch`, `remove` (records `removedContacts`), `trustGrantee` (share, rotation via `granteeSealer`, re-seal pass), `trustGranter` (mounting, `MountPass`: settings read once per pass, one verdict per granter and full served identity, `Contact.trustKey`), `openWaiting`. `Settings.setPinOnce` moves a pin stored under the id in other letters (raw JSON, every field) to the served id, forgets the removal, forgets removals oldest first for room and refuses past 64 KiB with "Your contacts are full. Remove someone you no longer share with."
- Verdicts: `Trust.of` takes `effectivePins()` (the guarded view); a first-seen pin's records read `SEEN`: no mark, Info's "Added by" with "Not verified · Check it’s Maya" (`seenByOf`). The mark's words are 6.12's; its way out is Check it's Maya (a pin that vouches for nothing) or Check who wrote this (Add someone with `writer`, then the words), shown by `Main` (`DriveViewModel.contactStep`) so it outlives the mark.
- UI (`ui/ContactsUi.kt`): `ContactStepSheet` (Add someone, Check it's Maya with the mismatch path and Remove, "Maya's account changed" with both variants and Technical details) takes the place of the sheet it was met in. The share sheet's lookups (`Vault.shareeChanged`) are kept a minute (`cachedLookup`), forgotten on Continue, They match and removal, three at a time (`ShareeChecks`), never on the sheet's own reloads, and a failure is said. Stop sharing never waits on Review. Tests: `ContactGuardTest`, `ContactTrustTest` (FakeDrive serves lookups, successions, `startOverGrace`, settings edits and a lost save answer), `SettingsTest`.

Every wipe of a family (a sync's not-member, route 2's reconciliation, a member check, a join, a leave), whoever runs it (the background work through the app's vault included), is queued in `FamilySync.takeRemovals` (`publishRemovals`), and so is one whose wipe couldn't finish (`FamilyState.Failed.removal`) and any refusal a sync met (a fork, an unchecked chain, a rollback: everything but accepted and no answer), shown by the model as its own sync's would be (`applyRemovals` → `show`); an unfinished wipe on a listed family makes the background pass RETRY, and the model is told (`onRemovals`), so the screens let go of them too; a join that lands schedules the job at once (`FamiliesModel.joined`). A WorkManager stop (its window, the network lost) cancels the worker's coroutine but not the blocking pass, so the pass takes `checkStop` (JobStopped, as the transfer workers' `stoppable`) and checks it between families, walks, batches and feed pages, never with a batch's keys pending: a stopped pass sends nothing more, leaves no folder locked and answers STOPPED (retried). Jobs are per session (a tag, unique names and input carrying `FamilyWalkWork.sessionKey`, a digest of account and token); a pass works and stops only while its vault is open and still the session signed in (`current`), stops cancel only its own session's jobs, and a job of an ended session does nothing.
