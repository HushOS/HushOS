## Scope

This page describes what is implemented. It covers sign-in, the account key, identity keys, recovery, and remembered browser unlock. The byte-level protocol lives in the `@hushos/crypto` package and is specified in `docs/opaque-auth-design.md` in the repository. Where this page and the code disagree, the code is right and this page has a bug.

## Sign-in without sending a password

HushOS uses OPAQUE, a password-authenticated key exchange, through the Serenity implementation. During registration your browser and the server run a short protocol that leaves the server with a record it can use to verify future sign-ins. The password never leaves the browser, not even as a hash.

OPAQUE produces two secrets. The **session key** is shared with the server and used only for the authenticated session. The **export key** is known only to the client. Only the export key is used for encryption, and only after a further derivation step.

## The account key

Your account key is 32 random bytes generated in your browser. It is not derived from your password, so changing the password does not change the key. Two independent wrappings of the same key exist:

/>

Every envelope carries associated data that names its purpose, version, and owner. An envelope moved to another account or another version fails to open.

## Identity keys

At signup the browser also generates an X25519 key pair for encryption and an Ed25519 key pair for signatures. The private halves are wrapped with keys derived from the account key and bound to their own public keys, so a swapped public key is detected when the envelope is opened. Only public keys and wrapped private material reach the server. These identities prepare for recipient key exchange and signatures; they are not a sharing protocol on their own.

## Recovery

A 32-byte recovery secret is generated on your device and shown once as 24 English BIP39 words. It wraps the same account key, so recovering with the phrase preserves everything the key protects. A backup of the secret is stored encrypted by the account key, which is how the phrase can be shown again while your device is unlocked.

Resetting a password requires a verified email link and the phrase. The browser proves it holds the phrase by signing the reset with a key derived from it, re-registers with OPAQUE under the new password, and rewraps the unchanged account key. The server checks the signature and every binding, replaces the credentials in one transaction, and revokes every other session. A reset issues a new recovery phrase.

<Note title="What recovery cannot do">
    Replacing a phrase stops it from authorising future resets, but an old phrase paired with an old
    downloaded kit can still open the unchanged account key. Email alone can never restore a lost
    key. If you lose your password, your remembered devices, and your recovery kit, the key is gone
    and so is access to what it protects.
</Note>

## Remembered browser unlock

The plaintext account key lives only inside a Web Worker. To let a browser reopen your account without the password, the worker wraps the key with a non-exportable AES-256-GCM device key held in IndexedDB. What is persisted is a versioned encrypted bundle and a lock revision; the key itself never enters application state. Locking the device discards the bundle. Signing out anywhere with a credential change locks every remembered device.

## What comes next

Drive will apply the same shape to files: keys created on your device, content encrypted before it leaves, and envelopes bound to their owner and version. When it ships, this page will document the file and folder key hierarchy in the same detail. Until then, treat anything not on this page as not implemented.
